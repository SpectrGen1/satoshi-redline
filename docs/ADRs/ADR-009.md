# ADR-009: Keep Core Execution Local and Prohibit Outbound Telemetry by Default

* **Date:** 2026-07-30
* **Decision owners:** SATOSHI//REDLINE maintainers
* **Depends on:**

  * ADR-001 — Use a Go Modular Monolith for the Diagnostic Backend
  * ADR-002 — Use Capability-Based, Composable Platform Adapters
  * ADR-003 — Separate Observations, Findings, and Diagnoses
  * ADR-004 — Run the Main Daemon Unprivileged and Isolate Deep-Scan Access in an Optional Privileged Helper
  * ADR-005 — Do Not Persist Raw Logs or Protocol Responses
  * ADR-006 — Version External API and Report Schemas Independently from Internal Models
  * ADR-007 — Compile First-Party Probes into the Redline Binary for v0.1
  * ADR-008 — Require Explicit Reasons and Coverage Semantics for Unknown Results
* **Scope:**

  * Core network behavior
  * Telemetry and analytics
  * Crash reporting
  * Update checks
  * Diagnostic network connections
  * Local API exposure
  * Report export and sharing
  * External assets and dependencies
  * Future notification and subscription boundaries
* **Excluded from scope:**

  * Exact local API authentication design
  * Mobile push-notification implementation
  * Hosted monitoring architecture
  * Paid support workflow
  * Software-update installation mechanics
  * Remote administration
  * Automated remediation

## Context

SATOSHI//REDLINE is intended to diagnose privacy-sensitive Bitcoin infrastructure.

The system may be installed alongside:

* Bitcoin Core or Bitcoin Knots
* Electrs or Fulcrum
* DATUM
* Stratum services
* mining hardware
* Tor
* Docker
* systemd
* wallet backends
* host filesystems
* private LAN services

Even when Redline follows ADR-005 and does not persist raw logs or protocol responses, its network behavior can still reveal sensitive information.

A silent outbound request may disclose:

* that the user runs Redline
* the Redline product version
* the approximate time the node is active
* the public IP address of the host
* the use of a particular platform
* the presence of Bitcoin or mining infrastructure
* the timing of failures and recoveries
* the frequency of diagnostic scans
* the user’s timezone or locale
* the existence of Tor or mining services
* installation identifiers
* component versions
* support or purchasing intent

A telemetry system does not need to upload raw logs to create a meaningful privacy leak.

For example, a request such as:

```text
GET /check-update?version=0.4.2&platform=umbrel&arch=arm64
```

may reveal enough information to identify a rare deployment.

Similarly, a crash-reporting SDK may automatically collect:

* stack traces
* memory values
* local paths
* process arguments
* environment metadata
* component names
* request context

An analytics library in the web UI may contact a third party every time the local dashboard opens.

An externally hosted font, script, icon, chart library, or stylesheet may reveal dashboard use even if Redline itself sends no telemetry.

The product must still make network connections to perform legitimate diagnostics.

Examples include:

* connecting to Bitcoin RPC
* connecting to an Electrum endpoint
* testing a Stratum listener
* communicating through Tor SOCKS
* checking a configured DATUM interface
* resolving a configured local service hostname
* optionally verifying that a configured external dependency is reachable

These are not automatically telemetry. They are part of the user-requested diagnostic operation.

The architecture therefore must distinguish:

1. Traffic needed to inspect the user’s configured system.
2. Traffic to Redline-operated infrastructure.
3. Traffic to unrelated third parties.
4. Traffic initiated explicitly by the user.
5. Traffic occurring silently in the background.
6. Local, LAN, Tor, and public-internet destinations.
7. Product updates, notifications, support uploads, and commercial services.

The phrase “local-first” is insufficient unless these distinctions are enforceable.

A product can claim to be local-first while still:

* performing silent update checks
* sending anonymous usage metrics
* loading UI assets from a CDN
* uploading crash reports
* using remote feature flags
* contacting a licensing service
* resolving vendor domains
* using cloud-hosted AI analysis
* requiring an account for core functionality

SATOSHI//REDLINE’s core value must not depend on any of these.

## Decision

SATOSHI//REDLINE’s core diagnostic engine will execute locally and will not transmit telemetry, analytics, diagnostic results, crash reports, usage information, installation identifiers, or component metadata to Redline-operated or third-party services by default.

The core product will remain fully functional without contacting SATOSHI//REDLINE infrastructure.

The default installation will perform no automatic network communication except:

1. Connections to explicitly configured or platform-declared diagnostic targets.
2. Connections required to serve the local Redline API and web interface.
3. Network operations explicitly enabled as part of a named diagnostic check.
4. Operating-system behavior outside Redline’s direct control, where clearly documented.

The following will not occur by default:

* usage analytics
* product telemetry
* remote metrics
* crash uploads
* automatic support uploads
* remote feature flags
* licensing checks
* account authentication
* cloud-based diagnosis
* remote configuration
* remote probe updates
* silent update checks
* third-party web analytics
* CDN-loaded UI assets
* externally hosted fonts
* public telemetry endpoints
* Redline-operated DNS queries
* automatic report sharing
* remote-control registration

Any future feature that communicates with Redline-operated infrastructure must:

1. Remain separate from the local diagnostic core.
2. Be disabled until the user explicitly enables it.
3. Describe the destination and data categories before activation.
4. Use a distinct capability or service boundary.
5. Avoid receiving forbidden data.
6. Be independently disableable.
7. Fail without degrading core local diagnostics.
8. Be governed by a separate ADR when it materially changes the privacy model.

The central decision is:

> Redline may connect to the system the user asked it to diagnose. It may not silently report on that system—or on the user—to anyone else.

## Decision drivers

The decision drivers, in priority order, are:

1. Preserve user privacy at the network boundary.
2. Make the core diagnostic product usable without an account or cloud service.
3. Prevent silent disclosure of Bitcoin-node and mining-stack operation.
4. Keep product claims technically verifiable.
5. Distinguish diagnostic traffic from vendor telemetry.
6. Avoid third-party tracking through frontend dependencies.
7. Preserve deterministic behavior in disconnected environments.
8. Ensure future commercial services remain optional layers.
9. Make every public-internet connection attributable to a declared feature.
10. Keep local failures diagnosable without depending on external infrastructure.

## Terminology

### Local execution

Local execution means that diagnostic collection, normalization, evaluation, correlation, persistence, report generation, and user-interface rendering occur on infrastructure controlled by the user.

Local execution does not necessarily mean that every diagnosed component runs on the same machine.

A Redline installation may diagnose:

* a service in another local container
* a node elsewhere on the LAN
* a miner on a private subnet
* an Electrum endpoint reached over Tor
* a remote component explicitly configured by the user

The important property is that Redline does not send the resulting evidence to an unrelated external analysis service.

### Diagnostic target

A diagnostic target is a component or endpoint that the user, platform, or discovered dependency graph identifies as part of the system being diagnosed.

Examples:

```text
Bitcoin RPC endpoint
Electrum server
DATUM status endpoint
Stratum listener
Tor SOCKS proxy
miner management endpoint
StartOS service interface
Umbrel application dependency
```

A destination does not become a diagnostic target merely because a probe developer wants to contact it.

It must be tied to:

* explicit user configuration
* authoritative platform configuration
* a validated component binding
* or an explicitly enabled external diagnostic operation

### Telemetry

Telemetry is data sent away from the user-controlled diagnostic environment for product analytics, monitoring, development, commercial, or support purposes.

Telemetry includes more than metrics.

Examples include:

```text
application started
scan completed
feature used
probe failed
platform type
component version
installation ID
anonymous crash
performance timing
report generated
update available
```

Telemetry remains telemetry even when:

* identifiers are hashed
* the payload is described as anonymous
* the information seems harmless
* no raw logs are included
* it is used only for product improvement
* it is sent through Tor
* it is retained briefly

### Explicitly initiated communication

Communication is explicitly initiated when the user knowingly performs an action whose immediate purpose requires the communication.

Examples:

* selecting “Check for updates”
* selecting “Send this report to support”
* enabling push notifications
* testing a configured external endpoint
* enabling a hosted monitoring subscription
* signing into a separately defined account service

Opening the local dashboard does not constitute consent to analytics.

Installing the application does not constitute consent to telemetry.

Running a scan does not constitute consent to upload results.

### Background communication

Background communication occurs without a contemporaneous user action.

Examples:

* periodic update checks
* telemetry heartbeats
* crash-report retries
* remote feature-flag refresh
* licensing validation
* background support upload
* remote configuration polling

Background communication to Redline-operated or unrelated public services is prohibited in the core default configuration.

### Redline-operated service

A Redline-operated service is infrastructure controlled by the SATOSHI//REDLINE project or its commercial operator.

Examples may eventually include:

* update metadata
* push-notification relay
* monitoring service
* support portal
* account service
* subscription API
* report-analysis service

No such service is required for v0.1 core functionality.

## Network destination classes

Every network-capable capability and probe will classify its intended destination.

Initial destination classes are:

```text
loopback
unix_socket
container_local
host_local
lan
configured_remote
tor_configured
redline_service
third_party_public
```

### Loopback

Examples:

```text
127.0.0.1
::1
```

Loopback traffic remains on the local host under ordinary network configuration.

### Unix socket

Examples:

```text
Bitcoin RPC Unix socket, if supported
Docker socket through an approved provider
redline-privd socket
local service socket
```

Unix-socket access is local but may still be privileged or sensitive.

### Container-local

Traffic within a container network or application namespace.

Examples:

* Redline app to an Umbrel Bitcoin service
* Redline service to a StartOS dependency interface
* Redline container to a colocated Electrum backend

Container-local does not imply that the data is non-sensitive.

### Host-local

Traffic to a host address or bridge interface not necessarily limited to loopback.

### LAN

Traffic to a private local network target.

Examples:

* a miner
* another node
* a wallet backend
* a home server

### Configured remote

Traffic to a public or remote endpoint explicitly configured as part of the user’s stack.

This may include:

* a remote Electrum backend
* a remote Stratum endpoint
* a remote node under the user’s control

Configured-remote traffic must be visible in configuration and scan planning.

### Tor-configured

Traffic intentionally routed through a configured Tor proxy to a configured target.

Redline will not treat Tor as implicit permission to contact arbitrary services.

### Redline service

Traffic to SATOSHI//REDLINE-operated infrastructure.

This class is disabled in the v0.1 core unless triggered by a separate explicit user action such as a manual update check.

### Third-party public

Traffic to a public service not operated by Redline and not configured as part of the diagnosed stack.

Examples include:

* public IP-discovery services
* public DNS-over-HTTPS services
* generic uptime endpoints
* certificate-checking services
* analytics services
* CDNs
* public block explorers
* public Bitcoin-height APIs
* NTP-over-HTTP services

This destination class is prohibited by default.

A diagnostic check requiring it must be separately designed, explicitly enabled, and justified.

## Core outbound network policy

The unprivileged daemon will implement an application-level default-deny policy for public outbound communication.

The policy does not attempt to replace an operating-system firewall.

It governs which Redline components may request network access.

### Allowed by default

The following may be allowed when required by configured diagnostics:

```text
loopback
unix_socket
container_local
host_local
lan
configured_remote
tor_configured
```

The exact allowance depends on:

* the scan profile
* the probe’s declared side effects
* the target binding
* user configuration
* platform policy

### Denied by default

The following are denied unless a separately authorized feature enables them:

```text
redline_service
third_party_public
```

A compiled probe does not receive permission to contact a public service merely because its source code contains a URL.

### Destination binding

Network capabilities will be bound to approved endpoint references.

A probe should receive:

```text
TCP connection capability for electrum.primary
```

rather than:

```text
generic Internet dialer
```

A Bitcoin RPC probe should not be able to repurpose its capability to contact a Redline server.

The capability provider will enforce:

* allowed host or socket
* allowed port
* transport
* proxy behavior
* TLS policy
* destination class
* address-family constraints where appropriate

### No arbitrary URL capabilities

The core engine will not expose a general capability such as:

```go
FetchURL(ctx, url string)
```

to probes.

Protocol-specific clients may use HTTP internally, but the destination remains pre-bound.

This prevents configuration, log content, or protocol responses from redirecting a probe to arbitrary destinations.

## Diagnostic traffic is not telemetry

A diagnostic request may still reveal information to the target being tested.

For example:

* a TCP connection reveals the source address to the destination
* an RPC request reveals that a client is querying the service
* an Electrum handshake may expose a Redline client identifier
* a Stratum subscription may appear in server logs
* a Tor egress test may contact a public destination

Redline must not describe these operations as network-invisible.

Instead, each probe descriptor will declare:

* destination class
* connection purpose
* expected protocol interaction
* whether authentication is used
* whether the target may record the request
* whether the operation leaves the local environment
* whether the check is enabled by default

### Protocol client identification

Redline should minimize unnecessary identifying information.

Where a protocol requires a client name or version:

* use a stable generic product identifier where operationally useful
* avoid including installation IDs
* avoid including platform details
* avoid including hostnames
* avoid including user labels
* avoid including exact build metadata unless required for compatibility

Example:

```text
SatoshiRedline/0.1
```

may be acceptable.

Example:

```text
SatoshiRedline/0.1 Umbrel ARM64 node-7f3a9c
```

is not.

Where a client identifier is optional, Redline should omit it unless it has clear diagnostic value.

## Local API exposure

The Redline API and web UI will bind to loopback by default.

Preferred default listeners:

```text
127.0.0.1
::1
```

or a Unix-domain socket where packaging supports it.

The default installation will not expose the Redline API to:

* the LAN
* container-external interfaces
* Tor
* the public internet

Platform packaging may expose the UI through a platform-managed local interface, but that exposure must remain explicit and constrained by the platform.

Binding the API to a non-loopback interface is a separate administrative decision.

The daemon must not silently broaden its listener based on network discovery.

### Browser assets

The embedded web UI will be fully self-contained.

It will not load:

* JavaScript from a CDN
* fonts from a remote provider
* externally hosted icons
* analytics scripts
* remote stylesheets
* third-party graph libraries at runtime
* remote error-reporting SDKs
* remote feature flags

All production assets will be compiled and served locally.

The dashboard must remain usable when the host has no internet access.

### Browser security

The UI should use a restrictive Content Security Policy.

A suitable baseline should prohibit external resource origins.

Conceptually:

```text
default-src 'self';
connect-src 'self';
img-src 'self' data:;
style-src 'self';
script-src 'self';
font-src 'self';
object-src 'none';
base-uri 'none';
frame-ancestors 'none';
```

Exact directives may change according to implementation needs.

The policy must not add broad public origins merely for development convenience.

If the browser UI later supports opening external documentation, those links should be normal user-initiated navigation, not background requests.

## Telemetry and analytics

### Product analytics

Redline v0.1 will include no product analytics SDK and no custom usage-event pipeline.

The project will not automatically collect:

* daily active installations
* feature usage
* scan counts
* probe success rates
* platform distribution
* installation retention
* component versions
* error frequency
* performance metrics
* conversion behavior

This remains true even if the data is described as anonymous or aggregated.

### Local operational metrics

Redline may collect local metrics about itself for:

* scheduler behavior
* scan duration
* local resource use
* database size
* probe execution counts
* local incident history

Such metrics remain local.

They may be exposed through:

* the local API
* local diagnostic views
* local logs
* an optional local Prometheus endpoint

A local metrics endpoint must bind to loopback by default and must not include forbidden data.

Local metrics are not telemetry unless transmitted externally.

### Installation identifiers

The core product will not create a stable installation identifier for vendor analytics.

Identifiers required for local database relationships or report object identity must not be reused as remote tracking identifiers.

A report ID is not permission to correlate the installation across services.

### Anonymous telemetry

The project will not rely on the claim that telemetry is anonymous.

Public IP addresses, rare platform combinations, timestamps, and software versions can make supposedly anonymous events identifying.

The default decision is therefore no outbound telemetry, not anonymized outbound telemetry.

## Crash handling

Redline will not automatically upload crash reports.

Crash handling may produce a local structured crash record containing approved safe fields such as:

```text
product version
build ID
process name
panic category
safe stack function names
probe ID
probe version
scan stage
timestamp
```

It must not contain:

* raw protocol responses
* raw logs
* credentials
* external addresses
* onion addresses
* payout addresses
* arbitrary request context
* process environment
* local configuration contents
* provider response objects

A future “Send crash report” action may be considered, but it must:

1. Be explicitly initiated.
2. Show the categories being sent.
3. Generate a reviewed export projection.
4. Allow inspection before transmission.
5. Exclude forbidden data.
6. Fail closed on validation errors.
7. Be governed by a separate support-communication design.

Third-party crash-reporting SDKs will not be embedded in the core daemon or frontend.

## Software updates

### No silent update checks

The core v0.1 daemon will not periodically contact a Redline update service.

It will not perform an automatic startup update check.

The local dashboard will not silently fetch release metadata.

### Manual update check

A future or v0.1 manual “Check for updates” action may contact a Redline-operated update endpoint.

Such an action must be:

* initiated by the user
* clearly labeled
* isolated from diagnostic reports
* limited to the minimum request data
* independent of the core scan engine
* non-essential to core operation

The request should minimize identifying fields.

A minimal request may need no query parameters beyond those inherent in the network connection.

The server can return current release metadata, after which the client compares versions locally.

Avoid sending:

```text
platform
architecture
installed components
scan history
installation ID
node version
mining configuration
```

unless a later design demonstrates a specific need and receives privacy review.

### Package-manager behavior

System packages, Umbrel, StartOS, Docker registries, or operating-system tools may perform their own update checks.

Those behaviors are outside the core daemon’s network activity.

Redline documentation must distinguish:

* Redline’s own network behavior
* platform update behavior
* package-manager behavior
* container-registry access during installation or upgrade

The fact that installation requires downloading a package does not authorize the running daemon to communicate later.

### Security advisories

The absence of automatic update checks creates a risk that users miss security releases.

Initial mitigation will use:

* release notes
* repository announcements
* package-platform update mechanisms
* optional manual update checks
* documentation showing the installed version

An opt-in background security-advisory check may be considered later, but it remains outbound communication and requires explicit design.

## DNS behavior

DNS queries may disclose target hostnames and product activity.

Redline will not use a Redline-operated DNS resolver.

It will use the configured operating-system resolver for endpoints that require hostname resolution, unless a platform-provided resolver or Tor resolution mode is explicitly configured.

### Local targets

Where platform service bindings provide resolved addresses or Unix sockets, Redline should avoid unnecessary DNS lookups.

### Tor targets

Onion names must be resolved through the configured Tor mechanism and must not leak to the system DNS resolver.

A Tor-capable endpoint binding must carry resolution policy explicitly.

### Public third-party DNS

Redline will not silently send queries to public DNS-over-HTTPS services.

### DNS diagnostics

A DNS diagnostic may query:

* a configured component hostname
* the host’s configured resolver
* a user-selected diagnostic target

It will not query arbitrary vendor domains solely to determine whether “the internet works.”

## External connectivity tests

A generic internet-reachability check is deceptively invasive.

Common implementations contact:

* a public website
* a captive-portal endpoint
* a cloud provider
* a DNS service
* an IP-reflection service

These reveal user activity to third parties.

Redline v0.1 will not run a generic public-internet connectivity test by default.

Instead, connectivity should be tested against actual declared dependencies.

Examples:

```text
Can DATUM reach its configured pool?
Can Tor reach the configured onion service?
Can the node reach its configured proxy?
Can the wallet backend reach the configured Bitcoin node?
```

If an external neutral test target is eventually provided, it must be:

* separately enabled
* named in the scan plan
* classified as third-party or Redline-operated
* excluded from default Safe Scan
* documented as externally visible traffic

Redline will not use a public IP-discovery service.

## Time checks

Clock drift is part of the diagnostic scope.

Redline will prefer local evidence such as:

* operating-system clock state
* configured time-synchronization service state
* kernel synchronization indicators
* comparison between locally observed protocol timestamps and the local clock

Redline will not contact a Redline-operated time service.

It will not introduce an independent public NTP or HTTP time request by default.

If a future explicit external time comparison is added, its destination and network implications must be declared.

## Certificate validation and revocation

Standard TLS validation may involve operating-system trust stores.

Redline itself will not add hidden external revocation or certificate-transparency queries.

Where the Go TLS stack or operating system performs no external revocation lookup, Redline will not add one automatically.

If stronger certificate validation later requires public network access, that access must be declared as part of the probe.

Redline should not weaken normal TLS validation merely to avoid all external behavior.

The correct approach is explicit documentation and endpoint-bound behavior.

## Report export and sharing

Report generation remains entirely local.

Creating a report will not:

* upload it
* register it
* notify Redline
* create a public URL
* contact a support service
* fetch rendering assets

A report becomes external only through an explicit user action such as:

* saving it to a chosen path
* copying it
* attaching it to an email
* selecting a future “Send to support” function

### Shareable report

The default shareable report remains governed by ADR-005 and ADR-006.

It must pass:

* schema validation
* privacy allowlisting
* forbidden-data detection
* evidence-reference validation

before it may be saved or transmitted.

### Future support upload

A built-in support upload would be a separate network feature.

It must not reuse ordinary telemetry infrastructure.

It would require a new ADR defining:

* endpoint ownership
* authentication
* report scope
* retention
* deletion
* access controls
* encryption
* support personnel access
* user consent
* retry behavior
* failure behavior
* abuse prevention

## Notifications

The roadmap includes:

* iOS push notifications
* Android push notifications
* monitoring subscriptions

Mobile push ordinarily requires communication with:

* a Redline-operated relay
* Apple Push Notification service
* Firebase Cloud Messaging or another platform service

This is incompatible with a purely local no-outbound model unless the user explicitly enables a notification service.

Therefore, push notifications will be implemented as an optional layer rather than as hidden core behavior.

A future notification architecture must preserve:

* local diagnosis
* minimal event projection
* no raw evidence upload
* explicit enrollment
* revocable device registration
* independent disablement
* clear destination disclosure
* operation without push when disabled

A notification payload should contain the minimum needed to notify the user.

It should not automatically contain:

* full reports
* logs
* RPC data
* addresses
* component secrets
* detailed dependency graphs

The local UI and CLI must remain usable without notification enrollment.

## Hosted monitoring and subscriptions

A future paid monitoring subscription may require external communication.

That service must remain architecturally separate from the core engine.

Possible models include:

1. Redline sends minimal incident events to a relay.
2. A user-operated gateway receives local Redline events.
3. A mobile client connects through the user’s own VPN or Tor service.
4. A separately installed agent exports a constrained monitoring projection.

This ADR does not choose a hosted-monitoring design.

It establishes requirements any future design must meet:

* disabled by default
* explicit enrollment
* clear data contract
* no forbidden data
* no raw logs or protocol responses
* independent authentication
* independent retention policy
* local diagnostic operation when disconnected
* no remote-control authority
* no automatic expansion from notification to telemetry
* separate ADR and threat model

The monetization layer must not be embedded in probe execution.

A paid subscription must not change whether local checks pass or fail.

## Licensing and entitlement

The core local scanner will not require an online licensing or entitlement check.

Free local diagnostic functionality must not stop working because:

* Redline servers are unavailable
* the host is offline
* an account expires
* a subscription cannot be verified
* a licensing endpoint is blocked

Future paid hosted services may require account authentication.

Paid local-only features, if introduced, require a separate licensing decision.

The core architecture must not include a dormant telemetry or licensing client merely in anticipation of monetization.

## Remote configuration and feature flags

Redline v0.1 will not retrieve remote feature flags or remote configuration.

The active behavior will be determined by:

* installed binary
* local configuration
* platform-provided bindings
* scan profile
* root-owned privileged-helper policy
* explicit user actions

Remote configuration creates risks including:

* behavior changes without a local software update
* covert telemetry
* emergency-control abuse
* inconsistent reproducibility
* inability to interpret historical reports
* server dependency

Urgent probe deactivation will occur through a software update or explicit local configuration, as established in ADR-007.

## External documentation links

The local UI may display links to:

* Redline documentation
* Bitcoin component documentation
* platform documentation
* support resources

Links must not be fetched automatically.

Opening a link is an explicit browser navigation outside the local application.

The UI should indicate when a link leaves the local Redline interface.

Documentation required to understand core findings should be bundled locally where practical.

A user must not need internet access to view the basic explanation of:

* a finding
* an unknown reason
* a recommendation
* a scan limitation

## Dependency and build considerations

### Go dependencies

Runtime libraries must not perform unexpected network activity.

Dependencies will be reviewed for:

* telemetry
* update checks
* certificate lookups
* remote configuration
* crash reporting
* dynamic module retrieval
* external asset loading

Go modules are downloaded during development or build time, not by the running production daemon.

### Frontend dependencies

Frontend libraries will be bundled at build time.

Production code must not rely on package-manager CDNs or runtime module loading.

### Database and migration tools

Database libraries must not phone home.

### Error-reporting libraries

Third-party error-reporting clients are prohibited in the core product.

### AI or language-model services

Core diagnosis, explanation, and report generation will not depend on a cloud AI service.

If optional AI-assisted support is introduced later, it must:

* be explicitly invoked
* use a sanitized report projection
* disclose the service receiving the data
* remain unnecessary for core diagnosis
* be governed by a separate ADR

## Enforcement architecture

### Network broker

Probes will not receive an unrestricted global network client.

Network operations will flow through capability providers or destination-bound protocol clients.

Conceptually:

```go
type NetworkTarget struct {
    ComponentID      ComponentID
    EndpointRef      EndpointRef
    DestinationClass DestinationClass
    Transport        Transport
    ProxyPolicy      ProxyPolicy
}
```

A resolved network capability will permit operations only against that target.

### Probe descriptors

Under ADR-007, every probe declares side effects.

Network-capable probes must declare:

```text
destination class
protocol
whether authentication is used
whether external traffic is possible
whether the operation is default-enabled
```

A descriptor mismatch is a defect.

### Scan plan

Before execution, the scan plan can summarize network operations:

```text
This scan may connect to:

- Bitcoin RPC on the local host
- Fulcrum on the Docker application network
- DATUM on the local host
- Miner A on the private LAN

No public or Redline-operated services will be contacted.
```

If an explicitly enabled external check exists:

```text
This scan will also connect through Tor to the configured pool endpoint.
```

The plan need not prompt for every ordinary local connection, but the information must be inspectable.

### Redline-service client separation

Any future Redline-service client will live in a separate package and capability boundary.

Core probe packages will not import it.

The network broker will not treat a Redline-operated domain as an ordinary diagnostic target.

### Build-time tests

Official builds will be scanned for:

* analytics SDKs
* crash-reporting SDKs
* known telemetry hosts
* remote font URLs
* CDN references
* embedded vendor endpoints
* automatic updater code
* remote feature-flag clients

This is defense in depth and does not replace code review.

## Failure behavior

The core application must remain usable when:

* the public internet is unavailable
* DNS is unavailable
* Redline-operated infrastructure is unavailable
* outbound traffic is blocked
* update services are unreachable
* notification services are disabled
* support services are unavailable

Diagnostic checks against unavailable configured remote targets may fail or become unknown according to their evidence.

The application itself must not fail merely because it cannot contact Redline.

Examples:

```text
Redline update service unreachable
```

must not affect:

```text
Bitcoin synchronization finding
```

A disabled hosted notification feature must not affect local incident creation.

A blocked analytics endpoint cannot affect anything because no analytics endpoint exists in the core product.

## Security considerations

### Server-side request forgery

A compromised or misconfigured local API must not turn Redline into an arbitrary network scanner or request proxy.

Mitigations include:

* destination-bound endpoint references
* typed component configuration
* restricted supported protocols
* no generic URL-fetch endpoint
* no redirect following across destination classes
* address revalidation after DNS resolution
* private/public destination classification
* request-size and response-size limits
* no browser-supplied arbitrary probe destination in ordinary scans

### DNS rebinding

Where the local web UI permits configuring hostnames, the backend must not assume that a hostname always resolves to the same trust zone.

Endpoint resolution should:

* classify resolved addresses
* enforce destination policy at connection time
* handle multiple address records
* avoid trusting browser-originated DNS results
* prevent a configured public hostname from silently rebinding to a privileged local service where relevant

The exact endpoint-security design may require a separate implementation note.

### Redirects

HTTP-based diagnostic clients will not follow redirects automatically unless the protocol integration explicitly permits them.

A redirect must not cross destination classes without explicit authorization.

A configured local endpoint redirecting to a public analytics domain must not be followed.

### Proxy inheritance

Redline will not blindly inherit generic `HTTP_PROXY`, `HTTPS_PROXY`, or `ALL_PROXY` environment variables for all traffic.

Proxy behavior must be explicit per endpoint binding.

Blind inheritance could:

* send local RPC credentials through a proxy
* leak local service names
* alter destination classification
* route diagnostic traffic externally

Platform packaging may intentionally inject a proxy policy, but the provider must preserve it as explicit provenance.

### TLS

Remote diagnostic traffic should use TLS where supported and appropriate.

Privacy does not justify disabling certificate validation.

Tor onion services and local self-signed endpoints may need distinct trust policies, but those policies must be explicit.

## Operating-system behavior outside Redline

Redline cannot guarantee that no packet leaves the host under all circumstances.

The operating system or platform may independently perform:

* DNS queries
* time synchronization
* package updates
* container-registry access
* certificate handling
* captive-portal checks
* platform telemetry
* push notifications
* Tor bootstrap
* network-manager probes

This ADR governs Redline’s own processes and bundled frontend.

Documentation must not falsely claim:

```text
Installing Redline guarantees the host makes no external connections.
```

The accurate claim is:

```text
Redline’s core daemon and UI do not send telemetry or contact Redline
services by default. Diagnostic traffic is limited to declared targets and
explicitly enabled checks.
```

## Auditability

Redline should provide a local network-policy view showing:

* configured diagnostic targets
* destination classes
* enabled externally visible checks
* Redline-operated features enabled
* last manual update check
* notification enrollment state
* active listener bindings
* proxy policies
* Tor routing policies

This view must not expose forbidden endpoint details in shareable reports.

### Local connection audit

Redline may maintain a local structured record of its own network operations.

Permitted fields include:

```text
probe ID
component alias
destination class
protocol
outcome category
started time
finished time
bytes sent category
bytes received category
```

It must not retain:

* forbidden addresses
* credentials
* raw requests
* raw responses
* onion addresses
* payout addresses

This record is intended to verify policy behavior locally, not create telemetry.

## Alternatives considered

### Alternative A: Anonymous telemetry enabled by default

This is rejected.

Anonymity cannot be guaranteed from public IP, timing, versions, and rare platform combinations.

The benefit to product development does not outweigh the trust cost.

### Alternative B: Telemetry enabled with an installation notice

This is rejected.

Disclosure is not equivalent to meaningful opt-in, particularly for infrastructure software.

### Alternative C: Silent update checks with no other telemetry

This is rejected for the default configuration.

An update request still reveals installation activity and version information.

A manual check provides sufficient initial functionality.

### Alternative D: Use a third-party analytics platform only in the web UI

This is rejected.

Opening a local dashboard must not contact an analytics provider.

### Alternative E: Host frontend assets on a CDN

This is rejected.

The local UI must work offline and must not reveal dashboard activity to a CDN.

### Alternative F: Use a public block explorer to verify Bitcoin height

This is rejected by default.

Redline should compare local stack layers and direct protocol evidence rather than disclose node activity to a public explorer.

An explicit external comparison would require separate authorization.

### Alternative G: Use a public IP-discovery service

This is rejected.

External IP addresses are specifically outside Redline’s intended data collection, and the request itself creates disclosure.

### Alternative H: Require a Redline account

This is rejected for the local scanner.

Accounts may be appropriate for optional hosted services, not core diagnosis.

### Alternative I: Upload sanitized reports automatically after failures

This is rejected.

Sanitization does not create consent, and automatic upload would violate the local-first model.

### Alternative J: Route all outbound traffic through Tor

This is rejected as a substitute for no telemetry.

Tor may reduce destination visibility into the user’s public IP, but it does not justify unnecessary communication.

Tor also introduces availability, fingerprinting, and endpoint-trust considerations.

### Alternative K: Block all network traffic, including diagnostic targets

This is rejected.

Redline’s purpose requires protocol and connectivity checks.

The correct boundary is declared target access, not absolute network isolation.

### Alternative L: Allow arbitrary HTTP checks configured by users

This is rejected for v0.1.

A generic HTTP checker would create an arbitrary request engine, complicate SSRF protections, and weaken destination governance.

Supported protocol integrations should remain typed and component-bound.

## Consequences

### Positive consequences

* Core diagnostics work without a cloud service.
* Users do not need an account.
* Redline does not disclose node or mining activity through telemetry.
* Opening the local dashboard creates no third-party requests.
* Reports remain local until explicitly shared.
* Product behavior is more predictable in disconnected environments.
* Public network traffic can be tied to a configured target or explicit feature.
* Future monetization remains separate from diagnostic correctness.
* Redline avoids dependency on vendor availability.
* UI assets cannot become tracking channels.
* Crash handling cannot silently upload sensitive context.
* The privacy promise becomes testable at the network boundary.
* Local monitoring remains useful when external services are blocked.
* The architecture remains compatible with highly privacy-conscious Bitcoin users.

### Negative consequences

* The project receives no automatic usage or reliability statistics.
* Maintainers will have less visibility into deployment failures.
* Users may remain on outdated versions longer.
* Product decisions must rely on voluntary feedback and explicit support reports.
* Manual update checks are less convenient.
* Future notification and monitoring services require additional architecture.
* Destination-bound network clients require more implementation effort than generic HTTP access.
* Offline-bundled frontend assets increase release artifact size.
* Debugging rare production failures may require user participation.
* Optional cloud features cannot be added casually.

### Neutral consequences

* Diagnostic traffic to configured components still occurs.
* Installation and package updates still require network access through external tooling.
* Tor may itself make external connections.
* Local operational metrics remain possible.
* Future hosted services remain possible with explicit opt-in.
* The project may publish release metadata without the daemon fetching it automatically.
* Users may expose the local API manually under a later security design.

## Risks and mitigations

### Risk: Users miss critical security updates

**Mitigations:**

* Display the installed version prominently.
* Provide a manual update-check action.
* Use package-platform update channels.
* Publish clear security advisories.
* Consider a separately opt-in security-only update check later.
* Keep update-check requests minimal.

### Risk: A dependency adds telemetry

**Mitigations:**

* Review dependencies before adoption.
* Prohibit analytics and crash SDKs.
* Scan built assets for remote origins.
* Test runtime network behavior.
* Pin dependencies.
* Include network-policy checks in release validation.

### Risk: A probe contacts an undeclared destination

**Mitigations:**

* Use destination-bound capabilities.
* Do not give probes a generic dialer.
* Declare side effects in probe descriptors.
* Record safe connection provenance.
* Test with an egress-deny harness.
* Treat undeclared network traffic as a security defect.

### Risk: Frontend code contacts the internet

**Mitigations:**

* Bundle all assets.
* Enforce restrictive Content Security Policy.
* Test the dashboard with no internet route.
* Scan compiled assets for remote URLs.
* Prohibit runtime package loading.
* Avoid third-party telemetry libraries.

### Risk: Manually configured targets create SSRF behavior

**Mitigations:**

* Use typed component endpoints.
* Restrict protocols.
* Validate destination classes.
* Revalidate DNS results.
* Limit redirects.
* Do not expose arbitrary fetch APIs.
* Require explicit configuration for remote targets.

### Risk: Proxy environment variables leak local traffic

**Mitigations:**

* Ignore ambient proxies by default.
* Use explicit per-target proxy policy.
* Distinguish Tor routing from generic proxy routing.
* Test that local RPC connections remain direct unless configured otherwise.

### Risk: Update checks become a covert telemetry channel

**Mitigations:**

* Keep them manual.
* Send no installation identifier.
* Minimize request metadata.
* Do version comparison locally.
* Do not combine update requests with component or usage data.
* Keep update clients outside probe packages.

### Risk: Future push notifications quietly expand data collection

**Mitigations:**

* Require a separate ADR.
* Send minimal event projections.
* Make enrollment explicit and reversible.
* Keep local incidents canonical.
* Do not attach reports automatically.
* Separate notification infrastructure from analytics.

### Risk: “No telemetry” claims become broader than implementation

**Mitigations:**

* State claims precisely.
* Distinguish Redline behavior from platform and OS behavior.
* Publish the network destination policy.
* Provide local auditability.
* Test runtime connections.
* Avoid absolute claims about the entire host.

### Risk: Lack of telemetry slows product improvement

**Mitigations:**

* Use voluntary issue reports.
* Provide explicit sanitized support-export tooling.
* Maintain public compatibility matrices.
* Build strong synthetic test labs.
* Invite opt-in user research outside the core product.
* Prefer trust over convenience in the core architecture.

### Risk: External checks are necessary for some diagnoses

**Mitigations:**

* Tie them to real configured dependencies.
* Classify their destination.
* Make public third-party checks explicit.
* Explain the network effect before enabling.
* Keep independent local checks available.

## Testing strategy

### Egress tests

Integration tests will run Redline in an environment where outbound traffic is intercepted.

Tests must verify that an idle daemon and ordinary local Safe Scan make no connections to:

* Redline-operated domains
* analytics services
* crash-reporting services
* CDNs
* public block explorers
* public IP services
* remote feature-flag services
* package registries
* update services

### Destination-policy tests

Tests must verify:

* a Bitcoin RPC capability can reach only its bound endpoint
* a probe cannot substitute another hostname
* redirects across destination classes are rejected
* public destinations are denied by default
* Tor-bound targets do not use system DNS
* ambient proxy variables do not reroute local RPC traffic
* a LAN target remains classified as LAN after resolution
* DNS rebinding is handled according to connection-time policy

### Frontend tests

The production web UI must be tested to ensure:

* no external resource requests occur
* all scripts and styles load locally
* fonts are bundled or use system fonts
* the Content Security Policy blocks public connections
* the application remains usable offline
* opening findings or graphs causes no remote fetch
* documentation content required for core use is local

### Update tests

Tests must verify:

* no automatic update request occurs at startup
* no periodic update request occurs
* the manual action is required
* manual requests contain no installation ID
* update failure does not affect scans
* update-service unavailability is handled locally

### Crash tests

Tests must verify:

* crashes create no outbound request
* no third-party crash client is initialized
* local crash records contain only approved fields
* raw protocol inputs do not enter crash logs
* restarting the daemon does not retry an upload

### Report tests

Tests must verify:

* generating a report makes no network request
* viewing an HTML report makes no external request
* reports contain no remote asset references
* support sharing cannot occur without a user action
* failed validation prevents transmission

### Dependency tests

CI should scan:

* Go dependency graph
* frontend dependency graph
* compiled JavaScript
* embedded HTML
* binary strings
* service configuration

for known or undeclared remote-service references.

A remote URL may be present in documentation, but executable runtime use must be reviewed.

### Network-manifest tests

The build should generate an expected network-behavior manifest containing:

```text
listeners
destination classes
Redline-operated endpoint clients
third-party endpoint clients
externally visible probe types
```

For the v0.1 core, the Redline-operated and third-party runtime endpoint lists should be empty except for an explicitly implemented manual update client.

### Platform tests

Umbrel, StartOS, Docker, and generic Linux packaging must be tested separately because platform proxies, service discovery, and UI wrappers may alter network behavior.

Platform packaging must not inject analytics into the Redline interface.

## Architecture enforcement

Automated checks should enforce that:

1. Probe packages cannot import Redline-service clients.
2. Probes do not receive a generic Internet dialer.
3. Every network capability is destination-bound.
4. Every network-capable probe declares destination and side effects.
5. The frontend build contains no unapproved external origins.
6. The core daemon contains no telemetry or analytics SDK.
7. The crash path contains no uploader.
8. Report generation imports no network client.
9. The privileged helper has no external network capability.
10. Update logic remains outside the diagnostic engine.
11. Redline-service communication is impossible without a separately enabled feature.
12. Local API listeners default to loopback or Unix sockets.
13. Remote listener configuration cannot be enabled silently.
14. External-connect probes are excluded from default Safe Scan unless explicitly approved.
15. Runtime remote configuration and feature-flag clients are absent.
16. Configuration cannot define arbitrary URLs or HTTP requests for probes.

2. Mobile push notifications are implemented.

4. A security-only automatic update channel is proposed.
5. A Redline account becomes necessary for an optional service.
6. Third-party cloud analysis becomes a proposed feature.
7. Remote agents or fleet management are introduced.
8. Public reference services become necessary for a diagnostic check.
9. A licensing or entitlement system is proposed.
10. The local API must bind beyond loopback by default.
11. A browser-based remote-access architecture is introduced.
12. A package platform requires Redline-controlled callbacks.
13. A signed remote rule or compatibility-data channel is proposed.
14. Users request opt-in product telemetry.
15. A future AI support feature sends report data to an external model.
16. Certificate-validation requirements introduce new external lookups.

18. External security review identifies a privacy issue in the destination-class model.

* purpose
* destination ownership
* exact data contract
* identifiers
* authentication

* retention
* deletion

* offline behavior

## Final decision statement

SATOSHI//REDLINE’s core diagnostic engine, persistence, correlation, reporting, CLI, and local web interface will operate without a cloud dependency and without outbound telemetry.

Redline will connect to explicitly configured or platform-declared components when those connections are necessary to diagnose the user’s stack. Those connections will be destination-bound, classified, and attributable to declared probe behavior.

Redline will not silently contact vendor infrastructure, analytics providers, crash-reporting services, CDNs, public block explorers, public IP-discovery services, remote feature-flag systems, or update services.

Reports remain local until the user explicitly shares them.

The web UI remains fully self-contained and usable offline.

Future update, notification, support, monitoring, account, or commercial services must remain optional layers with explicit enrollment, minimal data contracts, and separate architectural review.

The central rule established by this ADR is:

> Redline may observe the stack the user entrusted it to diagnose. It may not make that observation visible to anyone else without the user deliberately choosing to do so.
