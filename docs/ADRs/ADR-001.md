# ADR-001: Use a Go Modular Monolith for the Diagnostic Backend

* **Date:** 2026-07-30
* **Decision owners:** SATOSHI//REDLINE maintainers
* **Scope:** Diagnostic engine, platform adapters, local daemon, CLI, privileged helper, reporting, and persistence
* **Excluded from scope:** Browser UI implementation language, mobile clients, hosted commercial services

## Context

SATOSHI//REDLINE is a local-first diagnostic system for Bitcoin nodes and home-mining infrastructure. It must inspect and correlate behavior across multiple layers:

* Bitcoin Core and Bitcoin Knots
* Electrs and Fulcrum
* DATUM and Stratum services
* Wallet-to-backend connectivity
* Tor and local networking
* Linux processes, systemd, Docker, filesystems, storage, and system resources
* UmbrelOS and StartOS service environments

The product must run on AMD64 and ARM64 systems ranging from relatively powerful servers to Raspberry Pi-class hardware. Installation must remain practical for non-expert node runners.

The backend will need to:

1. Communicate with several network protocols.
2. Perform many concurrent, timeout-bound diagnostic checks.
3. Normalize results from different platforms.
4. Correlate failures across a dependency graph.
5. Operate without a cloud service.
6. Avoid retaining secrets or sensitive raw data.
7. Support both low-privilege and optional deep-scan modes.
8. Produce CLI, web, and machine-readable output from the same engine.
9. Remain maintainable by a small team, initially likely one primary developer.
10. Allow future extension without committing the project to a distributed architecture prematurely.

The architecture therefore needs to optimize for deployment simplicity, safety, development velocity, protocol support, testability, and long-term modularity.

## Decision

The SATOSHI//REDLINE diagnostic backend will be implemented as a **modular monolith written in Go**.

The project will use one repository and, initially, one Go module. It may produce multiple binaries from the same internal application code:

* `redlined` — unprivileged local daemon and API server
* `redline` — command-line client and optional one-shot scanner
* `redline-privd` — optional narrowly scoped privileged helper

These binaries are separate operating-system processes where security requires a process boundary, but they remain parts of one coherent backend rather than independently deployed services.

The browser interface will be implemented separately in TypeScript and compiled into static assets that can be embedded in `redlined`. The browser UI is not part of the Go-language decision.

The internal backend will be divided into modules with explicit responsibilities:

```text
domain
    Core data types and invariants

engine
    Scan planning, scheduling, cancellation, and orchestration

inventory
    Component discovery and dependency graph construction

capabilities
    Interfaces through which probes access platform functions

probes
    Protocol-specific collection of normalized observations

correlation
    Interpretation of findings across dependency boundaries

incidents
    Failure persistence, debounce, recovery, and resolution state

platform
    Linux, Docker, Umbrel, and StartOS capability providers

redaction
    Sensitive-data filtering and export validation

reports
    Human-readable and machine-readable report generation

storage
    Persistence of approved normalized data

api
    Local HTTP API, scan control, and event streaming

privileged
    Client and server definitions for the optional privileged helper
```

A modular monolith in this ADR means:

* Modules communicate through in-process Go APIs unless a security boundary requires another process.
* Modules do not communicate through internal HTTP services, message queues, or service discovery.
* Platform-specific access is isolated behind capabilities.
* Diagnostic rules remain independent of platform adapters.
* Public data contracts are versioned even when their current consumers run in the same process.
* Components may be separated into services later, but are not designed as services before there is an operational reason to do so.

## Decision drivers

The decision drivers, in priority order, are:

1. **Safe handling of privileged and sensitive operations**
2. **Simple installation on AMD64 and ARM64 Linux**
3. **Fast implementation by a small team**
4. **Reliable concurrent network and system diagnostics**
5. **Low resource overhead**
6. **Strong static typing and explicit error handling**
7. **Straightforward testing with simulated protocols and platforms**
8. **Clear module boundaries without distributed-system overhead**
9. **Practical packaging for Linux, Docker, Umbrel, and StartOS**
10. **A credible path to future extensibility**

## Options considered

### Option A: Go modular monolith

Build the backend in Go with internal modules and a small number of binaries sharing the same domain and engine packages.

### Option B: Rust modular monolith

Build the same architecture in Rust, using traits and crates to enforce internal boundaries.

### Option C: TypeScript and Node.js modular monolith

Implement the backend and web interface in a mostly unified TypeScript codebase.

### Option D: Polyglot microservices

Create separate services for protocols, platform collection, correlation, reporting, and the user interface.

## Rationale

### Go provides the best overall delivery tradeoff

Rust offers stronger compile-time guarantees and more precise control over memory and system behavior. Those benefits are real, particularly for low-level agents and privileged software.

However, SATOSHI//REDLINE is primarily an orchestration and protocol-diagnostics system rather than a high-performance parser, kernel component, cryptographic library, or memory-constrained embedded application.

Most backend work will consist of:

* Calling local HTTP and JSON-RPC interfaces
* Opening TCP, TLS, SOCKS, Electrum, and Stratum connections
* Applying timeouts and cancellation
* Reading normalized operating-system state
* Comparing observations
* Constructing dependency graphs
* Generating reports
* Maintaining a small local history

Go is particularly well suited to this category of software. It provides static typing, memory safety, inexpensive concurrency, mature network primitives, and direct Linux integration without imposing Rust’s additional implementation and review cost on every part of the system.

The product’s principal early risk is not insufficient runtime performance. It is failing to ship enough reliable diagnostic coverage quickly enough. Go reduces that risk while retaining substantially more deployment and type safety than a Node.js backend.

### Deployment simplicity is a product feature

The generic Linux release should be installable as a small set of native binaries without requiring users to install:

* A language runtime
* A package manager
* A JavaScript dependency tree
* A database server
* An internal message broker
* Multiple independently versioned services

Go makes it practical to distribute builds for AMD64 and ARM64, run the same engine in containers or directly on Linux, and embed the compiled web interface into the daemon.

The intended deployment unit becomes:

```text
redlined
redline
redline-privd        optional
redline.service
redline-privd.service
```

Umbrel and StartOS packages can wrap these same artifacts rather than hosting separate implementations.

### Go’s concurrency model fits diagnostic scans

A scan consists of many operations that should execute concurrently but remain bounded by:

* Per-probe timeouts
* Global scan deadlines
* Connection limits
* Platform resource limits
* Cancellation when the user stops a scan
* Dependency ordering where one observation is required before another check

Go’s contexts, goroutines, channels, and standard networking facilities provide a direct model for this behavior.

The scheduler can run independent probes concurrently while preserving deterministic aggregation and reporting.

### A modular monolith avoids premature distributed systems

SATOSHI//REDLINE does not initially need independent scaling, independent deployment, or separate operational ownership for its internal components.

Turning probes, correlation, storage, and reporting into network services would introduce failure modes unrelated to the failures Redline is intended to diagnose:

* Internal network failures
* Service version incompatibilities
* Authentication between local services
* Startup-order problems
* Message-delivery semantics
* Distributed tracing requirements
* Additional ports and attack surface
* More difficult Umbrel and StartOS packaging
* Higher memory consumption on small hosts

The project should not become a distributed system merely because it diagnoses distributed components.

Internal modules should remain separable by design, but deployment boundaries will be introduced only when justified by security, operational independence, or demonstrated scaling requirements.

### Security boundaries still receive separate processes

The modular-monolith decision does not mean everything runs in one process.

The optional privileged helper is a legitimate process boundary because compromise of the web API or protocol parser must not automatically provide unrestricted host privileges.

`redline-privd` will therefore be:

* Independently executable
* Root-owned
* Exposed only through a local Unix socket
* Authenticated using operating-system peer credentials
* Limited to a fixed set of typed operations
* Unable to execute arbitrary shell commands
* Unable to read arbitrary paths
* Disabled unless deep-scan functionality is installed and enabled

This is a security separation inside one product, not a microservice architecture.

### Go is preferable to Node.js for the backend

A TypeScript backend would allow more code sharing with the browser interface and could provide rapid early development.

It is not selected because the backend must integrate deeply with Linux, Docker, systemd, Unix sockets, process credentials, filesystem state, and optional privilege separation. Requiring a Node.js runtime would also complicate installation and increase baseline resource usage on small node appliances.

TypeScript remains appropriate for the local browser UI because the UI has different concerns and does not need direct host access.

### Rust remains a credible alternative, not a rejected technology

Rust is not rejected because it is unsuitable. It is rejected as the default backend language because its additional development cost is not currently justified by Redline’s workload.

Rust should be reconsidered for an isolated future component when that component has materially different requirements, such as:

* Parsing complex untrusted binary data
* Running under extremely tight memory constraints
* Requiring predictable low-level performance
* Integrating with a Rust-only platform library
* Becoming sufficiently security-sensitive that stronger compile-time guarantees outweigh implementation cost

No component should be rewritten in Rust merely for perceived prestige or generalized safety. A migration or isolated Rust component must address a demonstrated problem.

## Architectural constraints resulting from this decision

### Domain packages must remain platform-independent

The domain model, finding model, component graph, and correlation logic must not import Linux, Docker, Umbrel, StartOS, database, or HTTP-server packages.

Dependencies must point inward:

```text
platform implementations
        ↓
capability interfaces
        ↓
engine and probes
        ↓
domain
```

The domain layer must remain testable without a running operating system service, container engine, Bitcoin node, or database.

### Platform adapters provide access, not conclusions

A platform adapter may:

* Discover components
* Resolve service endpoints
* Read service state
* Provide bounded log access
* Expose filesystem statistics
* Report unavailable capabilities

A platform adapter may not decide:

* Whether Electrum is unacceptably behind
* Whether a miner outage is caused by DATUM
* Whether a Bitcoin node is operationally healthy
* Whether a dependency chain is broken
* What remediation the user should perform

Those decisions belong to probes and correlation rules.

### Probes must use capabilities rather than direct platform access

A Bitcoin probe should depend on a Bitcoin RPC capability.

A filesystem probe should depend on a filesystem-stat capability.

A service-state probe should depend on a process, systemd, Docker, or platform-service capability.

A probe must not inspect the current operating system to determine which implementation it should call.

This prevents the diagnostic engine from becoming a collection of hidden platform conditionals.

### Interfaces will be introduced at behavioral boundaries

The codebase will not define interfaces for every struct preemptively.

Interfaces are appropriate where:

* Multiple platform implementations exist
* Tests require controlled substitutes
* A security or process boundary exists
* The caller should not know the implementation
* An external dependency needs isolation

Concrete types are preferred within cohesive modules until an actual abstraction boundary is established.

This avoids an architecture dominated by speculative interfaces and indirection.

### Public contracts must be versioned

Although the initial product is local, several contracts may later be consumed by mobile clients, support tooling, report viewers, or hosted commercial services.

The following will therefore be versioned from their introduction:

* HTTP API
* JSON report schema
* Observation schema
* Finding codes
* Recommendation identifiers
* Privileged-helper protocol
* Export bundle format

Internal Go types are not automatically public contracts. API and export structures must be defined explicitly at the boundary.

### No native Go plugin mechanism

SATOSHI//REDLINE will not use Go’s native plugin mechanism for third-party extensions.

Native in-process plugins would create unacceptable coupling to:

* Compiler versions
* Dependency versions
* Internal package layouts
* Host process memory and privileges
* Redline release compatibility

First-party v0.1 probes will be compiled into the product.

Future extension mechanisms should use one of the following:

1. Declarative signed rule packs for thresholds and correlations
2. A versioned external process protocol
3. Sandboxed WebAssembly modules with narrowly granted host capabilities

Untrusted extension code must not run with the daemon’s full filesystem, network, credential, or privileged-helper access.

## Consequences

### Positive consequences

* The same diagnostic engine can power the daemon, CLI, web UI, and platform packages.
* Linux installation can remain small and self-contained.
* AMD64 and ARM64 builds can be produced from the same codebase.
* Concurrent diagnostic execution is straightforward.
* Memory and CPU overhead should be appropriate for home-node hardware.
* The backend has static typing without imposing Rust’s full development cost.
* The system can be tested with fake capabilities and protocol fixtures.
* Internal failures remain easier to trace than they would be across microservices.
* Sensitive operations can still be isolated in a dedicated process.
* The architecture can later be decomposed without requiring early decomposition.

### Negative consequences

* The project will use at least two implementation languages: Go for the backend and TypeScript for the web interface.
* Go cannot enforce every domain invariant as strongly as Rust’s type system.
* A poorly governed monolith could accumulate hidden coupling between modules.
* The compiled binary may grow as more platform integrations are added.
* In-process first-party probes share the daemon’s failure domain.
* Go does not provide a suitable stable native plugin ABI.
* Garbage collection introduces runtime behavior that must be considered, although it is not expected to materially affect diagnostic workloads.
* StartOS packaging will still require a thin TypeScript layer even though the engine is written in Go.

### Neutral consequences

* SQLite remains an implementation detail behind the storage module.
* The project may generate several binaries even though it is architecturally a modular monolith.
* The web UI may be developed and tested separately while still being embedded into production daemon builds.
* Some platform packages may provide fewer capabilities than generic Linux without requiring separate engines.

## Risks and mitigations

### Risk: The modular monolith becomes tightly coupled

**Mitigations:**

* Enforce package dependency direction.
* Keep platform types out of the domain layer.
* Require probes to use capability interfaces.
* Prohibit correlation rules from directly querying platforms.
* Add architecture tests that detect forbidden imports.
* Record significant boundary changes in later ADRs.

### Risk: Invalid diagnostic states remain representable

Go does not provide algebraic data types as directly as Rust.

**Mitigations:**

* Use dedicated types instead of unrestricted strings.
* Validate data at constructors and serialization boundaries.
* Separate observations, findings, and diagnoses.
* Require explicit unknown reasons.
* Require evidence references for every non-unknown finding.
* Reject malformed reports before storage or export.

### Risk: A probe blocks or leaks resources

**Mitigations:**

* Every probe accepts a context.
* Every network operation has an explicit timeout.
* The scheduler enforces global and per-class concurrency limits.
* Response bodies and connections are always closed.
* Long-running probes are separately classified.
* Tests include cancellation and timeout behavior.

### Risk: Sensitive data enters logs or persistence

**Mitigations:**

* Structured logging uses an allowlist of approved fields.
* Raw protocol responses are not logged.
* Raw logs are processed through bounded, streaming redaction.
* Storage accepts normalized domain objects rather than arbitrary byte payloads.
* Export performs a final fail-closed sensitivity scan.
* Secret-handling tests use generated canary values and verify that they do not survive.

### Risk: The privileged helper expands into a root agent

**Mitigations:**

* Define a closed operation enum.
* Do not expose command execution or arbitrary file reads.
* Keep the helper free of HTTP listeners.
* Authenticate over a root-owned Unix socket.
* Review every new privileged operation independently.
* Allow deployments to omit the helper completely.
* Treat expansion of the helper’s authority as an architectural decision requiring review.

### Risk: Go becomes a constraint for future extensibility

**Mitigations:**

* Keep public contracts language-neutral.
* Use JSON Schema and OpenAPI at external boundaries.
* Avoid exposing serialized internal Go types as permanent contracts.
* Use external-process or WebAssembly extensions instead of native plugins.
* Keep the correlation model independent of platform implementations.

## Implementation guidance

The initial codebase should remain deliberately small. Package boundaries should follow actual responsibilities rather than creating one package per type.

A suitable initial dependency structure is:

```text
cmd/redline
cmd/redlined
        │
        ▼
internal/app
        │
        ├── internal/engine
        ├── internal/reports
        ├── internal/storage
        └── internal/api
                    │
                    ▼
            internal/probes
            internal/correlation
                    │
                    ▼
          internal/capabilities
                    │
                    ▼
             internal/domain
```

Platform implementations satisfy capability interfaces:

```text
internal/platform/linux
internal/platform/docker
internal/platform/umbrel
internal/platform/startos
```

The privileged helper protocol should be defined independently from its Unix-socket transport so it can be tested without root privileges.

The browser UI should consume a generated client from the versioned OpenAPI contract rather than duplicating API request and response definitions manually.

## Validation criteria

This decision will be considered successful when the first vertical slice demonstrates all of the following:

* The same engine runs in the daemon and one-shot CLI.
* AMD64 and ARM64 artifacts are produced from the same source tree.
* A Bitcoin node and its storage dependency can be represented in the component graph.
* Probes execute concurrently with cancellation and deadlines.
* A fake capability provider can test the engine without a live Bitcoin node.
* The web UI receives scan progress without implementing diagnostic logic.
* The report schema is independent of internal Go types.
* Safe mode runs without root.
* Deep mode obtains one privileged observation through the constrained helper.
* Raw RPC responses and logs do not enter persistent storage.
* Umbrel or StartOS can wrap the same engine without forking its diagnostic rules.

## Reconsideration triggers

This ADR should be revisited if one or more of the following becomes true:

1. Independent teams need to deploy and release major backend modules separately.
2. SATOSHI//REDLINE introduces a remote fleet architecture that requires independently scalable services.
3. A third-party probe ecosystem becomes a core product requirement.
4. Go cannot support a required target platform or platform API.
5. Profiling demonstrates that Go’s runtime materially prevents operation on supported hardware.
6. The privileged helper requires substantially more low-level code than currently anticipated.
7. Mobile applications must execute the diagnostic engine locally rather than acting as clients.
8. Module coupling repeatedly prevents isolated testing or release.
9. A different language provides a measured and substantial security or delivery advantage for a specific component.
10. The operational needs of the product no longer match a local-first diagnostic appliance.

A reconsideration trigger does not automatically invalidate the decision. It requires a new ADR based on observed constraints rather than anticipated possibilities.

## Final decision statement

SATOSHI//REDLINE will begin as a Go modular monolith because this architecture provides the strongest balance of deployment simplicity, implementation velocity, static safety, resource efficiency, protocol support, and maintainability for a local-first cross-layer diagnostic system.

The monolith will be modular in code, unified in deployment, and divided into separate processes only where a genuine security boundary exists.

The architecture will preserve future options through versioned language-neutral contracts, capability-based platform access, isolated domain logic, and sandboxable extension boundaries rather than through premature microservices.
