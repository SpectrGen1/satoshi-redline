# ADR-005: Do Not Persist Raw Logs or Protocol Responses

* **Date:** 2026-07-30
* **Decision owners:** SATOSHI//REDLINE maintainers
* **Depends on:**

  * ADR-001 — Use a Go Modular Monolith for the Diagnostic Backend
  * ADR-002 — Use Capability-Based, Composable Platform Adapters
  * ADR-003 — Separate Observations, Findings, and Diagnoses
  * ADR-004 — Run the Main Daemon Unprivileged and Isolate Deep-Scan Access in an Optional Privileged Helper
* **Scope:** Production data ingestion, transient processing, application logging, local persistence, temporary storage, evidence normalization, diagnostic exports, and crash behavior
* **Excluded from scope:**

  * Exact report-retention periods
  * Database encryption
  * User authentication and authorization
  * User-provided files submitted outside the core diagnostic engine
  * Future opt-in forensic capture workflows
  * Development fixtures containing synthetic or manually sanitized data

## Context

SATOSHI//REDLINE must inspect data sources that frequently contain sensitive information unrelated to the diagnostic question being answered.

Potential sources include:

* Bitcoin JSON-RPC responses
* Electrum protocol messages
* DATUM status interfaces
* Stratum messages
* Tor status information
* systemd properties
* Docker metadata
* journal entries
* application logs
* configuration files
* command output
* process metadata
* network listener information
* privileged-helper responses

Even when Redline invokes a read-only operation, the returned data may contain:

* RPC usernames or passwords
* cookie contents
* authorization headers
* external IP addresses
* onion addresses
* payout addresses
* wallet addresses
* xpubs
* filesystem paths
* usernames
* container environment variables
* command-line arguments
* authentication failures containing supplied credentials
* URLs with embedded secrets
* API tokens
* private service names
* peer identifiers
* transaction identifiers
* user-entered wallet labels
* fragments of configuration files
* unrelated application activity

The diagnostic engine rarely needs the complete raw source.

For example, to determine whether an Electrum backend is behind Bitcoin, Redline needs normalized heights and timestamps. It does not need to retain the full Bitcoin RPC response or Electrum message.

To detect a restart loop, Redline may need:

* restart count
* timestamps
* exit status
* a classified failure reason

It does not need to preserve every journal line emitted by the process.

To determine whether a Docker container is healthy, Redline may need:

* container state
* restart count
* health status
* selected port bindings
* selected mount relationships

It does not need the container’s full environment or raw Docker inspection document.

Persisting raw material “for debugging” would create a durable repository of data that Redline explicitly promises not to collect or export. It would also make privacy depend entirely on the completeness of a later redaction pass.

Redaction alone is not a sufficient primary defense.

Secret formats evolve. Logs can contain arbitrary user-controlled text. Addresses and identifiers are not always syntactically distinguishable from harmless values. A value may be sensitive because of context rather than format. A generic regular expression cannot reliably determine whether every token in an unrestricted log is safe.

The safest durable dataset is therefore not a successfully redacted copy of all input. It is a deliberately constructed set of normalized diagnostic facts that never contained the irrelevant raw fields.

At the same time, Redline still needs:

* evidence for every finding
* expert-readable reports
* enough detail to localize failures
* trend history for monitoring
* reproducible diagnostic decisions
* meaningful support escalation

The architecture must preserve diagnostic value without creating a raw-data archive.

## Decision

SATOSHI//REDLINE will not persist raw logs, raw protocol responses, raw command output, raw configuration content, or unrestricted platform API responses.

Raw source data may exist transiently in process memory only for the minimum time needed to:

1. validate framing and size
2. parse the expected protocol or source format
3. extract approved typed fields
4. classify known events
5. construct normalized observations or structured collection errors
6. discard the source buffer

Only explicitly approved structured data may cross the persistence boundary.

The production persistence layer will accept:

* scan metadata
* component inventory records
* capability metadata
* probe-execution metadata
* normalized observations
* findings
* diagnoses
* incident lifecycle state
* structured recommendation references
* aggregated counters and trends
* approved sanitized aliases
* explicit truncation and evidence-quality metadata

It will not accept:

* arbitrary `[]byte`
* unrestricted strings from external sources
* raw JSON documents
* raw log lines
* raw RPC responses
* command stdout or stderr
* arbitrary maps copied from decoded external data
* generic “debug payload” fields
* unreviewed serialized provider objects

The initial production release will not persist free-form excerpts from source logs, even after generic redaction.

Evidence displayed in the UI or exported report will be generated from structured observations, finding parameters, diagnosis parameters, and approved message templates.

The central decision is:

> Redline will retain the smallest structured facts needed to explain a diagnosis, not the raw material from which those facts were extracted.

## Decision drivers

The decision drivers, in priority order, are:

1. Prevent durable storage of wallet, node, mining, and network secrets.
2. Make privacy depend primarily on data minimization rather than perfect redaction.
3. Ensure every persisted field has a defined diagnostic purpose.
4. Preserve enough normalized evidence to support Redline’s claims.
5. Prevent application logs and crash handling from becoming accidental data stores.
6. Limit the consequences of local database theft or report sharing.
7. Keep restricted and privileged data on the same controlled processing path.
8. Make persistence boundaries auditable and testable.
9. Support historical reevaluation of findings without retaining raw sources.
10. Fail closed when data cannot be proven safe to persist or export.

## Terminology

### Raw source data

Raw source data is any data returned substantially in the form supplied by an external system.

Examples include:

```text id="jnv2v0"
an HTTP response body
a JSON-RPC response object
an Electrum protocol message
a Stratum message
a Docker inspect document
a journal entry
a systemd property map
command stdout or stderr
a configuration file
a process environment
a line copied from an application log
```

Decoding JSON into a generic map does not make the data normalized.

Removing one known password field does not make the remaining object safe.

### Normalized observation

A normalized observation is an approved typed fact defined under ADR-003.

Examples:

```text id="oask5c"
Bitcoin block height: 910123
Bitcoin initial block download: false
Fulcrum block height: 910076
Filesystem free capacity: 8.2 GiB
Service restart count over 20 minutes: 11
DATUM template age: 94 seconds
Stratum subscription handshake: successful
```

A normalized observation contains only fields required by its registered schema.

### Structured collection error

A structured collection error describes why evidence collection failed without preserving the unbounded external error content.

Examples:

```text id="mhaefy"
connection_refused
authentication_failed
method_not_found
response_too_large
invalid_json
unexpected_message_type
permission_denied
deadline_exceeded
unsupported_version
```

A structured collection error may retain approved numeric or enumerated context such as:

* HTTP status class
* JSON-RPC error code
* process exit code
* TLS alert category
* operation identifier
* timeout duration

It must not retain arbitrary remote error text by default.

### Persistable data

Persistable data is a closed set of reviewed domain types accepted by the storage boundary.

A type is not persistable merely because it can be serialized.

### Exportable data

Exportable data is a stricter projection of persistable data that has passed export policy and final sensitivity validation.

Not all locally persisted data is necessarily exportable.

### Forbidden data

Forbidden data is information Redline must not intentionally retain or export.

Initial forbidden categories include:

* seed phrases
* private keys
* wallet passwords
* RPC credentials
* authorization tokens
* xpubs
* external IP addresses
* onion addresses
* payout addresses
* unrestricted wallet addresses
* private service credentials
* container secrets
* raw configuration content

## Data lifecycle

The production data lifecycle will be:

```text id="9wtpcv"
External source
      ↓
Bounded read
      ↓
Source-specific decoder
      ↓
Field allowlist and structural validation
      ↓
Typed extraction
      ↓
Sensitivity validation
      ↓
Normalized observation or structured error
      ↓
Finding and diagnosis evaluation
      ↓
Approved persistence
      ↓
Stricter export projection
      ↓
Final fail-closed export validation
```

Raw source data must not bypass this sequence.

### Bounded read

Every source read must enforce appropriate limits before or during allocation.

Limits may include:

* maximum HTTP response body
* maximum RPC message size
* maximum Electrum frame size
* maximum Stratum line size
* maximum number of journal records
* maximum total journal bytes
* maximum command-output bytes
* maximum Docker object count
* maximum configuration fragment size
* maximum nesting depth
* maximum JSON token count

If the source exceeds its limit, collection produces a structured limitation or error.

Redline must not increase limits automatically to obtain the complete raw response.

### Source-specific decoding

Each source type must have a decoder that understands its expected structure.

A Bitcoin RPC decoder should extract only approved response fields.

A Docker provider should build a typed container-state result rather than returning a generic inspect document.

A journal processor should classify approved events rather than preserving every field and message.

A generic JSON parser may be used internally, but generic decoded values must not cross the provider or probe boundary.

### Typed extraction

Approved fields are copied into dedicated domain types.

Unapproved fields are ignored rather than copied and later deleted.

This distinction is important:

```text id="0fykvd"
Preferred:
Extract the five fields Redline needs.

Rejected:
Copy the complete object and redact the known dangerous fields.
```

### Immediate discard

Once typed extraction and validation finish, the raw buffer must become unreachable from the diagnostic pipeline.

It must not be:

* attached to the probe execution
* placed in an asynchronous event
* sent to the report layer
* added to a retry record
* stored for support
* passed to the UI
* logged
* inserted into SQLite
* written to a temporary file

Where practical, mutable byte buffers should be overwritten before reuse or release.

However, Go does not provide a reliable guarantee that every copy created by the runtime, parser, or garbage collector has been zeroized. Redline will therefore avoid claiming guaranteed memory erasure.

The enforceable guarantee is architectural:

> Production code minimizes raw-data lifetime and prevents intentional application-level persistence or propagation.

## Data classification

Production data will use explicit sensitivity classes.

An initial classification model is:

```text id="zj5np5"
forbidden
ephemeral-sensitive
local-sensitive
normalized-safe
export-safe
```

### Forbidden

Data Redline must not intentionally retain.

Examples:

* private keys
* seed phrases
* RPC passwords
* wallet passwords
* xpubs
* payout addresses
* onion addresses
* external IP addresses

If forbidden data is encountered in raw input, it must not be copied into normalized objects.

### Ephemeral-sensitive

Data temporarily required for parsing or authentication but not eligible for persistence.

Examples:

* RPC cookie content
* authorization header
* raw RPC body
* raw journal line
* full TLS certificate object
* Docker inspect response
* raw configuration fragment
* raw helper response

### Local-sensitive

Structured data that may be useful locally but should not automatically be exported.

Possible examples include:

* internal component labels
* local service names
* local filesystem aliases
* internal port relationships
* host-specific installation identifiers

Local-sensitive data must still be typed and purpose-limited.

The exact local-sensitive catalog will be governed by the report and redaction architecture.

### Normalized-safe

Structured data approved for local persistence.

Examples:

* block heights
* restart counts
* resource percentages
* protocol latency
* implementation version
* pruning state
* index state
* enumerated service status
* event counts
* relative age and lag measurements

### Export-safe

A normalized field approved for inclusion in an explicitly generated shareable report.

Export-safe status is not inherited automatically from normalized-safe status.

## Persistence boundary

### Closed storage API

The storage module will expose methods accepting reviewed domain types rather than generic serialized data.

Conceptually:

```go id="fs9qdc"
type DiagnosticStore interface {
    SaveScan(ctx context.Context, scan ScanRecord) error
    SaveProbeExecution(ctx context.Context, execution ProbeExecutionRecord) error
    SaveObservation(ctx context.Context, observation PersistableObservation) error
    SaveFinding(ctx context.Context, finding FindingRecord) error
    SaveDiagnosis(ctx context.Context, diagnosis DiagnosisRecord) error
    SaveIncident(ctx context.Context, incident IncidentRecord) error
}
```

It will not expose methods such as:

```go id="00i49d"
SaveBlob(name string, data []byte)
SaveDebugPayload(value any)
SaveRawResponse(source string, body []byte)
SaveLogLine(line string)
SaveMetadata(map[string]any)
```

### Schema allowlists

Each persisted observation kind will have an explicit schema.

A database migration that introduces a new free-form text or binary field must receive security review.

The initial database schema should avoid generic columns such as:

```text id="qrsj5k"
raw_payload
debug_data
source_document
provider_response
extra_json
arbitrary_metadata
```

A constrained JSON column may be used for versioned typed observation values only if:

* its schema is registered
* serialization is produced from a dedicated type
* arbitrary maps are rejected
* forbidden-field tests cover the schema
* migrations preserve compatibility

### Database internals

SQLite rollback journals, WAL files, backups, and copied database files contain the same logical records as the database.

Because raw data never enters the database transaction, these mechanisms should not create raw-data remnants.

Sensitive raw data must not be briefly inserted and then deleted. Deletion is not an acceptable substitute because deleted values may remain in:

* free pages
* WAL files
* backups
* filesystem snapshots
* flash translation layers

The rule is:

> Raw data must never enter durable database storage, even temporarily.

## No temporary raw-data spool

Production Redline will not write raw source data to temporary files for later processing.

This includes:

* `/tmp` response captures
* temporary log bundles
* protocol transcripts
* command-output files
* crash-time payload dumps
* debug archives
* failed-parse samples

Processing must be streaming or memory-bounded.

If a source cannot be processed without temporarily writing the raw content to disk, that source is unsupported under the current architecture.

A future forensic-capture feature would require a separate ADR defining:

* explicit user consent
* clear retention
* encryption
* access control
* scope
* deletion semantics
* export behavior
* support workflow

It must not be introduced as a hidden debug option.

## Application logging

Redline’s own logs are not permitted to contain raw diagnostic source data.

### Structured allowlist

Application logging will use structured events with reviewed fields.

Permitted fields may include:

```text id="swvpst"
scan ID
probe ID
component alias
capability ID
provider ID
operation ID
outcome
duration
byte count
record count
truncated flag
error category
retryability
version
```

Prohibited fields include:

```text id="99ejbc"
response body
request body
raw log line
authorization header
cookie content
external endpoint
onion address
payout address
configuration fragment
Docker environment
command stdout
command stderr
generic serialized error object
```

### Error wrapping

Errors must preserve useful categories without embedding sensitive payloads.

Good:

```text id="p3o3th"
bitcoin RPC response exceeded 4 MiB limit
```

Rejected:

```text id="j8sfmt"
bitcoin RPC parse failed: <complete response body>
```

Good:

```text id="b49snh"
journal classifier encountered unsupported record format
```

Rejected:

```text id="f5udr8"
could not parse journal record: <entire journal record>
```

External error strings may contain reflected secrets or source content. They must not automatically be included through `%v`, `%+v`, generic stack wrapping, or automatic object serialization.

Providers must translate external errors into structured internal categories.

### Log levels do not weaken privacy

Debug or trace logging must not enable raw payload logging in production builds.

The following must not become valid merely because debug mode is active:

```text id="nz9ndp"
log complete RPC request
log complete RPC response
log journal lines
log environment variables
log configuration files
log authorization failures with supplied values
```

Debug logging may add:

* operation sequencing
* timings
* selected provider
* state-machine transitions
* counts
* size information
* safe schema names
* sanitized aliases

Privacy boundaries must not depend on the configured log level.

## Protocol-specific requirements

### Bitcoin JSON-RPC

Redline will:

* call only approved read-only methods
* decode only expected response fields
* avoid wallet RPC namespaces
* avoid `getpeerinfo` when an aggregate method provides sufficient evidence
* discard raw response bodies after typed extraction
* retain RPC error codes only when approved
* map arbitrary RPC error text to structured categories
* never persist authentication headers, cookie content, peer addresses, local addresses, or proxy addresses

If an implementation returns extra fields, those fields are ignored by default.

Unknown fields do not become generic metadata.

### Electrum

Redline will:

* enforce bounded line or frame sizes
* decode only approved message types
* extract protocol version, tip height, tip hash alias where approved, and latency
* discard full messages after extraction
* avoid persisting server banners when they may contain identifying information unless represented by an approved normalized implementation/version field
* avoid retaining arbitrary error strings

### Stratum

Redline will:

* retain only the normalized outcome of approved diagnostic handshakes
* avoid persisting subscription identifiers, usernames, payout addresses, extranonce values, or full work notifications unless a specific normalized field is approved
* not persist protocol transcripts
* not store submitted or received authorization material
* classify malformed or rejected responses without preserving unrestricted text

### DATUM

Redline will:

* use typed status and metric extraction where available
* normalize template age, connection state, counters, and selected versions
* avoid retaining raw gateway responses or complete status documents
* classify logs into event codes and counts where deep-scan evidence is used

### Tor

Redline will:

* retain only normalized reachability, bootstrap state, latency, and error categories
* not persist onion addresses
* not retain circuit or peer details
* not preserve raw control-protocol responses

### Docker

Redline will:

* never persist raw Docker inspect output
* never persist container environment variables
* avoid command arguments unless represented by an explicitly approved safe classification
* use typed allowlisted container-state fields
* represent mounts and endpoints through safe aliases where needed
* discard helper or Docker API responses after normalization

### systemd and journal

Redline will:

* retain typed unit state
* retain restart counts and approved timestamps
* retain classified event counts
* retain approved exit-code information
* avoid persisting complete unit property maps
* avoid persisting complete journal entries
* avoid persisting `_CMDLINE`, environment data, or arbitrary `MESSAGE` content
* discard raw bounded journal input after classification

### Command output

When a provider internally invokes a fixed command under ADR-004:

* stdout and stderr remain ephemeral-sensitive
* output limits are enforced
* known formats are parsed immediately
* exit status and approved fields may become normalized data
* raw output is not returned through capability interfaces
* parse failures produce structured provider errors
* failed output is not saved for later debugging

## Log classification

Deep-scan log analysis should convert log input into a controlled event vocabulary.

Example event codes:

```text id="oj09cl"
bitcoin.rpc-auth-failure
bitcoin.database-open-failure
bitcoin.disk-write-failure
bitcoin.unclean-shutdown
electrum.indexer-retry
electrum.database-lock
datum.node-rpc-disconnected
datum.template-refresh-timeout
datum.stratum-listener-failure
service.out-of-memory
service.permission-denied
service.restart
```

A persisted structured event may contain:

```go id="n6lc54"
type ClassifiedEventObservation struct {
    EventCode    EventCode
    Count        uint64
    WindowStart  time.Time
    WindowEnd    time.Time
    FirstSeenAt  time.Time
    LastSeenAt   time.Time
    SourceClass  SourceClass
    Truncated    bool
}
```

It must not contain the original log message.

When a log line does not match a known classifier, Redline may record:

```text id="swbcmx"
Unclassified relevant log records: 7
```

provided the determination of relevance itself is safe and deterministic.

It must not preserve the unmatched lines.

This creates an intentional tradeoff: some forensic detail is lost to preserve privacy.

## Evidence without raw excerpts

ADR-003 requires evidence for every finding. That evidence will normally consist of structured facts.

Example:

```text id="8anfzs"
Finding:
Fulcrum is 47 blocks behind Bitcoin.

Evidence:
- Bitcoin tip height: 910123 at 08:13:02
- Fulcrum tip height: 910076 at 08:13:05
- Observation skew: 3 seconds
- Allowed lag threshold: 3 blocks
```

Example:

```text id="n0fxmz"
Finding:
bitcoind is restarting repeatedly.

Evidence:
- Restart count: 11
- Evaluation window: 20 minutes
- Most recent exit classification: non-zero
- Current service state: activating
```

Example:

```text id="ev5i16"
Finding:
DATUM lost access to Bitcoin RPC.

Evidence:
- 19 classified RPC authentication failures
- First occurrence: 08:01:12
- Last occurrence: 08:11:47
- Successful template update after last failure: none observed
```

The absence of raw excerpts does not prevent precise evidence when the observation schemas are designed correctly.

## Source provenance

Persisted evidence may retain provenance such as:

```text id="19l5ls"
probe ID
probe version
capability ID
provider ID
operation version
source class
collection time
truncation state
evidence quality
```

It must not retain raw source identities when those identities are forbidden or unnecessary.

For example, provenance may say:

```text id="lxjc3z"
source class: bitcoin-json-rpc
provider: umbrel-bitcoin-binding
```

rather than storing the endpoint address.

## Sensitive identifiers and aliases

Where Redline must distinguish components, endpoints, peers, containers, or volumes, it should use local opaque aliases.

Examples:

```text id="esfha3"
bitcoin.primary
electrum.primary
service-A
container-B
volume-C
endpoint-D
```

Aliases should be derived from configuration identity or generated locally.

They must not be reversible encodings of forbidden identifiers.

Redline will not use unsalted hashes of:

* IP addresses
* onion addresses
* payout addresses
* RPC credentials
* raw log lines

as a substitute for retaining those values.

Small-domain values may be recoverable from unsalted hashes, and hashes can still create persistent correlation identifiers.

If stable correlation is required, it must be designed for the specific safe normalized field rather than applied to forbidden raw data.

## API and user interface

The local API will expose normalized diagnostic records and report projections.

It will not expose:

```text id="vr6im9"
raw protocol responses
raw journal entries
raw helper responses
raw command output
raw configuration content
generic provider debug payloads
```

There will be no production endpoint such as:

```text id="lxcuae"
/api/v1/scans/{id}/raw
/api/v1/debug/responses
/api/v1/log-bundle
```

The UI may show:

* evidence values
* event codes
* counts
* timestamps
* safe implementation versions
* coverage limitations
* structured error categories
* truncation notices
* provider provenance

The UI must not imply that a hidden raw archive is available.

## Export pipeline

Exports will be generated from normalized domain objects, not from raw source buffers.

The export path will be:

```text id="17k0lt"
persisted or in-memory normalized diagnostic model
        ↓
export projection
        ↓
field-level export allowlist
        ↓
identifier aliasing
        ↓
generic forbidden-pattern scanner
        ↓
schema validation
        ↓
explicit user save or share action
```

The generic scanner is a final defense, not the primary privacy mechanism.

If the exporter detects:

* a forbidden field
* an unknown free-form field
* an invalid schema
* a suspicious unclassified value
* an unsupported observation type
* a failed redaction invariant

the export must fail closed.

Redline should explain which internal record type prevented safe export without displaying the suspected sensitive value.

Automatic uploads remain prohibited.

## In-memory handling

Raw input may be processed in memory, but Redline will minimize its exposure.

Production code should:

* use bounded readers
* stream where practical
* avoid converting large byte buffers to immutable strings
* avoid copying response bodies unnecessarily
* avoid retaining raw input in closures or asynchronous jobs
* avoid generic request or response middleware that captures bodies
* reuse controlled buffers only after processing
* overwrite mutable secret buffers where practical
* close response bodies and file descriptors promptly
* cancel parsing when the scan is cancelled
* prevent raw values from entering panic messages

Because Go may copy data internally, zeroization cannot be guaranteed.

The architecture will not make claims such as:

```text id="ui1zjd"
all raw bytes are securely erased from RAM
```

The accurate claim is:

```text id="17d5ip"
Redline does not intentionally persist raw source data and minimizes its
lifetime and propagation within the process.
```

## Swap, hibernation, and host-level persistence

The operating system may write process memory to:

* swap
* hibernation images
* virtual-machine snapshots
* kernel crash dumps
* hypervisor snapshots

Redline cannot provide a universal guarantee against these host-level mechanisms.

This ADR defines the application’s persistence behavior.

Documentation should state that users with stronger host-level secrecy requirements should configure:

* encrypted swap
* encrypted storage
* disabled hibernation
* appropriate VM snapshot controls

Redline will not silently claim that transient memory can never reach physical storage.

## Core dumps and crash handling

Production service packaging will disable core dumps for:

* `redlined`
* `redline-privd`

The services should use controls such as:

```text id="yho4yi"
LimitCORE=0
```

Production builds and service definitions must not request Go crash behavior that writes process memory to a core file.

Panic handling must avoid serializing:

* request objects
* raw response objects
* parser buffers
* configuration values
* capability provider internals

Stack traces may include function names and safe metadata, but logs must not print local variables or payloads.

Crash reporting, if added later, must contain only approved structured application state and must remain local unless the user explicitly exports it.

## Backups and snapshots

Redline’s local database and configuration may be copied by:

* host backups
* filesystem snapshots
* appliance backups
* virtual-machine images

Because these mechanisms are outside Redline’s control, the durable database must be safe by construction.

Raw data must never be written with the expectation that later deletion will remove it from all copies.

The product documentation should distinguish:

* Redline’s own persistence guarantees
* host backup behavior
* operating-system memory persistence
* user-created diagnostic exports

## Authentication material

Some protocol providers must transiently use credentials.

Examples include:

* Bitcoin RPC cookies
* HTTP basic-auth values
* platform-injected service secrets

Credential handling will follow these rules:

1. Configuration stores a secret reference where possible, not the secret value.
2. Secret resolution occurs inside the narrow provider boundary.
3. Probes receive an authenticated client capability rather than credential bytes.
4. Credentials are never copied into observations.
5. Credentials are never logged.
6. Credentials are never included in provider errors.
7. Credentials are never written to SQLite.
8. Credentials are never exported.
9. Authentication failures retain only structured error categories.
10. The provider discards transient credential buffers as soon as practical.

This ADR does not claim that the Go runtime provides guaranteed memory zeroization.

## Unknown and unsupported input

If Redline receives a response shape it does not understand, it must not preserve the response for possible future interpretation.

The result should be a structured collection outcome such as:

```text id="fvd6k1"
protocol response unsupported
response schema version unknown
expected field missing
unexpected field type
message exceeded limit
```

The finding may become `unknown` because evidence could not be safely normalized.

This behavior is preferred over retaining unknown data.

Example:

```text id="gocpjy"
DATUM status analysis: unknown

Reason:
The gateway returned an unsupported status schema. Redline discarded the
response because it could not safely normalize the data.
```

## Development and testing data

Development tests may include:

* synthetic protocol responses
* generated fake logs
* manually sanitized fixtures
* intentionally embedded canary secrets
* public protocol examples

Production-collected raw data must not be automatically converted into a test fixture.

A contributor who wishes to add a real-world fixture must:

1. obtain it outside the production persistence system
2. sanitize it manually
3. replace identifying values with synthetic equivalents
4. run forbidden-data tests
5. document its provenance
6. receive review before committing it

Repository history is durable. Accidental inclusion of real secrets or user data in fixtures is a security incident.

## Support and escalation

The core product will produce a structured support report containing:

* component inventory
* diagnostic coverage
* normalized evidence
* findings
* diagnoses
* versions
* timestamps
* safe remediation steps
* explicit uncertainty

It will not automatically include raw logs.

When normalized evidence is insufficient, Redline may recommend:

```text id="3b62f6"
A human may need to inspect the original service logs locally.
```

This does not mean Redline retained those logs.

A support technician may guide the user through separate, explicit collection outside the core engine. Any future built-in support-capture feature must be governed by a new ADR rather than treated as an exception to this one.

## Retention

Because raw data is never persisted, ordinary retention policy applies only to normalized diagnostic records.

A later retention ADR may define:

* number of retained scans
* incident-history duration
* metric downsampling
* database-size limits
* manual deletion
* automatic expiration

Retention decisions must not broaden the types of data eligible for persistence.

Short retention is not a justification for storing raw input.

## Alternatives considered

### Alternative A: Persist everything locally and redact only during export

This is rejected.

Local-only storage can still be:

* stolen
* backed up
* snapshotted
* exposed by another local process
* accidentally included in support bundles
* retained after deletion
* accessed through future vulnerabilities

The privacy promise applies to local processing as well as transmission.

### Alternative B: Persist encrypted raw data

This is rejected for the core architecture.

Encryption reduces some theft risk but does not solve:

* application access to decrypted data
* key management
* excessive collection
* accidental export
* unsafe debugging
* retention governance
* unnecessary liability

Data that Redline does not need should not be collected merely because it can be encrypted.

### Alternative C: Persist generically redacted log lines

This is rejected for v0.1.

Generic redaction cannot reliably classify every context-sensitive identifier or secret in arbitrary text.

Redacted excerpts may also preserve unrelated personal or operational information.

The initial product will use structured event classification instead.

### Alternative D: Persist raw data for a few minutes

This is rejected.

Temporary persistence can still reach:

* WAL files
* deleted filesystem blocks
* snapshots
* backups
* crash dumps

A short retention timer does not make raw persistence safe.

### Alternative E: Store raw payload hashes

This is rejected as a general substitute.

Hashes of small-domain identifiers may be reversible through enumeration. Stable hashes can also permit unwanted correlation.

Redline may persist hashes only for specifically approved normalized values with a defined diagnostic purpose.

### Alternative F: Let debug mode record raw traffic

This is rejected in production builds.

Privacy guarantees must not disappear when a user enables verbose logging to diagnose a problem.

### Alternative G: Store raw data only after user consent

This is not selected as part of the core diagnostic workflow.

Meaningful consent would require a separate capture mode with clear scope, retention, encryption, and deletion behavior.

Such a feature requires a new ADR.

### Alternative H: Do not persist any diagnostic history

This would maximize data minimization but weaken:

* monitoring
* trend detection
* incident lifecycle
* before-and-after comparisons
* support reports
* evaluator replay

Persisting carefully normalized observations provides diagnostic value with substantially lower privacy risk than raw storage.

## Consequences

### Positive consequences

* The database cannot become a hidden archive of raw node and wallet data.
* Shareable reports are derived from controlled schemas.
* Data minimization reduces dependence on perfect regular-expression redaction.
* Local compromise exposes substantially less sensitive information.
* Raw protocol and log formats may evolve without silently expanding persistence.
* Evidence remains precise through typed observations.
* Rule reevaluation remains possible using normalized historical facts.
* Application debug logs remain safer to collect.
* Restricted and privileged sources follow the same persistence boundary.
* The product’s privacy claims become technically enforceable.
* Unknown input fails safely rather than being retained.
* Backups and snapshots contain only approved durable data.

### Negative consequences

* Some forensic detail will be unavailable after a scan completes.
* Unknown log formats cannot be inspected retrospectively.
* Classifiers must be implemented for diagnostically important log events.
* Protocol integrations require deliberate typed schemas.
* Support personnel may occasionally need the user to inspect original logs separately.
* New diagnostics may require recollecting evidence because the old raw response was discarded.
* Parsing failures are harder to debug from user installations.
* Developers cannot rely on raw captures from production systems.
* Building precise evidence schemas requires more up-front work than storing generic JSON.

### Neutral consequences

* Raw data still exists transiently in memory during parsing.
* Host swap and snapshots remain outside the application’s complete control.
* SQLite remains suitable because it stores only normalized records.
* Final export scanning remains necessary as defense in depth.
* Local-sensitive normalized identifiers may require separate export treatment.
* Synthetic fixtures remain permitted for development.

## Risks and mitigations

### Risk: Normalization removes evidence needed for a later diagnosis

**Mitigations:**

* Design observation schemas around diagnostic questions.
* Version observation kinds.
* Review proposed schemas with representative failure scenarios.
* Preserve approved timing, count, version, and quality metadata.
* Add new typed fields when a demonstrated diagnostic need exists.
* Re-run probes when new evidence is required.

### Risk: Developers add generic metadata fields

**Mitigations:**

* Prohibit arbitrary maps at persistence boundaries.
* Require schema review for new fields.
* Add architecture tests for forbidden storage APIs.
* Reject generic blob, payload, and debug columns.
* Use dedicated constructors for persistable records.

### Risk: External error strings enter logs

**Mitigations:**

* Use typed provider errors.
* Do not automatically wrap arbitrary remote text.
* Add safe error-formatting helpers.
* Test errors containing canary secrets.
* Prohibit generic object serialization in structured logs.

### Risk: Raw values survive through panic paths

**Mitigations:**

* Disable core dumps.
* Avoid payload values in panic messages.
* Recover at controlled process boundaries where appropriate.
* Log only approved panic metadata.
* Test malformed parser input under race and fuzz testing.

### Risk: Free-form fields hide sensitive content

**Mitigations:**

* Minimize free-form fields.
* Use message keys and typed parameters.
* Apply field-specific validators.
* Treat unknown strings as local-sensitive or non-persistable.
* Require export allowlisting.

### Risk: Log classifiers miss important failures

**Mitigations:**

* Track counts of unclassified relevant records without storing their text.
* Expose coverage limitations.
* Expand classifiers from sanitized fixtures.
* Prefer native metrics and APIs over log scraping.
* Mark findings unknown when classification is insufficient.

### Risk: Users expect Redline to retain original evidence

**Mitigations:**

* State clearly that Redline retains structured findings, not raw logs.
* Show normalized evidence in reports.
* Explain when human local log inspection is still required.
* Avoid UI controls implying that raw data can be retrieved later.

### Risk: A provider retains raw data internally

**Mitigations:**

* Keep provider lifetimes narrow.
* Review provider fields for raw buffers.
* Avoid caching protocol responses.
* Prohibit raw payloads in long-lived structs.
* Add heap-profile and lifecycle reviews for sensitive providers.
* Fuzz decoders and test cancellation paths.

### Risk: Temporary files are introduced by libraries

**Mitigations:**

* Review libraries handling large responses, archives, and multipart data.
* Disable automatic body spooling.
* Avoid generic upload middleware for diagnostic ingestion.
* Test filesystem activity during scans.
* Document any unavoidable runtime files.
* Reject dependencies that require unbounded raw spooling.

## Testing strategy

### Persistence-boundary tests

Tests must verify that storage APIs reject:

* raw bytes
* arbitrary strings from providers
* generic maps
* raw JSON
* raw log records
* unrestricted error objects
* unknown observation schemas

### Canary-secret tests

Generated canary values representing:

* RPC passwords
* cookies
* tokens
* onion addresses
* external IPs
* payout addresses
* xpub-like strings
* wallet addresses

will be inserted into synthetic:

* RPC responses
* error messages
* logs
* Docker metadata
* command output
* configuration fragments

Tests must verify that canaries do not appear in:

* SQLite
* WAL files after checkpoints
* application logs
* exported reports
* API responses
* helper audit logs
* panic output
* temporary directories

### Protocol tests

Each protocol integration must verify:

* response-size limits
* unknown-field omission
* malformed-input handling
* structured error mapping
* no raw response retention
* cancellation cleanup
* no payload logging at debug level

### Log-pipeline tests

Tests must cover:

* known event classification
* unknown event handling
* record-count bounds
* byte bounds
* truncation reporting
* multiline messages
* secret-bearing messages
* binary or invalid UTF-8 input
* maliciously crafted redaction bypass attempts

### Database tests

Tests must inspect:

* main database
* WAL
* rollback journal where used
* exported backups
* deleted-record behavior

The test goal is to prove that raw canaries were never written, not merely that current queries do not return them.

### API and export tests

Tests must verify:

* every exposed field belongs to an approved schema
* no raw debugging endpoint exists
* unsupported observation kinds fail export
* forbidden patterns cause export failure
* local-sensitive fields are omitted or aliased
* evidence remains understandable without source excerpts

### Fuzz testing

Fuzz targets should include:

* Bitcoin RPC decoders
* Electrum framing
* Stratum line parsing
* DATUM status parsing
* Docker normalization
* journal classification
* structured error conversion
* export validation

Fuzz failures must not dump complete secret-bearing inputs into ordinary production-style logs.

## Architecture enforcement

Automated architecture tests should enforce that:

1. Storage packages do not import raw provider response types.
2. Provider raw types do not implement persistence interfaces.
3. Report packages consume domain records, not capability responses.
4. API handlers cannot access raw collector buffers.
5. Logging helpers reject byte slices and generic objects.
6. Persistable observation types come from a registry.
7. Generic payload database columns are absent.
8. Production debug configuration cannot enable raw capture.
9. Helper responses must pass through a normalizing probe before persistence.
10. Export operates only on approved report projections.

Static analysis or custom linting should flag patterns such as:

```go id="18xw8e"
slog.Any("response", response)
slog.String("body", string(body))
fmt.Errorf("parse failed: %s", body)
store.Save(..., raw)
json.Marshal(providerResponse)
```

These checks will not replace code review, but they will make accidental regressions harder.

## Validation criteria

ADR-005 will be considered successfully implemented when:

1. No production storage API accepts arbitrary bytes or raw provider objects.
2. Raw RPC, Electrum, Stratum, DATUM, Docker, helper, and journal responses are never written to SQLite.
3. Raw data is never written to temporary files.
4. Application logs contain no raw diagnostic payloads at any log level.
5. Core dumps are disabled in production service packaging.
6. Every persisted observation uses a registered typed schema.
7. Unknown external fields are ignored rather than stored generically.
8. Raw external error strings are translated into structured categories.
9. Evidence in reports remains sufficient to explain initial Bitcoin and Electrum findings.
10. Deep-scan log analysis persists classified events and counts rather than log lines.
11. Export is generated only from normalized diagnostic models.
12. Export fails closed on unknown fields or forbidden-data detection.
13. Canary secrets do not appear in databases, WAL files, logs, API responses, temporary directories, or reports.
14. Debug logging cannot enable raw traffic capture.
15. A malformed or unsupported response produces explicit uncertainty without being archived.
16. Providers do not retain raw payloads in long-lived objects.
17. The privileged helper returns typed minimal results rather than raw subsystem documents.
18. Host-level limitations concerning swap and snapshots are documented honestly.
19. The first support report is useful without any raw log excerpts.
20. Architecture tests prevent report, API, and storage packages from importing raw response types.

## Reconsideration triggers

This ADR should be revisited if:

1. A critical diagnostic class cannot be implemented from normalized evidence.
2. Human support repeatedly cannot resolve failures without built-in source excerpts.
3. Users explicitly require an opt-in forensic capture mode.
4. A platform API provides only opaque diagnostic bundles that cannot be safely streamed and normalized.
5. Legal, compliance, or incident-response requirements demand preservation of original evidence.
6. A remote agent architecture changes where normalization occurs.
7. Encrypted local evidence capture becomes a core paid feature.
8. A formally verified redaction mechanism becomes practical for a narrow source class.
9. New mobile workflows require temporary transfer of evidence not represented in current schemas.
10. Database or export schemas cannot preserve adequate diagnostic provenance without broader fields.

A reconsideration trigger does not permit adding a hidden raw-payload column, debug archive, or temporary spool.

Any production feature that intentionally persists raw or substantially free-form source content requires a new ADR defining:

* exact source scope
* user consent
* privilege requirements
* encryption
* retention
* deletion
* export
* support access
* threat model
* platform behavior

## Final decision statement

SATOSHI//REDLINE will not persist raw logs, raw protocol responses, raw command output, raw configuration content, or unrestricted platform API data.

Raw input may exist transiently and within strict bounds while a source-specific decoder extracts approved typed facts. Once normalization completes, the raw material is discarded.

Only registered structured observations, findings, diagnoses, incident state, and approved metadata may cross the durable-storage boundary.

Application logs, debug modes, temporary files, crash handling, APIs, and exports must not provide alternate paths around this rule.

When Redline cannot safely normalize a source, it will report that the evidence is unavailable or unsupported rather than retaining the source for later inspection.

The central rule established by this ADR is:

> Diagnostic value must be designed into structured evidence. Raw data is not a safety net; it is a liability Redline deliberately refuses to accumulate.
