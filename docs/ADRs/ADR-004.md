# ADR-004: Run the Main Daemon Unprivileged and Isolate Deep-Scan Access in an Optional Privileged Helper

* **Date:** 2026-07-30
* **Decision owners:** SATOSHI//REDLINE maintainers
* **Depends on:**

  * ADR-001 — Use a Go Modular Monolith for the Diagnostic Backend
  * ADR-002 — Use Capability-Based, Composable Platform Adapters
  * ADR-003 — Separate Observations, Findings, and Diagnoses
* **Scope:** Host privilege boundaries, deep-scan access, privileged capability providers, local inter-process communication, helper authorization, and failure behavior
* **Excluded from scope:**

  * Web UI authentication and remote-access policy
  * Report redaction implementation details
  * Automated remediation or service control
  * Cloud agents or remote fleet management

## Context

SATOSHI//REDLINE must inspect system state that is not always available to an ordinary unprivileged process.

A safe scan can obtain substantial diagnostic value through:

* Bitcoin JSON-RPC
* Electrum protocol requests
* TCP and TLS checks
* DATUM and Stratum interfaces
* Tor SOCKS access
* user-readable filesystem statistics
* platform-provided service APIs
* application health endpoints

A deeper Linux scan may require access to:

* systemd unit state and restart history
* protected journal entries
* Docker container state
* container restart metadata
* mount information
* protected data-directory metadata
* process ownership and state
* selected kernel and filesystem signals
* network listener ownership
* restricted configuration metadata

Giving the entire Redline daemon elevated privileges would make every part of the application part of the privileged attack surface.

The main daemon will contain or invoke:

* an HTTP server
* a browser-facing API
* protocol clients
* parsers for RPC responses
* Electrum and Stratum parsers
* log-processing code
* report generation
* SQLite access
* platform discovery
* future extension mechanisms

Any defect in one of these areas could expose the privileges of the process.

This is particularly concerning because Redline will inspect software that communicates over local and external networks. A malformed response from a Bitcoin-adjacent service, a compromised local application, or an error in the web API must not automatically become unrestricted host access.

At the same time, the privileged boundary must not be ceremonial. A helper that exposes arbitrary command execution, arbitrary path reads, unrestricted Docker access, or generic root RPC would merely move the same risk into another process.

The architecture must provide meaningful deep-scan evidence while keeping the privileged interface:

* optional
* local
* narrow
* typed
* bounded
* read-only
* independently auditable
* safe even if the unprivileged daemon is compromised

## Decision

SATOSHI//REDLINE will use two host-side privilege domains.

### Unprivileged domain

The primary daemon, `redlined`, will run under a dedicated unprivileged operating-system account.

It will contain:

* the diagnostic engine
* platform adapters
* safe capability providers
* protocol clients
* scan planning
* observations, findings, and diagnoses
* local persistence
* report generation
* the local API
* the embedded web UI

It will not run as root.

It will not receive ambient Linux capabilities as a substitute for proper privilege separation.

It will not be added to the host Docker group by default.

### Privileged domain

Deep-scan operations that genuinely require greater authority will be implemented by a separate executable:

```text id="4qz7dd"
redline-privd
```

The helper will:

* run only on supported Linux deployments
* be optional to install and enable
* expose only a fixed catalog of typed read-only operations
* listen only on a local Unix-domain socket
* authenticate callers using operating-system peer credentials
* accept requests only from the configured `redlined` service UID
* enforce per-operation argument validation and output bounds
* return minimal typed data rather than raw system interfaces
* maintain no diagnostic database
* expose no HTTP server
* perform no external network access
* accept no shell commands
* accept no arbitrary file reads
* perform no state-changing remediation

The helper will be treated as a privileged capability provider under ADR-002.

It will not produce observations, findings, or diagnoses. It will return narrowly scoped capability data to probes running in the unprivileged daemon.

The default operating mode will remain Safe Scan.

Deep Scan may use the helper only when:

1. The helper is installed and compatible.
2. The relevant privileged operation is enabled by root-owned policy.
3. The scan was explicitly initiated or configured as a deep scan.
4. The probe declares that it requires or optionally uses the corresponding capability.

The central decision is:

> Redline’s network-facing and diagnostic logic will remain unprivileged. Root authority will exist only behind a small, local, typed, read-only interface.

## Decision drivers

The decision drivers, in priority order, are:

1. Limit the impact of a compromised daemon or web interface.
2. Keep Safe Scan genuinely low privilege.
3. Obtain useful host-level evidence without exposing generic root access.
4. Ensure deep scanning remains optional.
5. Preserve the capability model established by ADR-002.
6. Preserve the evidence model established by ADR-003.
7. Prevent arbitrary command execution and arbitrary file access.
8. Make privilege use visible, attributable, and testable.
9. Support failure without taking down the diagnostic engine.
10. Allow the privileged surface to evolve under explicit architectural review.

## Threat model

This ADR assumes the following may be compromised or malicious:

* the browser UI
* the local HTTP API
* the unprivileged `redlined` process
* a protocol peer
* a local Bitcoin-adjacent service
* a malformed RPC, Electrum, Stratum, or DATUM response
* a malicious or secret-bearing log line
* an unprivileged local user
* user-controlled Redline configuration
* a future non-privileged extension

The helper must therefore remain safe when the caller sends:

* unexpected operation sequences
* malformed requests
* oversized inputs
* invalid identifiers
* repeated requests
* requests for resources outside the intended diagnostic scope
* requests intended to extract secrets
* requests designed to consume excessive CPU, memory, disk, or journal bandwidth

This ADR does not attempt to protect against:

* an attacker who already has root
* a compromised kernel
* deliberate modification of Redline’s root-owned helper policy
* replacement of the installed Redline binaries by root
* physical attacks against the host
* vulnerabilities in the operating system’s privilege enforcement

The helper is a blast-radius boundary, not a sandbox against a hostile kernel or administrator.

## Process architecture

```text id="peapm5"
┌─────────────────────────────────────────────────────────┐
│ Browser / CLI                                           │
└──────────────────────┬──────────────────────────────────┘
                       │ local API or CLI request
                       ▼
┌─────────────────────────────────────────────────────────┐
│ redlined                                                │
│ Dedicated unprivileged UID                              │
│                                                         │
│ - API and embedded UI                                   │
│ - Scan planner                                          │
│ - Protocol probes                                       │
│ - Safe capability providers                             │
│ - Observations, findings, diagnoses                     │
│ - SQLite                                                │
│ - Reports and redaction                                 │
└──────────────────────┬──────────────────────────────────┘
                       │ versioned local protocol
                       │ Unix-domain socket
                       ▼
┌─────────────────────────────────────────────────────────┐
│ redline-privd                                           │
│ Root-owned privileged service                           │
│                                                         │
│ - Authenticate peer UID                                 │
│ - Validate operation                                    │
│ - Enforce policy and bounds                             │
│ - Perform one typed read-only operation                 │
│ - Return minimal typed response                         │
│                                                         │
│ No HTTP, no database, no external network, no shell API  │
└─────────────────────────────────────────────────────────┘
```

The browser and CLI will never communicate directly with `redline-privd`.

All deep-scan requests must pass through the normal scan planner.

The daemon must not expose a generic API method such as:

```text id="h1v0sq"
POST /api/helper/request
```

that forwards arbitrary client-supplied helper operations.

The application API may request a predefined deep scan. The engine then determines which approved capability operations are required.

## Operating-system identities

The generic Linux package will create a dedicated system identity for the daemon, conceptually:

```text id="rbxc9e"
user:  satoshi-redline
group: satoshi-redline
```

The daemon will not run under the interactive user’s account.

The privileged helper will run as a root-owned system service.

The helper’s socket will be located in a volatile runtime directory such as:

```text id="66uk6e"
/run/satoshi-redline/privd.sock
```

The directory and socket must not be writable by the daemon.

The socket configuration should permit connection by the daemon account while the helper independently verifies the peer UID.

Group membership alone will not be treated as sufficient authentication.

The helper must verify the connecting process using Linux peer credentials, such as `SO_PEERCRED`.

The expected caller UID will come from root-owned service configuration, not from a value supplied by the connecting process.

### Compromise of the daemon UID

Any process running under the Redline daemon UID may be able to connect to the helper.

The architecture will not rely on executable-path checks, process names, or caller-provided tokens to make a compromised daemon trustworthy.

Instead, the helper API itself must remain safe when fully controlled by a process running as the daemon UID.

This is why the helper must not expose generic root operations.

## Communication protocol

### Transport

The initial Linux implementation will use a local Unix-domain socket.

A message-oriented Unix socket such as `SOCK_SEQPACKET` is preferred where it is reliably supported by the Go implementation and target packaging.

A length-delimited Unix stream protocol is acceptable when:

* maximum frame sizes are enforced
* partial-frame behavior is tested
* timeouts are explicit
* malformed framing closes the connection
* memory allocation is bounded before decoding

No TCP listener will be provided.

The helper protocol will not be remotely accessible.

### Serialization

The initial protocol may use strict JSON or another simple schema-driven encoding.

Whichever encoding is selected must support:

* explicit protocol versions
* bounded message sizes
* rejection of unknown or duplicate critical fields
* strict enum decoding
* typed request and response objects
* no unbounded recursive structures
* no arbitrary payload field

Ease of auditing is more important than wire efficiency.

### Handshake

At connection establishment, the daemon and helper will exchange:

```text id="r3suba"
protocol major version
protocol minor version
build identifier
supported operation versions
enabled policy features
maximum request and response sizes
helper instance identifier
```

The daemon must reject an incompatible helper rather than guessing compatibility.

An older helper may expose fewer capabilities. Missing operations become unavailable capabilities and therefore explicit diagnostic uncertainty.

The daemon must not silently emulate a privileged operation using a less safe generic mechanism.

### Request lifecycle

The preferred initial lifecycle is one bounded request and one bounded response per operation.

Each request will include:

```go id="tnn55e"
type PrivilegedRequest struct {
    ProtocolVersion ProtocolVersion
    RequestID       RequestID
    Operation       OperationID
    OperationVersion uint
    Resource        ResourceHandle
    Parameters      OperationParameters
    Deadline        time.Time
}
```

Each response will include:

```go id="sq0sq5"
type PrivilegedResponse struct {
    RequestID      RequestID
    Outcome        OperationOutcome
    Data           OperationResult
    Limitation     *OperationLimitation
    Error          *PrivilegedError
    StartedAt      time.Time
    FinishedAt     time.Time
}
```

Requests and responses must have hard size limits.

The helper may impose stricter limits than the daemon requested.

## Fixed operation catalog

The helper will expose a closed operation catalog.

Initial candidate operations include:

```text id="hzw4va"
systemd.discover-services/v1
systemd.read-unit-state/v1
systemd.read-restart-history/v1
journal.read-bounded/v1
docker.discover-containers/v1
docker.read-container-state/v1
filesystem.stat-configured-target/v1
mount.read-state/v1
process.read-summary/v1
network.read-listener-summary/v1
kernel.read-error-summary/v1
```

Each operation will define:

* valid resource types
* valid parameters
* maximum execution time
* maximum output size
* sensitivity classification
* required root-owned policy
* whether it may start a subprocess
* allowed underlying system APIs
* fields that may be returned
* fields that must never be returned

The helper will not expose operations resembling:

```text id="a4jwnd"
execute-command
execute-shell
read-file
write-file
list-directory-arbitrary
docker-api-proxy
systemd-dbus-proxy
journal-query-arbitrary
open-socket
connect-network
restart-service
stop-service
modify-firewall
change-permissions
```

The lack of destructive actions is an architectural requirement, not merely a UI restriction.

## Resource addressing

The daemon should not send unrestricted filesystem paths, Docker queries, journal expressions, or service-manager commands to the helper.

Privileged resources will be addressed using one of two mechanisms.

### Root-owned configured resources

Resources requiring explicit privileged access may be defined in root-owned policy:

```toml id="fqox9c"
[targets.bitcoin_data]
type = "filesystem"
path = "/var/lib/bitcoind"

[targets.bitcoind_service]
type = "systemd-unit"
name = "bitcoind.service"
```

The daemon refers to:

```text id="w6nmi8"
bitcoin_data
bitcoind_service
```

rather than passing the underlying path or unit definition as an unrestricted argument.

The daemon and web UI must not be able to broaden this policy.

### Helper-issued resource handles

For resources discovered dynamically by the helper, the helper may return opaque handles.

Example:

```text id="vpv0ub"
service:7f94...
container:1ae2...
mount:8c31...
```

Subsequent operations may reference these handles.

Handles will be:

* scoped to the current helper instance
* associated with one resource type
* invalidated when discovery state changes materially
* unusable across unrelated operation classes
* non-authoritative outside the helper

A handle prevents the daemon from turning a typed resource operation into an arbitrary host selector.

Human-readable names may still be returned when diagnostically appropriate, but names do not become authority-bearing selectors unless policy explicitly allows them.

## Root-owned policy

The helper’s authority will be governed by a root-owned policy file, conceptually:

```text id="rl5mt8"
/etc/satoshi-redline/privd-policy.toml
```

The policy may define:

* expected daemon UID
* enabled operation families
* configured service targets
* configured filesystem targets
* journal lookback limits
* maximum returned records
* allowed container discovery scope
* whether process and listener inspection are enabled
* operation rate limits
* helper logging level

The file must not be writable by the daemon account.

Configuration changes made through the normal Redline web UI must not expand helper authority.

Where a user wants Redline to inspect a new protected path or service, that expansion requires an explicit host-administration action.

This creates intentional friction at the privilege boundary.

## Data minimization

The helper will return the minimum structured data required by the capability contract.

### Filesystem example

Good:

```go id="lyo5qj"
type FilesystemStatResult struct {
    TotalBytes     uint64
    AvailableBytes uint64
    ReadOnly       bool
    MountPresent   bool
    FilesystemType FilesystemType
}
```

Rejected:

```text id="x5s2lc"
recursive directory listing
file contents
ownership data for every child
raw output from df or mount
```

### systemd example

Good:

```go id="y9uu6s"
type ServiceStateResult struct {
    LoadState          string
    ActiveState        string
    SubState           string
    MainProcessPresent bool
    RestartCount       uint64
    StateChangedAt     time.Time
}
```

Rejected:

```text id="uyvqz0"
all unit properties
all environment variables
full unit file
arbitrary D-Bus property access
```

### Docker example

Good:

```go id="v9sdz6"
type ContainerStateResult struct {
    Running        bool
    Restarting     bool
    RestartCount   uint64
    StartedAt      time.Time
    FinishedAt     *time.Time
    HealthStatus   string
    ExitCode       *int
    PortBindings   []SanitizedPortBinding
    MountAliases   []ResourceHandle
}
```

Rejected:

```text id="75gnp3"
container environment variables
raw Docker inspect response
registry credentials
bind-mounted secret paths
container command line when it may contain secrets
arbitrary Docker API access
```

### Journal example

The helper must not act as a generic journal export service.

A bounded journal operation must enforce:

* one approved service resource
* a maximum lookback window
* a maximum number of entries
* a maximum total byte count
* a fixed set of returned fields
* first-stage secret filtering
* truncation metadata

Where practical, the helper should return structured event summaries rather than raw lines.

When bounded redacted text is required for later source-specific parsing, it must be marked sensitive and passed directly through the daemon’s redaction pipeline without persistence of the raw intermediate.

## Subprocess execution

The helper will not provide arbitrary command execution.

A specific helper operation may internally invoke a fixed system command only when:

1. A stable native API is unavailable or materially less reliable.
2. The executable path is compiled in or root-configured.
3. No shell is used.
4. The argument vector is fully constructed by the helper.
5. Request values cannot introduce new flags or expressions.
6. The environment is replaced with a minimal fixed environment.
7. Standard input is closed.
8. Output size and execution time are bounded.
9. Exit status is interpreted by operation-specific code.
10. The subprocess use is documented in the operation definition.

For example, a bounded `journalctl` invocation may be acceptable as an internal implementation of `journal.read-bounded/v1`.

It does not justify exposing a generic process runner.

## Docker access

Access to the host Docker socket is effectively privileged host access.

Therefore:

* `redlined` will not be added to the Docker group by default.
* The host Docker socket will not be mounted directly into the normal daemon by default.
* The helper may access Docker only through typed, read-only operations.
* Raw Docker API responses will not be returned to the daemon.
* Environment variables and other commonly secret-bearing fields will be excluded.
* The helper will not support container creation, execution, restart, stop, image pull, volume mutation, or file copying.

Platform-local container information supplied by Umbrel or StartOS through their supported interfaces is a separate `platform-granted` capability and does not automatically imply host Docker authority.

## systemd and journal access

The helper may use systemd D-Bus, journald APIs, or fixed command invocations to obtain approved data.

It will not expose a generic D-Bus proxy.

The helper will not support:

* starting units
* stopping units
* restarting units
* enabling or disabling units
* changing unit properties
* writing transient units
* arbitrary journal expressions

Service identity must come from a configured target or helper-issued handle.

Journal reads must remain bounded and associated with a diagnosed component.

## Network restrictions

The helper will not perform general network operations.

Its address-family access should be restricted to what is required for:

* the local Unix socket
* local system APIs
* local Docker or service-manager sockets

The helper will not:

* perform DNS resolution
* connect to Bitcoin RPC
* connect to Electrum
* connect to Stratum
* connect through Tor
* contact external services
* upload reports
* fetch updates

All protocol and network diagnostics remain in the unprivileged daemon.

This ensures that network-facing parsers and privileged host authority do not coexist in the same process.

## Filesystem restrictions

The helper must not provide arbitrary file-reading capability.

Filesystem operations will be divided into typed classes, such as:

```text id="em0q5c"
stat configured target
read mount state
check path existence
read approved metadata field
```

Operations must canonicalize configured paths and resist:

* symbolic-link substitution
* path traversal
* mount replacement
* race conditions between validation and access

Where possible, the helper should:

* open the configured resource once
* use file descriptors rather than re-resolving paths
* apply `openat2`-style resolution restrictions on supported Linux systems
* avoid following symbolic links
* verify resource type after opening
* return metadata rather than contents

A future need to read configuration content from protected files requires a separate operation with explicit field extraction and redaction. It will not be added by broadening a generic filesystem operation.

## Capability integration

Under ADR-002, privileged helper operations will be exposed to the engine as ordinary typed capabilities with metadata such as:

```text id="8prmzi"
Capability:
    service.restart-history.read/v1

Provider:
    linux.redline-privd.systemd/v1

Privilege:
    privileged-helper

Side effect:
    sensitive-read

Subject:
    service.bitcoind

Availability:
    available
```

Probes will not know that a capability is implemented through a root process unless they inspect capability metadata for reporting purposes.

The same restart-loop evaluator must work when evidence comes from:

* `redline-privd`
* a StartOS service API
* an Umbrel-supported interface
* a future platform-native provider

The meaning of the finding does not change based on the provider.

## Observation integration

The privileged helper will not emit ADR-003 observations directly.

The flow will be:

```text id="7d02jg"
redline-privd returns typed capability data
                    ↓
probe validates and normalizes the response
                    ↓
probe creates observation
                    ↓
evaluator creates finding
                    ↓
correlation engine creates diagnosis
```

Every observation derived from the helper will record:

* the privileged capability ID
* the provider ID
* the helper operation version
* the helper instance identifier
* the time the operation ran
* whether output was truncated or degraded
* the privilege class

The observation will not contain the helper request, raw response, or protected selector.

## Scan modes and user control

### Safe Scan

Safe Scan is the default.

It must:

* run without the helper
* remain fully functional when the helper is not installed
* avoid privileged capability resolution
* avoid presenting missing deep-scan evidence as a component failure
* state which deeper checks were not attempted

### Deep Scan

Deep Scan may use helper-backed capabilities.

Before execution, the engine should be able to summarize the additional evidence classes it intends to request:

```text id="r2251c"
Deep Scan will inspect:

- systemd service state and restart history
- bounded logs for selected Redline components
- Docker container state
- configured filesystems and mounts
- local process and listener summaries
```

The user does not approve individual low-level helper operations. The user approves a defined scan mode or scan profile whose capability requirements are visible.

The engine must not automatically switch from Safe Scan to Deep Scan.

### Continuous monitoring

Continuous monitoring should use Safe Scan by default.

Privileged continuous checks must be separately enabled and should be limited to low-cost, bounded operations.

Continuous privileged log collection will not be enabled by default.

Deep scans that read bounded logs or enumerate protected resources should remain user-initiated unless a later ADR defines a safe monitoring profile.

## Failure semantics

The daemon must continue operating when the helper is:

* not installed
* disabled
* stopped
* incompatible
* denied by policy
* temporarily unavailable
* too old to support an operation
* rate-limiting requests
* returning malformed responses
* failing internally

The resulting capability state will map to explicit diagnostic uncertainty.

Examples:

```text id="2zxkx7"
Restart-loop analysis: unknown
Reason: privileged helper is not installed
```

```text id="wmffnt"
Docker restart analysis: unknown
Reason: container inspection is disabled by host policy
```

```text id="r2mqny"
Protected journal analysis: unknown
Reason: helper protocol version is incompatible
```

The helper’s absence must never make the whole scan fail.

A helper error must not be converted into evidence that the target component failed.

The error model must distinguish:

* helper unavailable
* helper authentication failure
* policy denial
* operation unsupported
* target not found
* target state changed
* operation timeout
* output truncated
* malformed helper response
* internal helper failure

## Rate limits and resource bounds

The helper must defend itself against a compromised or malfunctioning daemon.

It will enforce:

* maximum concurrent connections
* maximum concurrent operations
* per-operation execution deadlines
* request-size limits
* response-size limits
* journal record limits
* log byte limits
* process and container enumeration limits
* per-caller rate limits
* cool-down periods for expensive operations
* cancellation where the underlying API supports it

The helper should reject excessive work rather than attempting to satisfy it and exhausting host resources.

A rate-limited operation becomes an unavailable or degraded capability for that scan, with an explicit limitation.

## Helper state

The helper will remain as stateless as practical.

It may retain in memory:

* parsed root-owned policy
* helper-issued resource handles
* rate-limit state
* capability metadata
* short-lived operating-system handles
* its instance identifier

It will not retain:

* diagnostic history
* reports
* observations
* findings
* raw logs
* RPC credentials
* protocol responses
* user wallet data
* a copy of the Redline SQLite database

Restarting the helper may invalidate resource handles. The daemon must rediscover them.

## Logging and auditing

The helper will write a minimal structured local audit trail.

Permitted fields include:

```text id="h4yqrr"
operation ID
operation version
caller UID
resource alias or opaque-handle class
outcome
duration
response size
truncation state
policy decision
```

The helper must not log:

* raw request payloads
* raw response payloads
* filesystem paths beyond approved aliases
* service logs
* environment variables
* credentials
* network identifiers
* onion addresses
* payout addresses
* arbitrary command output

The audit trail is intended to answer:

* Which privileged operation ran?
* Which caller invoked it?
* Was it permitted?
* How long did it take?
* Did it complete or fail?

It is not a secondary diagnostic data store.

## Service hardening

The Linux service definition for `redline-privd` will apply systemd hardening appropriate to its actual operation set.

Candidate protections include:

```text id="xs9gmd"
NoNewPrivileges=yes
PrivateTmp=yes
PrivateDevices=yes
ProtectSystem=strict
ProtectHome=yes
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectKernelLogs=yes
ProtectControlGroups=yes
ProtectClock=yes
LockPersonality=yes
MemoryDenyWriteExecute=yes
RestrictRealtime=yes
RestrictSUIDSGID=yes
RestrictAddressFamilies=AF_UNIX
SystemCallArchitectures=native
```

The final hardening profile must be tested against each approved helper operation.

Hardening controls must not be copied blindly if they prevent required read-only inspection and encourage disabling the entire profile.

Any required exception should be narrow and documented.

The helper should not depend on writable persistent directories.

Its writable paths should normally be limited to:

* its runtime socket directory
* unavoidable temporary runtime state
* the system journal through normal logging

## Binary and update integrity

`redlined` and `redline-privd` may be updated together, but the helper protocol must not assume perfectly synchronized upgrades.

The handshake will support a declared compatibility range.

The helper will reject unknown operation versions.

The daemon will treat unavailable newer operations as missing capabilities.

An incompatible version will produce explicit coverage loss rather than unsafe fallback.

Package ownership and permissions must prevent the unprivileged daemon from replacing:

* the helper binary
* the helper service definition
* the root-owned policy
* the socket directory configuration

## Alternatives considered

### Alternative A: Run the entire daemon as root

This is rejected.

It would place the API server, protocol parsers, report engine, database, UI integration, and future extension system inside the root trust boundary.

It would maximize the impact of a daemon compromise.

### Alternative B: Grant Linux capabilities directly to `redlined`

This is rejected as the default.

Linux capabilities are process-wide ambient authority. They would still be available to network-facing parsers and the HTTP service.

They also do not cleanly solve access to Docker, journald, systemd, and protected files without introducing additional groups or broad permissions.

### Alternative C: Add `redlined` to the Docker group

This is rejected as the default because membership in the Docker group is effectively equivalent to broad host-root authority.

A read-only intention does not make the Docker API itself read-only.

### Alternative D: Use `sudo` commands from the daemon

This is rejected.

A sudo-based design would rely on command-line argument restrictions and text output while increasing the risk of:

* unsafe sudoers rules
* argument injection
* unstable parsing
* command substitution mistakes
* accidental expansion of authority
* raw secret-bearing output

### Alternative E: Install a setuid-root CLI

This is rejected.

Setuid programs require an exceptionally small and carefully audited interface. A multi-operation diagnostic CLI would create an unsafe and difficult-to-govern boundary.

A supervised local service with a typed protocol provides stronger lifecycle control, rate limiting, version negotiation, and auditing.

### Alternative F: Use a generic root RPC service

This is rejected even if the RPC is available only through a Unix socket.

Transport locality does not make arbitrary root operations safe.

### Alternative G: Use polkit for every deep-scan operation

Polkit may be suitable for certain future administrative workflows, but it is not selected for the initial architecture.

Redline needs:

* headless operation
* appliance compatibility
* predictable typed operations
* scan-level authorization rather than interactive prompts for every check
* support on minimal Linux distributions

Polkit may later govern installation or enabling of the helper, but it will not replace the bounded helper protocol.

### Alternative H: Use one privileged helper per subsystem

Examples would include separate helpers for systemd, Docker, filesystems, and networking.

This would reduce the authority of each helper but increase:

* packaging complexity
* service lifecycle complexity
* version coordination
* socket management
* memory use
* implementation overhead

A single tightly constrained helper is selected for v0.1.

The decision should be revisited if the operation catalog grows enough that independent helpers would materially reduce risk.

### Alternative I: Run a privileged container with the host root mounted

This is rejected as a generic Linux design.

A privileged container with host mounts would retain broad host authority while obscuring rather than eliminating the privilege boundary.

## Consequences

### Positive consequences

* Most Redline code remains outside the root trust boundary.
* Safe Scan requires no privileged component.
* A compromised web API cannot directly execute arbitrary root commands.
* Privileged access is explicit and observable.
* Deep-scan operations can be independently reviewed.
* Platform-native providers can replace helper operations without changing probes.
* Helper failure degrades coverage rather than taking down Redline.
* Network-facing protocol logic remains unprivileged.
* Docker and journal access can be narrowed before data reaches the daemon.
* The helper can enforce bounds even against a compromised daemon.
* Restricted platforms can omit the helper entirely.
* The system preserves a path toward stronger future sandboxing.

### Negative consequences

* Packaging requires an additional binary and service.
* Deep scans require more installation and configuration work.
* The local protocol must be versioned and tested.
* Some privileged resources require root-owned policy entries.
* Dynamic resource discovery is more complex when opaque handles are used.
* The helper becomes security-sensitive code requiring stricter review.
* Debugging cross-process failures is more involved than direct system calls.
* Some users may perceive explicit privilege setup as inconvenient.
* The first implementation will support fewer deep-scan operations than an unrestricted root process could.

### Neutral consequences

* The helper may run persistently or later use socket activation.
* Umbrel and StartOS may provide equivalent evidence through platform-granted capabilities.
* Some unprivileged Linux installations may expose enough information that the helper adds little value.
* Root-owned configuration remains necessary for certain protected targets.
* The helper’s existence does not imply that every scan will use it.

## Risks and mitigations

### Risk: The helper evolves into a generic root agent

**Mitigations:**

* Maintain a closed operation catalog.
* Require an architectural review for every new operation family.
* Reject generic command, file, Docker, D-Bus, and journal proxy operations.
* Keep operation responses typed and minimal.
* Track the helper’s total authority in security documentation.
* Split the helper if unrelated authority domains grow substantially.

### Risk: A compromised daemon abuses legitimate operations

**Mitigations:**

* Assume the daemon UID can issue any enabled request.
* Enforce bounds and rate limits in the helper.
* Require configured targets or helper-issued handles.
* Exclude secret-bearing fields at the source.
* Avoid operations that can mutate state.
* Keep the helper network-isolated.
* Log minimal operation audit events.

### Risk: Resource selectors can be raced or redirected

**Mitigations:**

* Prefer opaque helper-issued handles.
* Use root-owned configured resource aliases.
* Canonicalize paths.
* Avoid symbolic-link following.
* Use file-descriptor-based operations where practical.
* Revalidate resource type at access time.
* Invalidate handles when identity changes.

### Risk: Docker inspection exposes secrets

**Mitigations:**

* Never return raw Docker inspect output.
* Exclude environment variables and command arguments by default.
* Return an explicit typed field allowlist.
* Treat Docker access as privileged.
* Add canary-secret tests to container responses.

### Risk: Journal access exposes sensitive data

**Mitigations:**

* Restrict reads to approved services.
* Enforce time, record, and byte bounds.
* Return only approved journal fields.
* Apply first-stage secret filtering inside the helper.
* Mark returned text as sensitive until final redaction.
* Never persist the unprocessed response.

### Risk: The helper becomes a denial-of-service target

**Mitigations:**

* Rate-limit callers.
* Limit concurrency.
* Bound enumeration and output.
* Enforce deadlines.
* Reject oversized requests before decoding deeply.
* Keep expensive operations disabled from continuous monitoring by default.

### Risk: Users assume Deep Scan is safe merely because it is read-only

Read-only access can still expose sensitive host data.

**Mitigations:**

* Classify operations by sensitivity.
* Minimize returned fields.
* Surface the classes of evidence Deep Scan will inspect.
* Keep privileged policy root-owned.
* Preserve local-only processing.
* Apply final report redaction independently.

### Risk: The daemon silently loses deep coverage after an upgrade

**Mitigations:**

* Perform protocol negotiation.
* Expose helper compatibility in scan metadata.
* Mark missing operations as unavailable capabilities.
* Show coverage loss in the UI.
* Never silently reinterpret unavailable deep evidence as pass.

## Testing strategy

### Protocol tests

The helper protocol test suite must cover:

* compatible and incompatible versions
* malformed frames
* oversized frames
* unknown operations
* unknown operation versions
* duplicate fields
* missing required fields
* expired deadlines
* mismatched request IDs
* truncated responses
* connection cancellation
* helper restart during a request

### Authentication tests

Tests must verify:

* the configured daemon UID is accepted
* an unrelated UID is rejected
* group membership alone does not bypass the UID check
* caller-provided UID fields are ignored
* socket permissions do not replace peer-credential verification
* a root-owned policy change is required to change the accepted UID

### Authorization tests

For every operation:

* approved resources succeed
* unknown handles fail
* handles of the wrong type fail
* expired handles fail
* unauthorized configured targets fail
* parameter bounds are enforced
* unsupported combinations fail closed

### Abuse tests

The helper must be tested against:

* high request rates
* maximum concurrent connections
* repeated expensive operations
* oversized journal requests
* path traversal attempts
* symbolic-link replacement
* invalid service names
* invalid container identifiers
* malformed subprocess output
* subprocess timeouts
* secret canaries embedded in service metadata and logs

### Capability integration tests

Tests must verify that:

* helper absence produces unavailable capabilities
* helper policy denial produces explicit unknown findings
* helper-backed and platform-native providers produce equivalent normalized observations
* helper failure cannot create a target failure finding
* privileged provenance appears in observation metadata
* no raw helper response enters persistence

### Security regression tests

A security regression suite will assert that the helper API cannot:

* write a file
* execute an arbitrary command
* start or stop a service
* create or exec into a container
* access an unconfigured protected path
* make an external network connection
* return container environment variables
* return RPC credentials
* return unrestricted journal data

## Validation criteria

ADR-004 will be considered successfully implemented when:

1. `redlined` runs under a dedicated non-root UID.
2. Safe Scan works with no helper installed.
3. Deep Scan detects and negotiates with a compatible helper.
4. The helper listens only on a local Unix-domain socket.
5. The helper verifies the caller through peer credentials.
6. The helper remains safe when the daemon UID is assumed compromised.
7. The helper exposes no generic command or file API.
8. Root-owned policy controls protected targets and enabled operation families.
9. The web UI cannot expand helper authority.
10. Every helper request has an operation version, deadline, and size bound.
11. Every operation returns a typed minimal response.
12. Docker environment variables and raw inspect data cannot be returned.
13. Journal access is service-scoped, time-bounded, count-bounded, and byte-bounded.
14. The helper performs no external network access.
15. A helper failure cannot crash the daemon.
16. A missing or denied helper capability produces explicit uncertainty.
17. Observations record privileged-provider provenance.
18. Raw helper responses are never persisted.
19. The daemon cannot directly access the host Docker socket by default.
20. The helper cannot start, stop, restart, or modify a service.
21. The helper cannot write to inspected targets.
22. Service hardening restrictions are applied and tested.
23. Incompatible daemon and helper versions fail closed.
24. Abuse tests demonstrate effective rate and resource limits.
25. The initial systemd and filesystem operations pass an independent security review.

## Reconsideration triggers

This ADR should be revisited if:

1. The helper operation catalog grows beyond a small auditable surface.
2. Docker, filesystem, systemd, and network inspection require materially different authority domains.
3. A privileged operation must modify host state.
4. Automated remediation becomes a product requirement.
5. A supported platform cannot provide Unix peer credentials.
6. StartOS, Umbrel, or another appliance requires a different privilege architecture.
7. Root-owned target registration creates unacceptable usability problems.
8. Opaque handles prove too complex or unreliable for real deployments.
9. Linux security mechanisms make a non-root helper with narrower group access materially safer than a root helper.
10. Systemd sandboxing cannot constrain the helper without breaking required operations.
11. External security review identifies a safer practical architecture.
12. A remote-agent architecture is introduced.
13. The helper requires network access.
14. A third-party extension needs privileged capabilities.
15. The daemon and helper can no longer maintain a stable compatibility window.

A reconsideration trigger does not permit quietly broadening the existing helper API. Material changes to the privilege boundary require a new ADR.

## Final decision statement

SATOSHI//REDLINE will run its primary daemon, diagnostic engine, protocol clients, API, persistence, and reporting system without root privileges.

Optional deep-scan access will be isolated in a separate root-owned helper that exposes a closed, versioned, local, typed, bounded, read-only operation catalog.

The helper will be designed under the assumption that the unprivileged daemon may be compromised. Its safety will therefore come from the narrowness of the authority it exposes, not from trusting the caller.

When privileged evidence is unavailable, denied, or incompatible, Redline will continue the scan and report explicit uncertainty rather than elevating the daemon or pretending the missing check passed.

The central rule established by this ADR is:

> Privilege belongs behind the smallest possible interface, and no diagnostic convenience justifies turning Redline into a general-purpose root agent.
