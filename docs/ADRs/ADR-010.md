# ADR-010: Platform Packages Wrap, but Never Fork, the Diagnostic Engine

* **Date:** 2026-07-30
* **Decision owners:** SATOSHI//REDLINE maintainers
* **Depends on:**

  * ADR-001 — Use a Go Modular Monolith for the Diagnostic Backend
  * ADR-002 — Use Capability-Based, Composable Platform Adapters
  * ADR-003 — Separate Observations, Findings, and Diagnoses
  * ADR-004 — Run the Main Daemon Unprivileged and Isolate Deep-Scan Access in an Optional Privileged Helper
  * ADR-005 — Do Not Persist Raw Logs or Protocol Responses
  * ADR-006 — Version External API and Report Schemas Independently from Internal Models
  * ADR-007 — Compile First-Party Probes into the Redline Binary for v0.1
  * ADR-008 — Require Explicit Reasons and Coverage Semantics for Unknown Results
  * ADR-009 — Keep Core Execution Local and Prohibit Outbound Telemetry by Default
* **Scope:**

  * Generic Linux packaging
  * Docker packaging
  * Umbrel packaging
  * StartOS 0.4 packaging
  * Platform bootstrap code
  * Platform configuration translation
  * Release and artifact composition
  * Platform-specific defaults
  * Cross-platform diagnostic equivalence
  * Package conformance testing
* **Excluded from scope:**

  * Exact package-store submission procedures
  * Software-update transport
  * Code-signing infrastructure
  * Reproducible-build implementation details
  * Mobile application architecture
  * Hosted monitoring services
  * Third-party downstream distributions

## Context

SATOSHI//REDLINE is intended to run in several environments with materially different packaging, lifecycle, networking, storage, and permission models.

Initial targets include:

* Generic Debian, Ubuntu, and Raspberry Pi OS systems
* Native systemd installations
* Docker and Docker Compose installations
* UmbrelOS applications
* StartOS 0.4 packages

These platforms require different integration work.

A generic Linux package may need:

* native binaries
* systemd service units
* a dedicated service account
* configuration files
* runtime directories
* optional privileged-helper installation
* package-manager scripts
* host filesystem paths

A Docker package may need:

* a multi-architecture image
* an entrypoint
* volume declarations
* health checks
* environment-to-configuration mapping
* container networking
* optional connection to host services

An Umbrel package may need:

* an application manifest
* Docker Compose configuration
* dependency declarations
* platform-provided Bitcoin RPC bindings
* application-network configuration
* Umbrel UI metadata
* persistent application storage

A StartOS 0.4 package may need:

* a TypeScript package definition
* daemon declarations
* service interfaces
* dependency bindings
* health checks
* configuration actions
* StartOS-specific storage and network declarations
* an `.s9pk` artifact

These platform differences are real and cannot be hidden behind identical package files.

They do not, however, justify different diagnostic engines.

If each platform package develops its own diagnostic behavior, Redline will quickly split into several products that merely share a name.

Examples of dangerous divergence include:

* Umbrel declaring a Bitcoin node healthy using only container state
* StartOS using a platform health flag instead of protocol evidence
* Generic Linux applying different Electrum lag thresholds
* Docker omitting unknown findings that the native package displays
* a platform package changing root-cause ranking
* one package retaining raw logs for debugging
* one package adding telemetry
* one package renaming finding codes
* a package-specific UI calculating health independently
* platform maintainers applying unreviewed engine patches
* different package releases shipping different probe catalogs under the same Redline version

Such divergence would violate the core product promise.

A finding such as:

```text
electrum.chain.sync-lag = failure
```

must mean the same thing regardless of whether the evidence came from:

* a native Linux TCP connection
* an Umbrel application-network binding
* a StartOS dependency interface
* a manually configured Docker endpoint

The available evidence may differ.

The resulting coverage may differ.

The diagnostic meaning must not differ.

The project therefore needs a strict boundary between:

1. The diagnostic engine
2. Platform capability integration
3. Platform bootstrap configuration
4. Platform lifecycle packaging
5. Platform-specific presentation guidance

Without this boundary, packaging work will become a hidden path for changing diagnostic semantics.

## Decision

All official SATOSHI//REDLINE platform distributions will package the same diagnostic engine and diagnostic semantics.

Platform packages may wrap, configure, launch, expose, and supply capabilities to the engine.

They may not fork or reimplement it.

The following will remain shared across every official platform package:

* domain model
* component model
* observation schemas
* finding codes
* diagnosis codes
* probe implementations
* evaluator implementations
* correlation rules
* status semantics
* unknown-reason semantics
* coverage aggregation
* default diagnostic thresholds
* report schemas
* API schemas
* privacy rules
* redaction rules
* network-policy rules
* recommendation identities
* embedded web application
* CLI behavior where the CLI is included

The following may differ by platform:

* installation format
* process supervision
* filesystem locations
* persistence locations
* platform adapter activation
* available capability providers
* secret-reference resolution
* service endpoint discovery
* listener exposure
* platform health integration
* packaging metadata
* platform-specific setup screens
* platform-specific remediation wording
* default scan-profile selection when required by platform capability limits

A platform package may change **how evidence is obtained**.

It may not change **what the evidence means**.

The preferred release process will build one canonical `redlined` binary per operating-system and CPU architecture and reuse that exact binary across compatible official packages.

For example:

```text
linux-amd64/redlined
linux-arm64/redlined
```

The same ARM64 binary should, where platform constraints permit, be used in:

* ARM64 native Linux packages
* the ARM64 Docker image
* the ARM64 Umbrel package
* the ARM64 StartOS package

If a platform requires a distinct binary build, that build must be produced from the same source revision and must expose an identical diagnostic semantic manifest unless the difference is explicitly documented and reviewed.

The central decision is:

> Official platform packages may adapt Redline to the environment, but they may not create a platform-specific interpretation of system health.

## Decision drivers

The decision drivers, in priority order, are:

1. Preserve one meaning for every Redline finding and diagnosis.
2. Avoid duplicate platform-specific diagnostic implementations.
3. Ensure platform restrictions reduce coverage rather than alter truth.
4. Allow platform packaging to evolve independently of diagnostic logic.
5. Keep bug fixes and new probes available to every platform.
6. Prevent platform stores or vendors from silently modifying privacy behavior.
7. Make cross-platform reports comparable.
8. Keep release and support complexity manageable for a small team.
9. Preserve one testable core product.
10. Permit legitimate platform-native integration without weakening architectural boundaries.

## Terminology

### Diagnostic engine

The diagnostic engine includes:

* component inventory
* capability resolution
* scan planning
* probe scheduling
* probes
* observation normalization
* evaluators
* findings
* correlation rules
* diagnoses
* coverage aggregation
* incident logic
* reporting
* persistence
* API
* embedded local web interface

The engine is primarily implemented by `redlined` and its shared Go packages.

### Platform adapter

A platform adapter discovers components and registers platform-specific capability providers under ADR-002.

Examples include:

```text
linux-host
systemd
docker
umbrel
startos-0.4
```

A platform adapter is part of the engine’s integration layer.

It does not redefine diagnostic semantics.

### Platform bootstrap

Platform bootstrap code translates packaging-provided information into Redline’s stable configuration and capability-binding model.

Examples include:

* environment-variable parsing
* StartOS dependency-interface import
* Umbrel-injected Bitcoin RPC binding
* filesystem-path selection
* platform identity detection
* persistent-storage initialization

Bootstrap code runs before or during engine initialization.

It must not emit findings or diagnoses.

### Platform wrapper

A platform wrapper is the packaging and lifecycle layer surrounding the engine.

Examples include:

* a systemd service unit
* Docker entrypoint
* Umbrel manifest and Compose file
* StartOS TypeScript package code

A wrapper may launch and supervise Redline.

It may not implement a second diagnostic engine.

### Semantic fork

A semantic fork exists when two official packages using the same product identity can produce different diagnostic interpretations from equivalent normalized evidence.

Examples include:

* different thresholds
* different finding statuses
* different unknown behavior
* different root-cause ranking
* different code meanings
* different evidence requirements
* different redaction behavior

A semantic fork is prohibited.

### Packaging revision

A packaging revision identifies changes to the wrapper that do not change the diagnostic engine.

Examples include:

* correcting a systemd unit
* changing an icon
* updating a StartOS manifest
* adjusting a volume path
* fixing an Umbrel dependency declaration

Packaging revisions remain distinct from the Redline engine version.

## Architectural boundary

The platform architecture will follow this direction:

```text
Platform package
      ↓
Platform bootstrap
      ↓
Platform adapter and capability providers
      ↓
Shared diagnostic engine
      ↓
Shared observations, findings, and diagnoses
```

The following reverse dependency is prohibited:

```text
Probe or evaluator
      ↓
Umbrel package implementation
```

or:

```text
Correlation rule
      ↓
StartOS TypeScript wrapper
```

Platform wrappers do not become dependencies of the diagnostic engine.

## Canonical engine artifact

### Build once, package many times

The preferred official release pipeline will:

1. Select one source revision.
2. Generate schemas and diagnostic catalogs.
3. Run the full test suite.
4. Build canonical Linux AMD64 and ARM64 binaries.
5. Produce checksums and build metadata.
6. Embed or attach the same binaries to platform packages.
7. Verify the packaged binary against the canonical checksum.
8. Run platform-specific conformance tests.
9. Publish the package with both engine and packaging identities.

Conceptually:

```text
source revision
      ↓
canonical binaries
      ├── tarball
      ├── Debian package
      ├── OCI image
      ├── Umbrel package
      └── StartOS package
```

A package build should not casually recompile the engine from a different source state.

### Architecture-specific artifacts

AMD64 and ARM64 binaries are expected to differ at the machine-code level.

They must nevertheless expose the same:

* probe catalog
* evaluator catalog
* correlation-rule catalog
* schema versions
* default thresholds
* recommendation catalog
* diagnostic profiles
* feature policy

Architecture-specific behavior must not alter diagnostic meaning.

If an operating-system API is unavailable on one architecture, the affected capability becomes unavailable and coverage changes accordingly.

The evaluator does not change.

### Platform-specific builds

A distinct platform build is permitted only when required by:

* operating-system ABI
* platform packaging restrictions
* unavailable system calls
* required static or dynamic linking
* platform SDK integration
* security hardening
* artifact-size constraints

A distinct build must still come from the same source revision and pass semantic-manifest equivalence tests.

Build tags must not be used to silently alter:

* finding thresholds
* status rules
* correlation logic
* privacy policy
* telemetry policy
* report semantics

## Semantic manifest

Every official engine artifact will expose a machine-readable semantic manifest.

The manifest will identify the diagnostic behavior included in the build.

Conceptually:

```json
{
  "engine_version": "0.1.0",
  "source_revision": "abc123...",
  "api_versions": [1],
  "report_versions": [1],
  "probe_catalog_digest": "sha256:...",
  "evaluator_catalog_digest": "sha256:...",
  "correlation_catalog_digest": "sha256:...",
  "observation_schema_digest": "sha256:...",
  "finding_registry_digest": "sha256:...",
  "diagnosis_registry_digest": "sha256:...",
  "recommendation_catalog_digest": "sha256:...",
  "defaults_digest": "sha256:...",
  "scan_profile_digest": "sha256:...",
  "privacy_policy_version": "1",
  "network_policy_version": "1"
}
```

The semantic manifest will be available through:

* CLI version output
* `/api/v1/meta`
* report producer metadata
* release artifacts
* platform conformance tests

Two official packages claiming the same engine version must have matching semantic manifests unless a documented exception has been approved.

A packaging revision does not change the semantic manifest.

### Semantic-manifest purpose

The manifest allows maintainers and users to determine whether:

* an Umbrel package contains the same diagnostic logic as the native package
* a StartOS wrapper changed only packaging
* an architecture-specific build includes the expected probes
* a platform store rebuilt the binary unexpectedly
* a support report was produced by an official semantic configuration

The manifest is not a substitute for binary signatures or reproducible builds.

It records semantic composition.

## Platform wrapper responsibilities

A platform wrapper may perform the following functions.

### Installation

* place binaries
* create directories
* define persistent storage
* install service definitions
* configure users and groups
* install or omit the optional privileged helper
* expose packaging metadata
* declare dependencies

### Startup

* select configuration paths
* provide platform identity
* pass platform bootstrap references
* initialize persistent directories
* bind the local API through the platform
* select the supported platform adapter
* define logging destinations

### Configuration translation

* convert platform configuration into Redline’s stable bootstrap model
* provide secret references
* provide service-interface bindings
* provide component aliases
* provide declared dependency relationships
* select a supported scan profile
* configure storage locations

### Lifecycle integration

* start and stop the daemon
* restart the daemon after package upgrades
* expose process health to the platform
* handle backups of approved persistent data
* preserve database and configuration state
* invoke engine-owned migrations

### Presentation integration

* provide application title
* icon
* package description
* platform menu integration
* local UI link
* platform-specific installation instructions

These responsibilities surround the engine.

They do not reproduce it.

## Prohibited wrapper responsibilities

A platform wrapper must not:

* evaluate Bitcoin synchronization
* compare Bitcoin and Electrum heights
* determine DATUM template freshness
* calculate component health
* emit Redline findings
* emit Redline diagnoses
* suppress unknown findings
* redefine severity
* change confidence
* rank root causes
* parse raw logs into health states
* produce an alternative Redline report
* modify report schemas
* upload reports
* add telemetry
* alter privacy restrictions
* introduce executable probes
* change core thresholds
* bypass the capability registry
* invoke the privileged helper directly for diagnostics
* give the web UI an alternative health model
* modify canonical finding or diagnosis wording in a way that changes meaning

A platform-native health check is allowed only to describe Redline’s own service availability.

For example:

```text
Redline daemon is accepting local API requests.
```

It may not claim:

```text
The Bitcoin stack is healthy.
```

unless that statement comes from the shared Redline diagnostic engine.

## Bootstrap contract

Platform packages will communicate with the engine through a stable bootstrap contract.

The contract may contain:

```go
type BootstrapConfig struct {
    Platform         PlatformDescriptor
    Storage          StorageBinding
    Listener         ListenerBinding
    SecretReferences []SecretReference
    ServiceBindings  []ServiceBinding
    ComponentHints   []ComponentHint
    AdapterSettings  []AdapterSetting
    ScanProfile      ScanProfileID
}
```

The bootstrap contract will not contain:

* finding results
* diagnosis results
* platform-computed health
* raw credentials
* raw logs
* arbitrary commands
* scripts
* arbitrary Go objects
* unrestricted provider documents

### Secret references

A wrapper may provide a reference to a platform-managed secret.

It must not copy that secret into:

* command-line arguments
* package metadata
* reports
* logs
* observations
* platform health responses

The relevant provider resolves the secret under ADR-005.

### Component hints

A wrapper may state:

```text
A Bitcoin service is available through binding X.
```

It may not state:

```text
Bitcoin is synchronized.
```

The first is inventory and access information.

The second is a finding that must be produced by the engine.

## Platform-specific defaults

### Shared diagnostic defaults

Diagnostic thresholds and semantic defaults will be owned by the engine.

Examples include:

* maximum acceptable Bitcoin block age
* acceptable Electrum block lag
* filesystem warning thresholds
* restart-loop thresholds
* DATUM template-age thresholds
* observation-freshness limits
* correlation confidence rules

Platform packages may not redefine these defaults independently.

### Platform scan profiles

A platform may select a default scan profile appropriate to available capabilities.

For example:

```text
linux-native-safe
linux-native-deep
umbrel-safe
startos-safe
docker-safe
```

These profiles may differ in:

* which checks are selected
* which capabilities are expected
* which checks are required, optional, or informational
* whether privileged operations are available
* whether external network checks are enabled

They may not change the meaning of a selected finding.

For example:

```text
electrum.chain.sync-lag
```

must use the same evaluator and threshold configuration unless the user has explicitly configured an approved threshold override.

A platform profile may omit a check because the necessary capability cannot exist.

It may not replace the check with a weaker platform-specific pass.

### Profile transparency

Every scan must record:

* profile ID
* profile version
* selected checks
* requirement level
* unavailable capabilities
* platform-specific exclusions

This ensures that reduced platform coverage is visible.

## Platform-specific recommendations

Diagnostic meaning remains shared, but remediation instructions may need platform-specific presentation.

For example, the finding:

```text
Bitcoin service is repeatedly restarting.
```

may have different safe investigation steps.

Generic Linux:

```text
Inspect the bitcoind systemd unit and bounded journal history.
```

Umbrel:

```text
Review the Bitcoin app status and logs through the Umbrel interface.
```

StartOS:

```text
Open the Bitcoin service in StartOS and review its health and log interface.
```

This variation is permitted under the following rules:

1. The canonical finding and diagnosis remain unchanged.
2. The recommendation uses a stable recommendation ID.
3. The platform variant changes instructions, not asserted facts.
4. Instructions remain non-destructive by default.
5. The variant must not claim evidence unavailable to the engine.
6. The report records the recommendation ID and optional renderer variant.
7. Missing platform guidance falls back to generic safe guidance.

Platform wrappers themselves should not generate recommendations dynamically.

Recommendation variants should remain first-party engine resources selected using platform metadata.

## Embedded web interface

The same compiled web application will be embedded in or served by the official Redline engine across platforms.

A platform package may frame or link to that interface.

It must not maintain a separate platform-specific dashboard that independently interprets diagnostic data.

Permitted platform customization includes:

* application icon
* outer navigation
* package title
* platform launch URL
* limited platform-aware setup guidance
* platform-native theme integration where it does not alter meaning

Prohibited customization includes:

* hiding unknown states
* recalculating health
* removing evidence
* changing status colors in a way that reverses meaning
* replacing findings with platform health flags
* adding analytics
* loading remote UI assets
* exposing raw logs outside Redline’s evidence model

## Generic Linux package

The generic Linux distribution is the reference full-capability platform.

It may include:

```text
redlined
redline
redline-privd
systemd units
default configuration
root-owned helper policy
dedicated service user
tmpfiles configuration
log-rotation policy where necessary
```

The Linux package may provide:

* systemd capability provider
* filesystem capability provider
* Docker provider
* privileged-helper provider
* native persistent storage

The Linux wrapper must not contain diagnostic scripts executed outside the engine.

Package maintainer scripts may:

* create users
* create directories
* apply permissions
* migrate packaging paths
* restart services after upgrade

They may not:

* call Bitcoin RPC to assess health
* inspect logs and cache findings
* generate reports
* change evaluator thresholds
* upload installation data

## Docker package

The Docker distribution will contain the same engine artifact appropriate to the image architecture.

The container entrypoint may:

* translate environment settings into bootstrap configuration
* validate volume mounts
* initialize writable directories
* select the Docker-safe scan profile
* launch `redlined`

It must not:

* run shell-based diagnostics
* parse Docker metadata into findings
* inject a different probe catalog
* mount the host root automatically
* require `--privileged`
* mount the Docker socket by default
* expose the local API publicly by default
* add container analytics

### Container health check

The OCI health check may verify:

```text
The Redline daemon responds on its local health endpoint.
```

It must not use overall Bitcoin-stack health as the container-health result.

A diagnosed Bitcoin failure must not cause the Redline diagnostic container itself to be restarted continuously.

### Docker host access

When host Docker inspection is enabled, it must follow ADR-004.

Mounting the Docker socket directly into `redlined` remains prohibited by default.

## Umbrel package

The Umbrel package will be a thin application wrapper around the canonical Redline engine.

It may include:

* Umbrel manifest
* Docker Compose file
* application metadata
* declared service dependencies
* injected Bitcoin RPC binding
* application-network configuration
* persistent app-data volume
* Redline UI exposure

The Umbrel bootstrap layer may translate platform-provided values into:

* Bitcoin RPC secret reference
* Bitcoin endpoint binding
* network mode
* component hints
* storage location
* platform descriptor

It must not contain separate Bitcoin, Electrum, or mining-health logic.

### Umbrel restrictions

When host access is unavailable, Redline will report:

```text
unknown
```

with an appropriate platform-restriction reason.

The Umbrel package must not substitute:

```text
container running = component pass
```

for missing protocol or host evidence.

### Umbrel dependencies

An Umbrel dependency declaration establishes a possible relationship and access path.

The engine still determines whether:

* the service responds
* the service is synchronized
* the dependency is behaving correctly

Platform dependency metadata is not itself a pass finding.

## StartOS 0.4 package

The StartOS package will use a thin TypeScript layer to satisfy StartOS package requirements.

The TypeScript package may define:

* daemons
* interfaces
* dependency imports
* configuration actions
* package health checks
* backups
* storage
* StartOS service metadata
* lifecycle hooks

The Go engine will continue to perform all Redline diagnostics.

### StartOS bindings

The StartOS layer may resolve runtime service interfaces and provide them to Redline through the bootstrap contract.

The engine must not assume static ports when StartOS provides dynamic bindings.

### StartOS health checks

A StartOS health check may verify:

```text
The Redline service is running and its local API responds.
```

It may not reduce the entire diagnosed stack to a StartOS package health flag.

Redline findings remain inside the Redline UI, API, CLI, and reports unless a later integration explicitly projects selected status summaries.

### TypeScript boundary

StartOS TypeScript code must not:

* duplicate probes
* duplicate evaluators
* parse Bitcoin RPC into findings
* generate diagnoses
* maintain a separate finding registry
* write Redline reports
* alter privacy policy
* add remote analytics

Its purpose is package integration, not diagnostic interpretation.

## Package and engine versioning

Every official distribution will identify at least:

```text
engine version
engine source revision
semantic manifest digest
platform package type
platform package revision
platform adapter version
```

Example:

```text
Engine version: 0.1.0
Engine revision: abc123
Semantic manifest: sha256:...
Package: startos-0.4
Package revision: 3
```

### Engine version

Changes when the Redline product release changes.

### Packaging revision

Changes when only platform packaging changes.

Examples:

* corrected icon
* fixed service dependency
* changed volume ownership
* repaired startup configuration
* updated package metadata

A packaging revision must not claim a new engine version unless the engine artifact actually changed.

### Adapter version

A platform adapter may have its own version for provenance.

Changing adapter behavior may affect:

* discovery
* endpoint binding
* capability availability
* provenance
* coverage

It must not affect the evaluator’s interpretation of equivalent normalized observations.

## Persistence and migrations

The engine owns the diagnostic database schema and migrations.

Platform wrappers may:

* provide the database path
* preserve the data directory
* invoke the new engine version
* back up approved persistent data
* stop the service before a required migration

They must not:

* edit SQLite tables directly
* rewrite observations
* rewrite findings
* rewrite diagnoses
* create platform-specific schema variants
* export the database as a report
* retain raw upgrade logs containing secrets

### Configuration migrations

Platform wrappers may migrate packaging-specific configuration into the stable bootstrap model.

Semantic configuration migrations, such as renamed evaluator thresholds, must be owned by the engine.

## Official package conformance

An official package is conformant only when it satisfies all core ADRs.

A platform package must not be labeled an official SATOSHI//REDLINE distribution if it:

* changes diagnostic semantics
* adds telemetry
* persists raw logs
* exposes destructive actions
* runs the full daemon as root without an approved exception
* changes report schemas
* loads unapproved runtime probes
* suppresses unknown results
* changes privacy defaults
* requires a cloud account
* replaces the embedded UI with an incompatible diagnostic implementation

### Conformance declaration

Each official package will include a conformance declaration containing:

```text
engine identity
semantic manifest
enabled adapters
default scan profile
listener policy
privileged-helper availability
network destination policy
package revision
known platform limitations
```

This declaration may be exposed through `/api/v1/meta`.

## Diagnostic equivalence

### Equivalent evidence

When two platform installations produce equivalent normalized observations for the same component graph, they must produce equivalent:

* findings
* statuses
* severities
* confidence
* diagnoses
* root-cause classifications
* coverage outcomes
* recommendation identities

Platform-specific rendered remediation details may differ.

### Different evidence

Platforms may legitimately produce different results when evidence differs.

Example:

Generic Linux:

```text
Bitcoin RPC reachable
Bitcoin synchronized
Filesystem nearly full
Restart loop confirmed
```

Umbrel:

```text
Bitcoin RPC reachable
Bitcoin synchronized
Filesystem state unknown
Restart history unknown
```

These scans may have different diagnoses because Linux supplied more evidence.

This is not semantic divergence.

It is evidence-driven coverage difference.

### Prohibited equivalence shortcut

A platform package must not force equivalent output by pretending missing evidence exists.

Cross-platform consistency means consistent reasoning, not identical colors regardless of access.

## Testing strategy

### Shared semantic fixture tests

The same normalized observation fixtures will be evaluated across all platform package test harnesses.

Given identical:

* observations
* findings
* graph snapshot
* evaluator configuration
* correlation configuration

every package must produce identical canonical diagnostic output.

### Capability-difference tests

Tests will verify that platform capability differences produce:

* explicit unknown findings
* correct coverage changes
* unchanged evaluator semantics
* no replacement platform-specific pass

### Artifact-verification tests

Packaging CI will verify:

* packaged binary checksum
* engine source revision
* semantic-manifest digest
* expected architecture
* embedded UI digest
* report-schema digest
* probe-catalog digest

### Platform smoke tests

Each package must demonstrate:

* installation
* first startup
* persistent storage
* local UI access
* Safe Scan
* report export
* upgrade
* rollback behavior where supported
* package removal without deleting user data unexpectedly

### Cross-platform golden tests

Representative scenarios will run through Linux, Docker, Umbrel, and StartOS harnesses.

Scenarios include:

```text
Bitcoin healthy
Bitcoin RPC unavailable
Bitcoin synchronized with Electrum lag
disk pressure causing node instability
DATUM disconnected from Bitcoin RPC
restricted platform with incomplete host evidence
ambiguous service dependency
privileged helper unavailable
```

Canonical findings and diagnoses must match wherever evidence matches.

### Privacy-conformance tests

Every package must verify:

* no telemetry
* no remote frontend assets
* no raw-data persistence
* no automatic report upload
* no package-specific debug capture
* no forbidden identifiers in reports
* no external update request by default

### Listener tests

Every package must verify its intended UI and API exposure.

A platform wrapper must not accidentally bind the API more broadly than documented.

### Upgrade tests

Upgrade tests must verify:

* engine-owned database migrations
* preserved report readability
* preserved configuration bindings
* packaging-revision upgrades without semantic changes
* engine-version upgrades with expected manifest changes
* old reports remain readable

## Architecture enforcement

Automated checks should enforce that:

1. Platform wrapper directories do not contain evaluator or correlation implementations.
2. StartOS TypeScript code does not define finding or diagnosis codes.
3. Umbrel packaging contains no diagnostic shell scripts.
4. Docker entrypoints do not execute diagnostic commands.
5. Platform packages reuse canonical engine artifacts where supported.
6. All official packages expose the semantic manifest.
7. Packages claiming the same engine version have compatible semantic manifests.
8. Platform profiles cannot override shared evaluator defaults silently.
9. The embedded UI digest matches the official engine release.
10. Platform-native health checks assess Redline service health only.
11. Platform packages do not add telemetry endpoints.
12. Wrappers cannot import or modify persistence records directly.
13. Platform adapters cannot emit findings or diagnoses.
14. Reports include both engine and package provenance.
15. Platform-specific recommendation variants retain stable recommendation IDs.
16. Core probes contain no packaging imports.
17. API and report schemas remain identical across official packages.
18. Package-specific configuration cannot introduce executable diagnostic logic.
19. The same normalized evidence produces the same canonical findings in every harness.
20. Reduced capability coverage never becomes an artificial pass.

## Release pipeline

The intended release pipeline is:

```text
1. Freeze source revision
2. Generate schema and catalog artifacts
3. Run unit, integration, privacy, and architecture tests
4. Build canonical AMD64 and ARM64 engine binaries
5. Generate semantic manifests
6. Verify cross-architecture semantic equivalence
7. Build generic Linux artifacts
8. Build multi-architecture OCI image
9. Build Umbrel package
10. Build StartOS package
11. Verify packaged engine checksums
12. Run platform conformance suites
13. Generate package provenance
14. Publish artifacts
```

Platform packages should not be released from unreviewed branches that contain engine modifications absent from the main Redline release.

## Downstream modifications

Third parties may fork Redline under the applicable software license.

A downstream fork is not prohibited by this ADR.

It must not be represented as an official SATOSHI//REDLINE package unless it passes the official release and conformance process.

A downstream distribution that changes the engine should disclose:

* source revision
* modifications
* semantic-manifest difference
* package maintainer
* diagnostic compatibility status

The official project should not accept bug reports based on an unidentified downstream semantic fork as though it were the canonical engine.

### Platform-store rebuilds

Some application stores may rebuild packages.

Where possible, official publishing should provide:

* source revision
* expected semantic manifest
* expected catalog digests
* build instructions
* checksums of canonical artifacts

A rebuilt package may still be conformant if its semantic manifest matches and it passes platform conformance.

Byte identity is preferred but semantic identity is the minimum architectural requirement.

## Emergency platform fixes

A platform-specific packaging defect may require an urgent package revision.

Examples:

* incorrect volume ownership
* broken StartOS interface declaration
* Umbrel network binding failure
* systemd service startup ordering
* Docker health-check error

Such a fix may be released without changing the engine version when the engine binary is unchanged.

An urgent diagnostic-engine fix must be released as an engine update and then propagated to every affected official package.

It must not remain as an indefinite platform-only patch.

A temporary platform-only engine patch, if absolutely unavoidable, requires:

* explicit maintainer approval
* distinct engine build identity
* changed semantic manifest if semantics differ
* documented divergence
* a tracked upstream merge
* a defined expiration
* no claim of identical engine behavior

This is an exceptional failure mode, not a normal workflow.

## Alternatives considered

### Alternative A: Separate diagnostic implementation for each platform

This is rejected.

It would duplicate logic and cause unavoidable semantic drift.

### Alternative B: Share schemas but allow platform-specific evaluators

This is rejected.

Identical JSON shapes do not guarantee identical meaning.

Thresholds, evidence requirements, and correlation rules must also remain shared.

### Alternative C: Let platform-native health checks replace Redline probes

This is rejected.

Platform health checks frequently measure process or package state rather than application behavior across the stack.

They may be evidence providers, not final diagnostic authorities.

### Alternative D: Maintain a long-lived engine fork for Umbrel

This is rejected.

Umbrel-specific access belongs in the adapter and wrapper.

It does not justify a separate diagnostic engine.

### Alternative E: Maintain a long-lived engine fork for StartOS

This is rejected for the same reason.

StartOS package logic should resolve service bindings and lifecycle integration, while the Go engine remains shared.

### Alternative F: Reimplement Redline diagnostics in StartOS TypeScript

This is rejected.

It would create two engines with different languages, release cycles, and diagnostic behavior.

### Alternative G: Use platform packages only as remote API clients

A thin client could contact a centrally hosted diagnostic engine.

This is rejected because it violates local-first execution and introduces a cloud dependency.

### Alternative H: Permit platform-specific thresholds by default

This is rejected.

The same observed lag or disk pressure should not mean different things merely because of packaging.

User-configured thresholds remain possible through approved evaluator configuration.

### Alternative I: Guarantee byte-identical binaries across all packages

This is preferred where practical but cannot be an absolute requirement because:

* CPU architectures differ
* platform build systems may rebuild
* operating-system ABI requirements may differ
* packaging constraints may require distinct linking

Semantic-manifest equivalence is therefore the required architectural guarantee.

### Alternative J: Let every platform package maintain its own web UI

This is rejected.

Separate UIs would eventually create separate health aggregation and uncertainty behavior.

### Alternative K: Hide unsupported checks on restricted platforms

This is rejected.

Restricted access must appear through explicit coverage and unknown semantics.

### Alternative L: Put all platform logic in shell entrypoints

This is rejected.

Shell wrappers are difficult to type, test, version, and secure.

Bootstrap logic should remain minimal and structured.

## Consequences

### Positive consequences

* Redline has one diagnostic meaning across every official package.
* Platform restrictions produce coverage differences rather than truth differences.
* New probes and fixes can propagate to all platforms.
* Cross-platform reports remain comparable.
* Support personnel can trust finding and diagnosis codes across installations.
* Platform wrappers remain relatively small.
* StartOS and Umbrel integrations do not duplicate the engine.
* Release provenance becomes inspectable.
* Package-only fixes do not require unnecessary engine-version changes.
* Privacy and telemetry rules remain consistent.
* One embedded UI preserves consistent uncertainty presentation.
* The project avoids maintaining several incompatible products.
* Architecture-specific builds can be verified semantically.
* Downstream forks can be distinguished from official packages.
* Platform vendors can contribute access integration without redefining diagnostic behavior.

### Negative consequences

* Platform packages cannot optimize diagnostic behavior independently.
* A core-engine change may require coordinated releases across several stores.
* The shared engine must accommodate restricted environments cleanly.
* Platform bootstrap contracts require careful design.
* Conformance testing increases release complexity.
* Reusing canonical binaries may conflict with some platform build systems.
* A bug in the shared engine affects every package.
* Platform maintainers must upstream diagnostic changes rather than patch locally.
* Platform-specific UX is constrained by the shared web application.
* Semantic-manifest generation and comparison add tooling.
* Support for old platform package versions may complicate compatibility matrices.

### Neutral consequences

* Packages may expose different capability sets.
* Packages may have different release revision numbers.
* Platform-specific remediation wording remains possible.
* The optional privileged helper may exist only in native Linux packages.
* Platform stores may rebuild artifacts if semantic conformance remains verifiable.
* Separate CPU architectures continue to require separate binaries.

## Risks and mitigations

### Risk: Platform adapters accumulate diagnostic logic

**Mitigations:**

* Prevent adapter packages from importing finding and diagnosis constructors.
* Restrict adapter outputs to inventory, capabilities, typed state, and provenance.
* Add architecture tests.
* Review health-related thresholds outside adapters.
* Require equivalent-evidence tests.

### Risk: Packaging defaults alter semantic behavior

**Mitigations:**

* Keep evaluator defaults in the engine.
* Version scan profiles.
* Record effective configuration in findings.
* Compare defaults digests across packages.
* Reject silent platform threshold overrides.

### Risk: Restricted platforms appear inferior because of unknown results

**Mitigations:**

* Explain platform limitations clearly.
* Group expected unknowns.
* maximize protocol-level evidence
* distinguish expected restrictions from broken access
* avoid replacing honest uncertainty with weaker green checks

### Risk: A platform package ships an outdated engine

**Mitigations:**

* Expose engine version separately from package revision.
* Include semantic manifest in metadata and reports.
* Maintain a platform compatibility matrix.
* Automate store-package verification.
* Notify users locally when a package is known to be outdated only through platform-provided update mechanisms or explicit checks consistent with ADR-009.

### Risk: Platform-specific patches never return upstream

**Mitigations:**

* Prohibit long-lived official semantic forks.
* Require tracked upstream changes.
* Distinguish packaging patches from engine patches.
* Require expiration for temporary divergence.
* Include divergence in metadata.

### Risk: The shared UI cannot meet platform conventions

**Mitigations:**

* Permit thin platform framing.
* expose stable local API
* support responsive design and PWA behavior
* allow platform-specific setup and remediation content
* keep diagnostic rendering canonical

### Risk: Canonical artifact reuse is blocked by platform tooling

**Mitigations:**

* Permit rebuilds from the exact source revision.
* Compare semantic manifests.
* publish build instructions
* pursue reproducible builds
* verify catalog and schema digests

### Risk: Platform package health conflicts with Redline health

**Mitigations:**

* Define package health as Redline service availability only.
* Label stack health separately.
* Do not map diagnosed component failure to supervisor failure automatically.
* Test restart-loop behavior of platform supervisors.

### Risk: Different platform profiles produce confusing comparisons

**Mitigations:**

* Include profile ID and version in reports.
* expose selected and unavailable checks
* compare only equivalent coverage sets
* keep canonical finding semantics unchanged

### Risk: Platform wrappers leak secrets through startup configuration

**Mitigations:**

* use secret references
* avoid command-line secrets
* validate environment handling
* exclude bootstrap values from logs
* test platform package manifests with canary secrets

### Risk: One engine becomes cluttered with platform conditionals

**Mitigations:**

* keep platform behavior behind adapters and bootstrap interfaces
* prohibit platform checks in probes and evaluators
* compose capability providers
* separate platform recommendation rendering from diagnostics
* review build tags carefully

## Testing strategy

### Semantic equivalence tests

Given identical domain inputs, all official package builds must produce identical:

* findings
* statuses
* severity
* confidence
* diagnoses
* coverage
* recommendation IDs
* report objects

### Adapter isolation tests

Tests must verify that adapters:

* discover components
* register capabilities
* preserve provenance
* report unavailable access

and cannot:

* emit findings
* alter evaluator defaults
* write reports
* suppress unknowns

### Platform bootstrap tests

Each bootstrap layer must test:

* valid bindings
* missing bindings
* secret references
* malformed platform input
* storage-path configuration
* listener policy
* scan-profile selection
* no raw secret logging

### Package tests

Each package must verify:

* correct engine artifact
* correct semantic manifest
* correct embedded UI
* correct persistent paths
* correct listener exposure
* correct platform identity
* no telemetry
* report compatibility
* safe upgrade

### Conformance-gate tests

Release publication should fail when:

* semantic digests differ unexpectedly
* a platform package contains a different probe catalog
* schemas differ
* privacy-policy versions differ
* network-policy versions differ
* the embedded UI differs unexpectedly
* a platform wrapper emits diagnostic output
* the package binds publicly without documented policy
* a package includes unapproved external assets

## Validation criteria

ADR-010 will be considered successfully implemented when:

1. Generic Linux, Docker, Umbrel, and StartOS packages use the same diagnostic engine source.
2. Canonical engine binaries are reused across packages where platform constraints permit.
3. Distinct builds expose matching semantic manifests when claiming the same engine version.
4. Platform wrappers contain no probes, evaluators, or correlation rules.
5. StartOS TypeScript code performs package integration only.
6. Umbrel manifests contain no independent health interpretation.
7. Docker entrypoints perform no diagnostic checks.
8. Platform adapters provide capabilities rather than findings.
9. Equivalent normalized evidence produces equivalent canonical findings across all packages.
10. Platform capability differences produce coverage differences rather than altered finding meaning.
11. Diagnostic thresholds remain engine-owned.
12. Platform scan profiles are versioned and visible.
13. Reports include engine, package, profile, and adapter provenance.
14. Platform package health checks assess Redline service availability only.
15. The embedded web UI is shared across official packages.
16. Platform UI integration cannot hide unknown findings.
17. Platform-specific recommendations retain stable recommendation IDs.
18. Engine database migrations remain package-independent.
19. Platform wrappers do not modify persisted findings or observations.
20. Packaging-only changes use a package revision distinct from the engine version.
21. Engine changes propagate through normal Redline releases.
22. Temporary platform-specific engine divergence is explicitly identified and time-bounded.
23. Official package conformance fails on unexpected semantic-manifest differences.
24. Official packages preserve ADR-005 raw-data restrictions.
25. Official packages preserve ADR-009 no-telemetry defaults.
26. The privileged helper remains optional and platform-specific without changing probe semantics.
27. Platform-provided health flags remain evidence rather than canonical Redline health.
28. API and report schemas remain identical across official packages.
29. Architecture tests prevent probes from importing packaging code.
30. Release CI verifies engine checksums or semantic equivalence.
31. AMD64 and ARM64 builds expose equivalent diagnostic catalogs.
32. Reports produced on one platform can be read and rendered on another.
33. Package upgrades preserve engine-owned data and schema compatibility.
34. Reduced platform coverage is clearly shown rather than silently omitted.
35. Core diagnosis remains fully local on every platform.
36. Downstream semantic forks cannot be confused with official packages through metadata.
37. The first cross-platform Bitcoin fixture produces identical findings where evidence matches.
38. The first restricted-platform fixture produces explicit unknowns instead of replacement passes.
39. Package-specific bootstrap values do not leak into logs or reports.
40. The platform conformance suite is required before official release.

## Reconsideration triggers

This ADR should be revisited if:

1. A supported platform cannot execute the Go diagnostic engine.
2. A platform requires diagnostics to run in a different language or process model.
3. Mobile applications must run the complete engine locally.
4. A remote-agent architecture requires splitting collection from evaluation.
5. Canonical binary reuse becomes impossible across major platforms.
6. Platform-specific semantic requirements are demonstrated rather than merely convenient.
7. A platform requires different privacy or regulatory behavior.
8. Platform stores mandate source rebuilds that cannot be semantically verified.
9. Maintaining one embedded web UI materially prevents platform adoption.
10. Engine size or dependencies exceed platform limits.
11. A platform capability cannot be represented through ADR-002.
12. StartOS or Umbrel introduces a native diagnostics framework that could safely host Redline rules.
13. Platform-specific release timing makes coordinated security updates impractical.
14. Reproducible builds become required for official distribution.
15. Third-party vendors request certified Redline-compatible downstream builds.
16. Automated remediation introduces platform-specific state-changing operations.
17. A future extension system allows platform-delivered probes.
18. Cross-platform semantic-equivalence testing becomes impractical.
19. A platform’s trust model requires the engine to be divided into additional security domains.
20. Commercial packaging creates pressure to make core diagnostic behavior platform-dependent.

A reconsideration trigger does not authorize a silent platform fork.

A material change requires a new ADR defining:

* which semantics may differ
* why capability differences are insufficient
* report compatibility
* finding-code compatibility
* test equivalence
* source ownership
* release ownership
* privacy behavior
* update coordination
* user-visible product identity
* downstream support obligations

## Final decision statement

SATOSHI//REDLINE will maintain one diagnostic engine across generic Linux, Docker, Umbrel, StartOS, and future official platforms.

Platform packages may provide installation, lifecycle management, configuration translation, endpoint bindings, secret references, capability providers, listener exposure, storage locations, and platform-specific remediation presentation.

They may not implement separate probes, evaluators, correlation rules, health aggregation, privacy rules, report schemas, or diagnostic semantics.

The preferred release process will build canonical engine artifacts once and reuse them across platform packages. Where rebuilding is required, semantic manifests and conformance tests will verify equivalent diagnostic composition.

Platform limitations will reduce evidence and coverage. They will not change the meaning of pass, warning, failure, unknown, or root cause.

The central rule established by this ADR is:

> One product may have many packages, but it must have only one diagnostic truth model.
