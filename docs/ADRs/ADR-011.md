# ADR-011: Use the Lab as a Packaging Consumer, Not a Package Fork

* **Date:** 2026-08-07
* **Decision owners:** SATOSHI//REDLINE maintainers
* **Depends on:**

  * ADR-001 — Use a Go Modular Monolith for the Diagnostic Backend
  * ADR-007 — Compile First-Party Probes into the Redline Binary for v0.1
  * ADR-009 — Keep Core Execution Local and Prohibit Outbound Telemetry by Default
  * ADR-010 — Platform Packages Wrap, but Never Fork, the Diagnostic Engine
* **Scope:**

  * Relationship between SATOSHI//REDLINE and bitcoin-vm-lab
  * Live and package-conformance testing tiers
  * Operator delivery of artifacts into lab guests
  * Separation of product packaging from lab lifecycle
* **Excluded from scope:**

  * Concrete Umbrel or StartOS package file formats (covered by ADR-010)
  * Lab VM lifecycle, storage, or checkpoint procedures (owned by bitcoin-vm-lab)
  * Store submission or code-signing infrastructure
  * Continuous monitoring product design

## Context

SATOSHI//REDLINE needs real Bitcoin Core / Knots and Electrum surfaces for live iteration. The sibling repository [bitcoin-vm-lab](https://github.com/SpectrGen1/bitcoin-vm-lab) provides production-fidelity Ubuntu, UmbrelOS, and StartOS guests on a shared signet checkpoint.

Separately, user consumption requires official platform packages (generic Linux, Docker, Umbrel, StartOS) that wrap one diagnostic engine (ADR-010).

These two needs can be confused:

* building a second “lab edition” of Redline with different packaging, defaults, privacy, or topology
* treating host-side protocol smoke as proof that a platform package works
* letting product tests start, stop, or reconfigure lab VMs
* publishing artifacts that never ran on the lab’s real package paths

A lab-specific product fork would defeat both the lab’s fidelity goals and ADR-010’s “build once, package many” rule.

## Decision

bitcoin-vm-lab is a **destination and fidelity harness** for SATOSHI//REDLINE. It is not a second product packaging line.

1. **One artifact graph.** Official packages and release binaries are defined only under the product repository’s normal packaging paths. There is no `packaging/lab` product and no lab-only diagnostic semantics, thresholds, privacy policy, or Compose topology.

2. **Two delivery destinations for the same artifacts.**

   * **Publish** — user consumption (stores, apt, OCI registries, tarballs).
   * **Sideload / local install** — install or copy those same artifacts into a lab guest for conformance and iteration.

   Delivery may differ (unsigned CI builds, local paths, operator scripts). Package *definition* must not.

3. **Four verification tiers.**

   | Tier | Name | What it proves | Lab role |
   | ---- | ---- | -------------- | -------- |
   | 0 | Offline engine | Unit and architecture tests | None |
   | 1 | Protocol live smoke | Authenticated RPC/Electrum, graph, API, report, privacy against real services | Lab provides endpoints; Redline runs on the host (or via tunnel) |
   | 2 | Package / binary in guest | Lifecycle, paths, and bindings as users would experience | Same release artifact (or labeled dev binary shortcut) installed into the matching guest |
   | 3 | User publish | Store or channel distribution | Lab may re-verify the RC artifact; it does not replace publish |

4. **Lab lifecycle ownership stays in bitcoin-vm-lab.** Product binaries, `go test` packages, and offline CI must not start, stop, promote, discard, reconfigure, or destroy lab VMs, overlays, or Bitcoin packages. Operator scripts may call `bvml` only to **read** connection info or to **deliver** an already-built artifact. They must remain opt-in and must not run under ordinary `go test ./...`.

5. **Dev binary sideload is allowed and non-gating.** Copying a freshly built `redline` / `redlined` into a guest for iteration is a documented development shortcut. It does not replace Tier 2 package conformance once platform packages exist, and it must not introduce lab-only diagnostic code paths.

6. **Promotion rule.** The artifact that passes the intended gate is the one that publishes. Rebuilds with different flags, probe catalogs, or privacy behavior are not “the same package tested on the lab.”

## Decision drivers

1. Preserve one meaning for every finding across lab and user installs (ADR-010).
2. Keep lab platform fidelity (official Umbrel/StartOS topology) intact.
3. Make live iteration practical without product ownership of VM lifecycle.
4. Avoid a long-lived lab fork that never ships to users.
5. Keep offline `go test ./...` safe, hermetic, and free of lab credentials.
6. Scale later package work without redesigning the test model.

## Consequences

### Positive

* Operators can run Tier 1 against Umbrel/Ubuntu today with shared scripts.
* Future Umbrel/StartOS packages reuse the same model for Tier 2.
* Clear language for what “tested on the lab” means at each tier.
* Product and lab repositories keep clean ownership boundaries.

### Negative / accepted costs

* Full platform-package confidence waits until wrappers exist (Tier 2).
* Host-side filesystem probes describe the host, not the guest datadir, unless the operator runs Redline in-guest or mounts the path.
* Operators must bring up the lab themselves via `bvml`.

### Neutral

* Live smoke may report `warning` or `failure` findings while still succeeding as an integration check (node lag, storage pressure).
* Cookie files and guest IPs remain local operator credentials and must never be committed.

## Implementation sketch

```text
satoshi-redline/
  packaging/           # official platform packages only (when present)
  scripts/lab/         # opt-in operator delivery + Tier 1 helpers
  testlab/live*        # opt-in go tests; no bvml lifecycle control
  docs/lab-integration.md

bitcoin-vm-lab/
  bin/bvml             # sole lab lifecycle controller
```

Operator flow (Tier 1):

```text
bvml resume umbrel && bvml index-adapter-setup umbrel
./scripts/lab/prepare.sh --vm umbrel
./scripts/lab/smoke.sh
./scripts/lab/scan.sh
```

Operator flow (Tier 2, when packages exist):

```text
build official package artifact
./scripts/lab/sideload-package.sh --vm umbrel --artifact dist/...
# or platform-native install, then scan as packaged
```

## Alternatives considered

### Separate lab packaging tree

Rejected. Diverges Compose, paths, privacy, or probe catalogs and falsifies fidelity.

### Product-driven lab orchestration from `go test`

Rejected. Couples CI to libvirt state, violates lab safety rules, and risks destructive operations from agent automation.

### Lab-only binary flags that change diagnostic meaning

Rejected. Violates ADR-010 semantic equivalence.

### Host-side smoke as the only gate before publish

Insufficient for platform packages. Retained as Tier 1 only.

## Status

Accepted.
