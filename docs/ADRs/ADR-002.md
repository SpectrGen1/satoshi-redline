# ADR-002: Use Capability-Based, Composable Platform Adapters

* **Date:** 2026-07-30
* **Decision owners:** SATOSHI//REDLINE maintainers
* **Depends on:** ADR-001 — Use a Go Modular Monolith for the Diagnostic Backend
* **Scope:** Environment discovery, platform integration, protocol access, privilege-aware scan planning, and probe access to external systems

## Context

SATOSHI//REDLINE must run across environments that expose substantially different levels of access.

A generic Linux installation may permit Redline to inspect:

* systemd units
* Docker containers
* process state
* mount points
* filesystems
* bounded journal entries
* local network listeners
* Bitcoin RPC
* Electrum endpoints
* DATUM and Stratum services
* Tor interfaces

An Umbrel installation may expose:

* application-provided Bitcoin RPC access
* declared Docker services
* selected application endpoints
* container-local network access
* little or no supported access to the underlying host

A StartOS installation may expose:

* declared service dependencies
* dynamically assigned service interfaces
* package health information
* service configuration
* logs and dependency metadata through supported platform interfaces
* no unrestricted host filesystem or service-manager access

These environments cannot be accurately represented by a single platform enum such as:

```go
switch platform {
case Linux:
case Umbrel:
case StartOS:
}
```

Real installations are compositional.

For example:

* A generic Linux host may use both systemd and Docker.
* Umbrel is itself a Docker-based environment but imposes additional application and permission boundaries.
* A StartOS package may receive some service interfaces from StartOS while communicating with other manually configured LAN services.
* A user may run Bitcoin under systemd, Fulcrum in Docker, DATUM directly from a shell service, and miners elsewhere on the LAN.
* A future appliance may expose Bitcoin RPC but no process, log, or filesystem access.

Diagnostic logic must therefore depend on what Redline can observe and do, not on a broad platform label.

The architecture must also preserve one of Redline’s central guarantees:

> Lack of access must produce explicit uncertainty, not a false pass.

A Bitcoin synchronization probe should work the same way regardless of whether its RPC connection was obtained from a Linux configuration file, an Umbrel-injected secret, or a StartOS service binding.

Likewise, an Electrum synchronization rule should not need to know which platform supplied the endpoint.

## Decision

SATOSHI//REDLINE will use **capability-based, composable platform adapters**.

Platform adapters will:

1. Detect or receive information about an execution environment.
2. Discover observable components and relationships.
3. Register narrowly scoped capability providers.
4. Explain capability limitations and access failures.
5. Supply provenance and security metadata for discovered access paths.

Platform adapters will not:

* determine component health
* interpret observations as failures
* correlate failures across components
* select root causes
* generate remediation advice
* silently substitute one source of evidence for another

Diagnostic probes will declare the capabilities they require and optionally use.

The scan planner will resolve those requirements against the capabilities available for each component. If a required capability cannot be resolved, the affected diagnostic result will be `unknown` with an explicit reason.

Multiple adapters may be active at the same time. Redline will not select one global adapter and discard the others.

The governing separation is:

```text
Platform adapters discover access
            ↓
Capability providers perform bounded operations
            ↓
Probes produce normalized observations
            ↓
Evaluators produce findings
            ↓
Correlation rules produce diagnoses
```

## Terminology

### Component

A component is an identified part of the user’s Bitcoin infrastructure.

Examples:

```text
bitcoin.primary
electrum.fulcrum-main
mining.datum-gateway
miner.avalon-office
tor.system
storage.bitcoin-data
service.bitcoind
container.fulcrum
```

A component represents the subject being diagnosed. It is not itself a capability.

### Platform adapter

A platform adapter understands an environment-specific integration model.

Examples:

* Linux host adapter
* systemd adapter
* Docker adapter
* Umbrel adapter
* StartOS 0.4 adapter

An adapter may discover components, relationships, endpoint bindings, credential references, and capability providers.

### Capability

A capability is a narrow, typed ability to observe or interact with part of the environment.

Examples:

```text
bitcoin.rpc.read
electrum.protocol.read
network.tcp.connect
network.tls.handshake
tor.socks.connect
service.state.read
service.restart-history.read
container.inspect
filesystem.stat
mount.inspect
journal.read-bounded
clock.read
dns.resolve
```

A capability describes available behavior. It does not describe whether the observed component is healthy.

### Capability provider

A capability provider is the concrete implementation of a capability.

Examples:

* A systemd provider implementing `service.state.read`
* A Docker provider implementing `container.inspect`
* An Umbrel-generated Bitcoin RPC provider implementing `bitcoin.rpc.read`
* A StartOS dependency binding implementing endpoint resolution
* The optional privileged helper implementing bounded journal access

### Probe

A probe uses one or more capabilities to collect normalized observations.

For example, the Bitcoin chain-state probe may require `bitcoin.rpc.read` and call a limited set of read-only RPC methods.

### Adapter composition

Adapter composition means several adapters may contribute components and capabilities to one scan.

A Linux installation may use all of the following simultaneously:

```text
linux-host
systemd
docker
manual-endpoints
tor
redline-privd
```

## Decision drivers

The decision drivers, in priority order, are:

1. Preserve platform-independent diagnostic logic.
2. Represent partial and asymmetric access honestly.
3. Support mixed-stack installations.
4. Prevent platform adapters from becoming duplicate diagnostic engines.
5. Make privilege requirements explicit.
6. Minimize secret and sensitive-data exposure.
7. Allow safe and deep scans to use the same probes where possible.
8. Make platform integrations independently testable.
9. Support future platforms without modifying existing probes.
10. Avoid a lowest-common-denominator design that weakens generic Linux diagnostics.

## Capability model

### Capabilities are narrow behavioral contracts

Capabilities must describe one coherent class of operation.

Good capability boundaries include:

```text
Read systemd unit properties
Inspect a Docker container
Read filesystem capacity
Perform a TCP connection
Call approved Bitcoin RPC methods
Read a bounded service journal
Resolve a platform-provided service endpoint
```

Poor capability boundaries include:

```text
Full Linux access
Diagnose Bitcoin
Access everything on Umbrel
Run commands
Read any file
Inspect the system
```

Capabilities must not grant arbitrary shell execution, arbitrary filesystem reads, or unrestricted host access.

### Stable identifiers and typed Go interfaces

Every capability will have:

1. A stable string identifier used in manifests, reports, logs, and scan plans.
2. A typed Go interface used by backend code.

Example:

```go
type CapabilityID string

const (
    CapabilityBitcoinRPCRead CapabilityID = "bitcoin.rpc.read/v1"
    CapabilityTCPConnect     CapabilityID = "network.tcp.connect/v1"
    CapabilityServiceState   CapabilityID = "service.state.read/v1"
    CapabilityFilesystemStat CapabilityID = "filesystem.stat/v1"
)
```

The stable identifier is an external architectural contract. The Go interface is an internal implementation contract.

A capability version changes only when its behavioral contract changes incompatibly.

### Capabilities are scoped

A capability must be bound to a subject or defined scope.

A Bitcoin RPC capability is not simply “Bitcoin RPC is available.” It is:

```text
Bitcoin RPC access for component bitcoin.primary
```

A filesystem capability may be scoped to:

```text
Filesystem statistics for storage.bitcoin-data
```

A bounded journal capability may be scoped to:

```text
Journal access for service bitcoind.service
Maximum lookback: 30 minutes
Maximum entries: 2,000
```

This prevents a capability intended for one component from becoming implicit unrestricted access to the host.

### Capability descriptors

Each registered capability instance will include metadata similar to:

```go
type CapabilityDescriptor struct {
    ID             CapabilityID
    ProviderID     string
    SubjectID      ComponentID
    Provenance     Provenance
    Availability   CapabilityAvailability
    Privilege      PrivilegeClass
    SideEffects    SideEffectClass
    Sensitivity    SensitivityClass
    Constraints    CapabilityConstraints
}
```

Representative metadata:

```text
Capability:     bitcoin.rpc.read/v1
Subject:        bitcoin.primary
Provider:       umbrel.bitcoin-binding
Provenance:     platform-declared
Availability:   available
Privilege:      unprivileged
Side effects:   local-network-read
Sensitivity:    consumes-secret-reference
Constraints:    approved read-only methods only
```

This metadata allows the scan planner and report engine to explain how evidence was obtained and why some checks could not run.

## Platform detection and composition

### Platform identity is descriptive, not controlling

Redline may identify that it is running inside Umbrel or StartOS, but platform identity will not directly select diagnostic behavior.

Platform detection may influence:

* which adapters are loaded
* where platform metadata is read
* which discovery mechanisms are attempted
* which packaging-specific bindings are available
* which access restrictions should be expected

It will not influence:

* Bitcoin health thresholds
* Electrum lag rules
* DATUM template-freshness rules
* root-cause ranking
* remediation meaning

A probe must not contain logic such as:

```go
if platform == "umbrel" {
    // alternate Bitcoin health logic
}
```

### Multiple adapters may be active

The adapter manager will support additive composition.

Example generic Linux environment:

```text
Linux host adapter
    ├── discovers mount and system information
    └── registers filesystem and clock capabilities

systemd adapter
    ├── discovers bitcoind.service
    └── registers service-state capability

Docker adapter
    ├── discovers Fulcrum container
    └── registers container-inspection capability

manual endpoint adapter
    ├── defines DATUM endpoint
    └── registers protocol connection information
```

Example Umbrel environment:

```text
Umbrel adapter
    ├── imports declared Bitcoin dependency
    ├── identifies application-local services
    └── registers platform-provided endpoint bindings

Docker adapter, restricted
    └── inspects only containers explicitly available to the app

protocol providers
    ├── Bitcoin RPC
    ├── Electrum
    └── TCP checks
```

The Umbrel adapter does not replace the protocol providers. It supplies the access paths those providers require.

### Adapters may enrich existing components

Different adapters may observe different aspects of the same component.

For example:

```text
manual configuration:
    bitcoin.primary has RPC endpoint

systemd adapter:
    bitcoin.primary is operated by bitcoind.service

Linux storage discovery:
    bitcoin.primary uses storage.bitcoin-data

Docker adapter:
    electrum.primary runs in container fulcrum
```

The inventory builder will merge compatible evidence into a single component graph.

Merging must be deterministic and provenance-preserving.

## Discovery model

### Discovery is evidence, not truth

Discovery sources may be incomplete or contradictory.

Sources include:

* explicit user configuration
* platform-declared service bindings
* systemd unit metadata
* Docker labels and environment metadata
* known default paths
* open local ports
* process inspection
* application manifests

Each discovered fact must retain its provenance.

Example:

```json
{
  "component_id": "bitcoin.primary",
  "attribute": "rpc_endpoint",
  "value": "internal-reference",
  "provenance": {
    "source": "startos-service-binding",
    "confidence": "authoritative"
  }
}
```

### Discovery precedence

When multiple sources provide the same binding, precedence will be:

1. Explicit user selection
2. Authoritative platform declaration
3. Application package metadata
4. Strong service metadata
5. Heuristic discovery

A lower-precedence source may enrich a component but must not silently overwrite a higher-precedence source.

### Ambiguity must not be silently resolved

If Redline discovers two plausible Bitcoin nodes and cannot determine which one backs a given Electrum server, it must not arbitrarily choose one.

The engine may:

* run checks against both components independently
* ask the user to define the dependency
* mark the cross-layer relationship as unknown
* report the competing candidates

It must not fabricate a dependency edge.

Example:

```text
Cross-layer Electrum comparison: unknown

Reason:
Two Bitcoin RPC endpoints were discovered, and Redline could not determine
which endpoint supplies electrum.primary.
```

## Probe requirements

Each probe will publish a descriptor.

Example:

```go
type ProbeDescriptor struct {
    ID                   ProbeID
    Version              string
    AppliesTo            []ComponentKind
    RequiredCapabilities []CapabilityID
    OptionalCapabilities []CapabilityID
    MinimumMode          ScanMode
    Timeout              time.Duration
    CostClass            ProbeCostClass
}
```

Example Bitcoin chain-state probe:

```text
Probe: bitcoin.chain-state/v1
Applies to: bitcoin-node
Required:
    bitcoin.rpc.read/v1
Optional:
    clock.read/v1
Minimum mode:
    safe
```

Example restart-loop probe:

```text
Probe: service.restart-loop/v1
Applies to: managed-service
Required:
    service.restart-history.read/v1
Minimum mode:
    deep
```

### Required capabilities

If a required capability is unavailable, the probe cannot claim a pass or failure.

It produces an `unknown` result with:

* the unavailable capability
* the reason it is unavailable
* the provider or adapter involved
* whether a deeper scan could provide it
* any unaffected checks that still ran

### Optional capabilities

Missing optional capabilities may reduce confidence or detail without invalidating the entire probe.

For example, a Bitcoin chain-state check can work without process restart history. Its result may still be conclusive about synchronization while remaining silent about restart stability.

### Probes must not acquire capabilities independently

A probe must not:

* open the Docker socket directly
* detect systemd itself
* read arbitrary configuration paths
* invoke platform commands
* search for credentials
* decide which platform adapter to use

The scan planner provides a resolved capability set to the probe.

## Capability resolution

### Resolution is component-specific

Capabilities are resolved for a particular probe and component.

Conceptually:

```go
resolved, err := registry.Resolve(
    componentID,
    CapabilityBitcoinRPCRead,
    resolutionPolicy,
)
```

The registry must not return a random global provider.

### Multiple providers

More than one provider may satisfy a capability.

For example, service state might be observable through:

* systemd
* Docker
* StartOS health state
* a service-native health endpoint

These sources are not necessarily equivalent.

Resolution policy may select:

* an authoritative provider
* all providers for corroboration
* a provider appropriate to the current scan mode
* a provider with the narrowest privileges
* a provider explicitly selected by the user

### Provider preference

Default preference will favor:

1. Explicitly configured provider
2. Platform-authoritative provider
3. Least-privileged provider
4. Narrowest data scope
5. Most direct evidence
6. Highest expected reliability

Preference must not convert semantically different evidence into interchangeable evidence.

For example:

```text
systemd says process is active
```

does not replace:

```text
Bitcoin RPC responds correctly
```

Both may be useful, but they satisfy different capabilities and support different claims.

### Corroboration

Some probes may deliberately use multiple providers.

Example:

```text
Service manager: bitcoind is active
Bitcoin RPC: connection refused
TCP listener: no process is bound
```

This combination is diagnostically valuable. The capability model must preserve the distinct observations rather than collapsing them into one “service health” value.

## Capability availability

A capability instance may have one of these availability states:

```text
available
degraded
unavailable
denied
unsupported
ambiguous
disabled
```

Definitions:

* **available** — the capability is usable within its declared constraints.
* **degraded** — usable, but with reduced scope, freshness, or reliability.
* **unavailable** — expected provider exists but cannot currently perform the operation.
* **denied** — access is blocked by permissions or policy.
* **unsupported** — the current platform or version does not implement the capability.
* **ambiguous** — more than one binding exists and no safe resolution can be made.
* **disabled** — the user or deployment configuration intentionally disabled it.

These states describe access, not component health.

### Mapping to diagnostic uncertainty

When capability availability prevents a probe from running, it maps to an explicit unknown reason:

| Capability state | Diagnostic unknown reason                                    |
| ---------------- | ------------------------------------------------------------ |
| unavailable      | `capability_unavailable`                                     |
| denied           | `permission_denied`                                          |
| unsupported      | `platform_restriction` or `unsupported_version`              |
| ambiguous        | `ambiguous_binding`                                          |
| disabled         | `user_disabled`                                              |
| degraded         | probe-specific reduced confidence or `insufficient_evidence` |

## Safe and deep scan modes

Safe and deep scans will not use separate diagnostic engines.

They will differ primarily in which capability providers are allowed.

### Safe mode

Safe mode may use capabilities such as:

```text
bitcoin.rpc.read
electrum.protocol.read
network.tcp.connect
network.tls.handshake
service.health-endpoint.read
filesystem.stat-unprivileged
dns.resolve
tor.socks.connect
```

Safe mode must avoid:

* privileged host access
* arbitrary configuration reads
* broad log collection
* host Docker access unless explicitly and safely exposed
* external network tests that were not enabled
* operations that could alter service state

### Deep mode

Deep mode may additionally enable:

```text
service.state.read
service.restart-history.read
container.inspect
journal.read-bounded
mount.inspect
firewall.binding.inspect
filesystem.configured-path.inspect
kernel-error-summary.read
```

Deep mode does not allow destructive operations.

The privileged helper, where installed, contributes additional narrowly scoped capability providers. It does not change diagnostic semantics.

### Capability escalation

A probe may report:

```text
Result: unknown
Reason: restart history is unavailable in safe mode
Additional evidence available through: deep scan
```

It must not automatically escalate privileges.

## Privilege and side-effect classification

Every capability must declare a privilege class:

```text
unprivileged
platform-granted
privileged-helper
```

Every capability must also declare a side-effect class:

```text
local-read
local-connect
lan-connect
external-connect
sensitive-read
```

All v0.1 capabilities remain operationally read-only, but read-only does not mean side-effect-free.

Examples:

* Connecting to a LAN Stratum port creates network traffic.
* Testing Tor circuit functionality may create external traffic.
* Calling Bitcoin RPC consumes authentication material transiently.
* Reading logs may expose sensitive data in process memory.
* Accessing the Docker socket grants broad host authority even when Redline intends only to inspect.

The planner may require explicit configuration or user approval for higher-risk classes.

## Secret handling

Capabilities that require authentication must consume secret references without exposing secret values to probes.

Example:

```go
type BitcoinRPCBinding struct {
    Endpoint  EndpointRef
    Auth      SecretRef
    Network   NetworkScope
}
```

A probe may receive an authenticated Bitcoin RPC client capability. It must not receive:

* the cookie contents
* RPC passwords
* platform secret environment variables
* raw authorization headers

Secret resolution belongs to the provider boundary.

Capability descriptors may state:

```text
Sensitivity: consumes-secret-reference
```

They must never include the secret itself.

## Data minimization

Capability providers must return the smallest data shape required by their contract.

A provider should return:

```go
type FilesystemStat struct {
    TotalBytes     uint64
    AvailableBytes uint64
    ReadOnly       bool
}
```

rather than exposing an unrestricted filesystem handle.

A service provider should return typed unit properties rather than arbitrary command output.

A Bitcoin RPC provider should allow only approved read-only methods rather than providing a generic method capable of calling every RPC namespace.

Where generic protocol invocation is unavoidable internally, the provider must enforce an allowlist.

## Error model

Capability errors must be typed and preserve the distinction between:

* target failure
* access failure
* provider failure
* timeout
* invalid configuration
* unsupported operation
* ambiguous binding
* cancellation

Example:

```go
type CapabilityError struct {
    Kind       CapabilityErrorKind
    Capability CapabilityID
    ProviderID string
    SubjectID  ComponentID
    Operation  string
    Retryable  bool
    Cause      error
}
```

A TCP connection refusal is evidence about the target.

A permission denial opening a socket is evidence about Redline’s access.

Those must not produce the same finding.

Similarly:

```text
Bitcoin RPC returned “method not found”
```

may indicate an unsupported implementation or version.

```text
Redline could not read the RPC cookie
```

indicates an access problem.

```text
Bitcoin RPC timed out after connection”
```

is evidence about service behavior.

Typed errors allow probes to preserve these distinctions.

## Capability lifecycle

Capability providers will be initialized either:

* at daemon startup for stable platform services
* during inventory discovery
* at scan start for ephemeral bindings
* lazily on first use where initialization is expensive

Every capability operation must:

* accept a `context.Context`
* obey cancellation
* use an explicit timeout
* bound returned data
* release network and file resources
* avoid retaining raw sensitive responses
* be safe for the documented concurrency level

Providers must declare whether they are:

```text
concurrency-safe
serialized
single-use
```

The planner will respect these constraints.

## Platform adapter responsibilities

### Linux host adapter

May provide:

* operating-system and architecture identification
* mount and filesystem discovery
* clock state
* memory and CPU pressure
* selected `/proc` and `/sys` observations
* relationships between configured data directories and volumes

It must not diagnose Bitcoin or mining services.

### systemd adapter

May provide:

* unit discovery
* active and sub-state
* activation timestamps
* restart counters
* bounded journal access through an approved provider
* unit-to-process relationships

It must not decide whether a service restart pattern constitutes a failure.

### Docker adapter

May provide:

* container discovery
* image and label metadata
* running state
* restart metadata
* declared networks and port bindings
* bounded log access
* volume relationships

It must not infer that a running container means the application is healthy.

Direct Docker-socket access must be treated as highly privileged even when the daemon itself is not running as root.

### Umbrel adapter

May provide:

* platform identity and version
* application metadata
* declared dependency bindings
* platform-injected Bitcoin endpoints
* application-local service relationships
* explicitly available container information

It must not assume access to the host beyond what the Umbrel application environment actually grants.

### StartOS adapter

May provide:

* service identity and version
* declared dependency graph
* imported runtime interfaces
* platform service health state
* supported configuration and log interfaces
* platform-resolved endpoint bindings

It must not rely on preferred or assumed static ports when StartOS provides runtime bindings.

## Alternatives considered

### Alternative A: One adapter interface per platform

Example:

```go
type PlatformAdapter interface {
    CheckBitcoin()
    CheckElectrum()
    CheckMining()
    CheckSystem()
}
```

This is rejected.

It would duplicate diagnostic logic across Linux, Umbrel, and StartOS and cause platform behavior to diverge.

Adding a new Bitcoin check would require modifying every platform adapter.

Cross-layer correlation would either be duplicated or forced to consume inconsistent platform-specific results.

### Alternative B: Select exactly one platform adapter

This is rejected because real installations are mixed environments.

A single-adapter model cannot accurately represent:

* systemd plus Docker
* platform bindings plus LAN services
* multiple Bitcoin nodes
* a local node with remote miners
* future platform extensions

### Alternative C: Normalize all platforms to the lowest common denominator

This would limit all environments to basic protocol checks because Umbrel and StartOS do not expose the same host access as generic Linux.

It is rejected because generic Linux users should receive deeper diagnostics when evidence is available.

The architecture must support unequal diagnostic coverage without generating unequal diagnostic meaning.

### Alternative D: Allow probes to inspect the environment directly

This is rejected because it would scatter platform detection, privilege handling, command execution, secret lookup, and error interpretation throughout the probe library.

It would make probes difficult to test and would eventually create hidden platform branches.

### Alternative E: Shell-command adapters

An adapter could expose generic command execution and let probes call tools such as:

```text
systemctl
docker
journalctl
ss
df
mount
```

This is rejected.

Generic command execution would:

* greatly expand attack surface
* weaken privilege separation
* make argument injection harder to prevent
* create unstable text-parsing dependencies
* obscure what authority each probe possesses
* make data minimization impossible to enforce

Where a command-line utility must be used internally, it will remain encapsulated inside a narrowly typed provider using fixed arguments and structured output.

### Alternative F: Build separate platform-specific products

Maintaining separate Linux, Umbrel, and StartOS diagnostic engines is rejected.

Packaging may differ, but diagnostic semantics and the core engine must remain shared.

## Consequences

### Positive consequences

* The same probe can operate across Linux, Umbrel, StartOS, and future platforms.
* Mixed-stack systems can be represented accurately.
* Missing access produces explicit uncertainty.
* Platform integrations remain focused on access rather than interpretation.
* Deep-scan functionality can be added without creating separate diagnostic logic.
* Privileged operations can be narrowly enumerated.
* Tests can substitute fake capability providers.
* New platform adapters can reuse the existing probe library.
* Diagnostic coverage can expand without weakening restricted-platform honesty.
* Evidence provenance remains available for reports and support analysis.

### Negative consequences

* The architecture introduces more types and planning logic than direct platform calls.
* Capability identifiers and versions require governance.
* Component discovery and provider resolution may become complex.
* Multiple providers can produce conflicting evidence.
* Incorrect capability boundaries could create excessive fragmentation.
* Developers must understand the distinction between access, observation, finding, and diagnosis.
* Some simple checks require more plumbing than an ad hoc shell script.
* Provider metadata and error semantics must remain consistent across integrations.

### Neutral consequences

* Platform-specific packaging code still exists.
* Platform-specific discovery logic remains necessary.
* Some capabilities may be available only on one platform.
* Restricted platforms will naturally produce lower coverage than deep Linux scans.
* A platform adapter may be distributed with the core binary without being active on every installation.

## Risks and mitigations

### Risk: Capability explosion

Creating a new capability for every small method could produce an unmanageable registry.

**Mitigations:**

* Define capabilities around cohesive behavior, not individual function calls.
* Version only stable contracts.
* Review new capabilities as architectural interfaces.
* Prefer a small typed interface with related read-only operations over dozens of single-method capabilities.
* Split a capability when its privilege, sensitivity, or lifecycle differs materially.

### Risk: Capabilities become disguised platform APIs

A capability such as `umbrel.everything` would defeat the architecture.

**Mitigations:**

* Capability names describe behavior, not platforms.
* Platform-specific capability IDs require explicit justification.
* Probes must not import platform adapter packages.
* Architecture tests enforce package dependency rules.

### Risk: Adapters begin producing health conclusions

This would lead to duplicated and inconsistent diagnostic rules.

**Mitigations:**

* Adapter outputs are limited to inventory, bindings, typed state, and capability metadata.
* Findings and recommendations cannot be emitted by adapter packages.
* Domain finding types are not imported by platform packages.
* Code review rejects platform-specific health thresholds.

### Risk: Incorrect provider selection

Choosing the wrong Bitcoin endpoint or service provider could produce misleading cross-layer diagnoses.

**Mitigations:**

* Preserve provenance.
* Apply deterministic precedence.
* Do not resolve genuine ambiguity silently.
* Permit explicit user bindings.
* Display component relationships in reports.
* Include selected provider identity in internal scan traces.

### Risk: Privileged providers quietly override safe providers

A deep scan could unintentionally increase exposure even when safe evidence is sufficient.

**Mitigations:**

* Prefer least-privileged providers by default.
* Use privileged providers only when required for additional evidence.
* Record the privilege class of every observation.
* Permit deployments to disable privileged capabilities globally.

### Risk: Provider responses leak sensitive data

**Mitigations:**

* Use minimal typed return values.
* Resolve secrets inside providers.
* Never expose raw authorization material.
* Bound log and configuration reads.
* Apply redaction before persistence.
* Add canary-secret tests to every provider handling sensitive inputs.

### Risk: `unknown` results overwhelm users

Restricted environments may generate many unavailable checks.

**Mitigations:**

* Group unknowns by missing capability.
* Distinguish expected platform restrictions from unexpected access failures.
* Show coverage summaries.
* Avoid creating one user-visible incident per unavailable optional check.
* Explain whether deep scan or configuration could improve coverage.

## Testing strategy

### Capability contract tests

Each capability interface will have a reusable contract test suite.

For example, all TCP-connect providers must demonstrate:

* cancellation
* timeout behavior
* connection-refused classification
* DNS failure classification
* resource cleanup
* bounded response handling

### Adapter tests

Adapters will be tested using captured platform metadata and controlled fixtures.

Tests must verify:

* deterministic discovery
* provenance preservation
* conflict handling
* no silent overwrites
* correct availability reasons
* correct capability scopes

### Probe portability tests

The same probe suite will run against fake providers representing:

* generic Linux
* restricted Umbrel
* StartOS bindings
* partially configured mixed stacks
* denied deep-scan access

Probe outputs should differ only where available evidence differs.

### Architecture tests

Automated checks will enforce that:

* probe packages do not import platform packages
* correlation packages do not import platform packages
* platform packages do not emit findings or diagnoses
* domain packages do not import adapters, storage, HTTP, or operating-system implementations
* privileged-helper clients are accessed only through approved capability providers

## Observability

Internal structured events should record:

```text
adapter loaded
component discovered
component merged
capability registered
capability unavailable
provider selected
provider ambiguity detected
probe skipped due to missing capability
probe executed with degraded capability
```

These events must not contain secrets, raw endpoint identifiers, IP addresses, onion addresses, or raw logs.

User-facing reports should summarize access limitations without exposing unnecessary implementation details.

Example:

```text
Restart-loop analysis was unavailable because this Umbrel application
does not have access to host service history.

Bitcoin RPC, chain state, and Electrum synchronization checks were completed.
```

A conceptual adapter contract:

```go
type Adapter interface {
    ID() string

    Detect(ctx context.Context) (DetectionResult, error)

    Discover(
        ctx context.Context,
        current InventorySnapshot,
    ) (DiscoveryResult, error)

    RegisterCapabilities(
        ctx context.Context,
        inventory InventorySnapshot,
        registry *CapabilityRegistry,
    ) error
}
```

A capability registry must support component-scoped resolution:

```go
type CapabilityRegistry interface {
    Register(descriptor CapabilityDescriptor, provider any) error

    Resolve(
        subject ComponentID,
        capability CapabilityID,
        policy ResolutionPolicy,
    ) (ResolvedCapability, error)

    ListForSubject(subject ComponentID) []CapabilityDescriptor
}
```

Go generics may be used internally to improve type safety, but the design must not require runtime reflection to invoke ordinary capabilities.

## Initial capability set

The first vertical slice should implement only the capabilities needed to prove the model:

```text
bitcoin.rpc.read/v1
network.tcp.connect/v1
filesystem.stat/v1
clock.read/v1
service.state.read/v1
```

Initial providers:

```text
manual Bitcoin RPC provider
Linux filesystem provider
Linux clock provider
systemd service-state provider
fake test providers
```

The first cross-platform proof should run the same Bitcoin chain-state probe using:

1. Manually configured RPC access on generic Linux
2. A platform-provided RPC binding in a simulated Umbrel environment
3. A simulated StartOS service binding

No probe code should change between these environments.

## Validation criteria

ADR-002 will be considered successfully implemented when:

1. Multiple adapters can be active during one scan.
2. The same component can be enriched by more than one adapter.
3. The same Bitcoin probe runs unchanged across Linux, Umbrel, and StartOS bindings.
4. A required missing capability produces `unknown`, never `pass`.
5. Optional missing capabilities reduce coverage without invalidating unrelated findings.
6. Ambiguous component bindings are reported rather than silently selected.
7. Deep scan adds privileged capabilities without changing probe semantics.
8. Probes cannot directly import platform implementations.
9. Platform adapters cannot emit findings or diagnoses.
10. Every observation records the capability and provider provenance used to obtain it.
11. Secret values remain inside provider boundaries.
12. The capability registry can resolve more than one provider for corroborating evidence.
13. A mixed systemd-and-Docker test environment can be modeled in one inventory graph.
14. Restricted-platform reports clearly identify coverage limitations.
15. Architecture tests enforce module direction automatically.

## Reconsideration triggers

This ADR should be revisited if:

1. Capability resolution becomes a major source of defects or user confusion.
2. Most probes require platform-specific behavior despite the abstraction.
3. Platform APIs cannot be represented without repeatedly bypassing capability boundaries.
4. Third-party adapters become a core requirement.
5. Mobile or remote agents need to negotiate capabilities over a network protocol.
6. Capability versioning becomes incompatible with the modular-monolith deployment model.
7. Performance measurements show that capability indirection materially affects scan execution.
8. The system begins performing state-changing remediation rather than read-only diagnosis.
9. A platform requires diagnostics to execute outside the main Redline process.
10. The component inventory model cannot represent real mixed-stack deployments without excessive ambiguity.

A reconsideration trigger requires a new ADR based on observed implementation evidence.

## Final decision statement

SATOSHI//REDLINE will model platform integration as a composition of narrowly scoped capabilities rather than as mutually exclusive platform-specific diagnostic engines.

Platform adapters will discover components, relationships, access paths, and capability providers. Probes will consume those capabilities to produce observations. Findings and cross-layer diagnoses will remain independent of the platform that supplied the evidence.

When a required capability is unavailable, denied, unsupported, or ambiguous, Redline will report explicit uncertainty.

The central rule established by this ADR is:

> Platforms determine what Redline can observe. They do not determine what the observations mean.
