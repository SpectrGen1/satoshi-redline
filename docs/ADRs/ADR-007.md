# ADR-007: Compile First-Party Probes into the Redline Binary for v0.1

* **Date:** 2026-07-30
* **Decision owners:** SATOSHI//REDLINE maintainers
* **Depends on:**

  * ADR-001 — Use a Go Modular Monolith for the Diagnostic Backend
  * ADR-002 — Use Capability-Based, Composable Platform Adapters
  * ADR-003 — Separate Observations, Findings, and Diagnoses
  * ADR-004 — Run the Main Daemon Unprivileged and Isolate Deep-Scan Access in an Optional Privileged Helper
  * ADR-005 — Do Not Persist Raw Logs or Protocol Responses
  * ADR-006 — Version External API and Report Schemas Independently from Internal Models
* **Scope:**

  * Probe implementation and registration
  * Probe trust model
  * Probe lifecycle and versioning
  * Runtime loading and extension policy
  * Probe resource limits
  * First-party contribution requirements
  * Future extension boundaries
* **Excluded from scope:**

  * Detailed correlation-rule language
  * Third-party marketplace design
  * Software-update mechanism
  * Package signing and release-distribution implementation
  * Hosted or remote-agent execution
  * Automated remediation plugins

## Context

SATOSHI//REDLINE must support a growing catalog of diagnostic checks across:

* Bitcoin Core and Bitcoin Knots
* Electrs and Fulcrum
* DATUM
* Stratum
* Tor
* systemd
* Docker
* Linux filesystems and mounts
* system resources
* Umbrel
* StartOS
* future Bitcoin infrastructure components

It is tempting to make the system extensible immediately through:

* runtime-loaded Go plugins
* shell-script probes
* external executables
* user-supplied JavaScript
* dynamically downloaded probe packages
* arbitrary WebAssembly modules
* YAML-defined command probes
* generic HTTP integrations
* a community plugin directory

Such mechanisms could make Redline appear flexible early.

They would also expand the trust boundary before the core diagnostic contracts have stabilized.

A probe is not merely a display extension.

Depending on its declared capabilities, a probe may be able to:

* authenticate to Bitcoin RPC
* connect to local or LAN services
* inspect filesystem state
* consume bounded logs
* inspect service state
* inspect Docker containers
* request privileged-helper operations
* process data that may contain credentials or identifiers
* produce evidence that affects health findings
* influence a root-cause diagnosis
* create user-facing remediation guidance

An unsafe or poorly designed probe could therefore:

* leak credentials
* retain raw protocol responses
* transmit information externally
* misuse privileged capabilities
* create false healthy states
* overstate a root cause
* consume excessive system resources
* crash the daemon
* create incompatible observation schemas
* silently change diagnostic meaning
* make reports impossible to interpret later

The extension boundary is especially sensitive because Redline’s core value depends on trust.

A user must be able to rely on the following:

* Safe Scan is actually safe.
* Deep Scan uses only declared access.
* No probe silently uploads data.
* Every finding is supported by evidence.
* Missing access becomes `unknown`.
* Probe behavior does not change without a Redline update.
* Reports can identify exactly which code produced each observation.
* A third-party extension cannot quietly gain the daemon’s full authority.

The v0.1 diagnostic model, capability catalog, observation schemas, and correlation behavior will still be evolving. Building a public plugin API before those contracts stabilize would either freeze immature interfaces or cause repeated compatibility breaks.

The architecture therefore needs to preserve future extensibility without exposing a premature runtime code-loading system.

## Decision

For v0.1, all production diagnostic probes will be **first-party Go code compiled into official SATOSHI//REDLINE binaries**.

Redline will not load executable diagnostic code dynamically at runtime.

The following mechanisms will not be supported in v0.1:

* Go native plugins
* shared-library probes
* user-supplied Go binaries
* shell-script probes
* arbitrary command probes
* Python or JavaScript probe runtimes
* dynamically downloaded probe packages
* remote probe execution
* user-supplied WebAssembly
* third-party in-process extensions
* plugin directories scanned at startup
* executable code embedded in configuration
* arbitrary regular-expression rules that emit findings
* arbitrary HTTP callbacks or webhooks from probes

All official probes will:

1. Live in the main Redline source repository.
2. Be reviewed and released with the Redline product.
3. Register through a compile-time-known probe registry.
4. Declare their capabilities, side effects, sensitivity, applicability, timeout, and resource cost.
5. Use capability interfaces rather than direct platform access.
6. Produce registered normalized observations.
7. Obey the persistence and privacy boundaries established by ADR-005.
8. Run under scheduler-enforced resource limits.
9. Record stable probe identity and version in every execution.
10. Be disabled or enabled through configuration without changing their executable behavior.

The compiled-probe decision applies to collection probes.

For v0.1, first-party finding evaluators and correlation rules will also be compiled into the binary. Declarative configuration may alter explicitly supported thresholds and tolerances, but it will not introduce executable logic.

The architecture will preserve a future path toward sandboxed extensions. That future mechanism will likely use:

* signed declarative rule packs for limited interpretation changes
* sandboxed WebAssembly for bounded diagnostic extensions
* or isolated external processes using a narrow versioned protocol

No future mechanism is selected by this ADR.

The central decision is:

> Redline v0.1 will be extensible through reviewed source changes and stable internal contracts, not through runtime loading of untrusted executable code.

## Decision drivers

The decision drivers, in priority order, are:

1. Preserve Redline’s privacy and security guarantees.
2. Keep the diagnostic evidence chain auditable.
3. Avoid freezing an immature plugin API.
4. Prevent runtime extensions from inheriting daemon authority.
5. Preserve deterministic packaging and reproducible builds.
6. Keep AMD64 and ARM64 deployment simple.
7. Limit crash and compatibility behavior during early development.
8. Allow strict review of every new capability request.
9. Ensure probe versions correspond to released software.
10. Preserve a credible future extension path without implementing it prematurely.

## Terminology

### Probe

A probe is a bounded collector that uses resolved capabilities to produce normalized observations or structured collection limitations.

A probe does not:

* determine cross-component root cause
* directly write to persistence
* render reports
* access the web UI
* invoke arbitrary operating-system commands
* resolve secrets itself unless it is the capability provider
* emit arbitrary user-facing prose as canonical evidence

Examples:

```text
bitcoin.chain-state
bitcoin.network-summary
bitcoin.index-state
electrum.protocol-state
electrum.chain-tip
datum.template-state
stratum.subscription
system.filesystem-capacity
system.service-state
system.restart-history
tor.socks-state
```

### Evaluator

An evaluator interprets observations and produces a finding under ADR-003.

Examples:

```text
bitcoin.chain.synchronized
electrum.chain.sync-lag
filesystem.capacity-pressure
service.restart-loop
```

Evaluators perform no external I/O.

### Correlation rule

A correlation rule combines findings, observations, and component relationships to produce a diagnosis.

Examples:

```text
wallet-backend.electrum-indexing-breakpoint
mining.datum-bitcoin-rpc-breakpoint
bitcoin.storage-capacity-risk
```

Correlation rules perform no external I/O.

### First-party probe

A first-party probe is implemented, reviewed, tested, and released by the SATOSHI//REDLINE project as part of an official build.

“First-party” refers to the release trust boundary, not necessarily the original author. A community-contributed probe becomes first-party only after it is accepted into the official source tree and passes the same review requirements as maintainer-written code.

### Runtime extension

A runtime extension is executable or interpreted logic supplied independently of the installed Redline binary and loaded or invoked during operation.

Runtime extensions are not supported in v0.1.

## Probe architecture

### Probe interface

The probe interface will remain narrow.

Conceptually:

```go
type Probe interface {
    Descriptor() ProbeDescriptor

    Run(
        ctx context.Context,
        target ProbeTarget,
        capabilities ResolvedCapabilities,
    ) ProbeResult
}
```

A probe receives:

* a context with a deadline
* an immutable target description
* only the capabilities resolved for that probe execution
* immutable scan metadata where required

A probe does not receive:

* the entire platform adapter registry
* the complete application configuration
* the SQLite store
* the report renderer
* arbitrary secret values
* unrestricted privileged-helper access
* the entire component graph unless its collection contract genuinely requires it
* a generic service locator

### Probe descriptor

Every probe must publish a static descriptor.

Conceptually:

```go
type ProbeDescriptor struct {
    ID                   ProbeID
    Version              ProbeVersion
    Stability            ProbeStability
    AppliesTo            []ComponentKind
    RequiredCapabilities []CapabilityRequirement
    OptionalCapabilities []CapabilityRequirement
    MinimumScanMode      ScanMode
    SideEffects          []SideEffectClass
    Sensitivity          SensitivityClass
    Cost                 ProbeCost
    Timeout              time.Duration
    ConcurrencyClass     ConcurrencyClass
    ObservationKinds     []ObservationKindRef
}
```

Example:

```text
Probe:
    bitcoin.chain-state

Version:
    1.0.0

Stability:
    stable

Applies to:
    bitcoin-node

Required capabilities:
    bitcoin.rpc.read/v1

Optional capabilities:
    clock.read/v1

Minimum scan mode:
    safe

Side effects:
    local-connect
    sensitive-read

Cost:
    low

Timeout:
    5 seconds

Produces:
    bitcoin.chain.tip/v1
    bitcoin.chain.state/v1
```

Descriptors are part of the internal probe contract and are also projected into safe API and report metadata where useful.

### Probe identity

Probe IDs will be stable namespaced strings.

Examples:

```text
bitcoin.chain-state
bitcoin.network-summary
electrum.chain-tip
datum.template-state
system.filesystem-capacity
```

A probe ID identifies one coherent evidence-collection responsibility.

A materially different collection responsibility requires a new probe ID.

### Probe version

Every probe will have a semantic implementation version.

A probe-version change records changes to collection behavior, including:

* supported protocol variants
* error classification
* data extraction
* timeout behavior
* optional evidence collection
* observation-production rules

A patch version may represent an implementation correction that does not change valid normalized meaning.

A minor version may add backward-compatible collection support or optional observations.

A major version is required when:

* collection semantics change incompatibly
* the same source state could produce materially different normalized evidence
* required capabilities change incompatibly
* an existing observation’s meaning changes
* error classifications change in a way that alters findings
* side-effect behavior changes materially

Observation-kind versions remain independently governed under ADR-003 and ADR-006.

A probe version does not replace observation-schema versioning.

## Compile-time registration

### Registry construction

Official probes will register through explicit constructors known at build time.

Conceptually:

```go
func RegisterBuiltInProbes(registry *ProbeRegistry) error {
    probes := []Probe{
        bitcoin.NewRPCReachabilityProbe(),
        bitcoin.NewChainStateProbe(),
        bitcoin.NewNetworkSummaryProbe(),
        electrum.NewChainTipProbe(),
        system.NewFilesystemCapacityProbe(),
    }

    for _, probe := range probes {
        if err := registry.Register(probe); err != nil {
            return err
        }
    }

    return nil
}
```

Registration will be explicit rather than based on:

* package initialization side effects
* filesystem discovery
* reflection
* naming conventions
* plugin directories
* environment-controlled shared libraries

This makes the active probe catalog visible in code review.

### Duplicate registration

The registry must reject:

* duplicate probe IDs
* duplicate incompatible versions
* invalid descriptors
* unregistered observation kinds
* undeclared capabilities
* invalid timeout or cost metadata
* contradictory scan-mode declarations
* descriptors with forbidden side effects

The daemon must fail startup rather than silently choose one duplicate probe.

### Catalog manifest

Every official build will expose a generated probe catalog containing:

```text
probe ID
probe version
stability
supported component kinds
required capabilities
optional capabilities
scan mode
side-effect classes
sensitivity class
observation kinds
build identifier
```

The catalog will be available through:

* the local metadata API
* CLI version or diagnostic commands
* report producer metadata where relevant
* release artifacts

This allows a report reader or support technician to determine which collector implementation was present in the producing release.

## Probe stability lifecycle

Probes will use an explicit stability lifecycle:

```text
experimental
stable
deprecated
removed
```

### Experimental

An experimental probe:

* is compiled into the official binary
* is disabled by default unless explicitly included in an experimental scan profile
* may change more rapidly
* still obeys all security and privacy rules
* must use versioned observation kinds
* must not weaken persistence boundaries
* must be clearly labeled in output

“Experimental” does not mean unrestricted.

### Stable

A stable probe:

* is eligible for default scan profiles
* has documented capability requirements
* has contract and privacy tests
* follows normal compatibility rules
* may not change meaning silently

### Deprecated

A deprecated probe:

* remains available for a defined transition period
* identifies its replacement where one exists
* is excluded from new default profiles when appropriate
* may continue to support old environments or report reproducibility

### Removed

A removed probe is no longer executable in the current release.

Its historical:

* probe ID
* versions
* observation kinds
* finding codes
* report interpretation

must remain documented so old reports remain readable.

Removal of a probe does not permit reuse of its ID for different behavior.

## Probe discovery and applicability

The scan planner will select probes based on:

* discovered component kind
* declared component relationships
* available capabilities
* selected scan mode
* configured scan profile
* probe stability
* user-disabled probe settings
* supported component implementation or version
* resource budget

Probe selection will not depend on runtime plugin discovery.

A probe may declare implementation constraints.

Example:

```text
electrum.fulcrum-stats
applies when:
    component kind is electrum-backend
    implementation is Fulcrum
    supported version range matches
    required stats capability is available
```

If the implementation cannot be determined, an implementation-specific probe is not assumed applicable.

The general Electrum protocol probe may still run.

## Capability restrictions

Under ADR-002, probes must use declared capabilities.

A probe may not directly:

* open the Docker socket
* read systemd D-Bus
* invoke `journalctl`
* read protected files
* contact the privileged helper
* inspect arbitrary processes
* locate RPC credentials
* inspect the platform
* execute shell commands

Capability providers perform those operations.

The scheduler passes only the resolved capability interfaces declared by the probe.

The probe registry and architecture tests must prevent undeclared capability acquisition.

A probe requesting a new privileged or sensitive capability must undergo explicit review.

Adding a probe is not sufficient authorization to broaden the privileged helper.

## Side-effect model

Although v0.1 probes are read-only in operational intent, they may still cause observable activity.

Each probe must declare side-effect classes such as:

```text
pure-local-read
sensitive-local-read
local-connect
lan-connect
external-connect
tor-connect
privileged-read
```

Examples:

* Parsing already collected typed state may be `pure-local-read`.
* Calling Bitcoin RPC may be `sensitive-local-read` and `local-connect`.
* Testing a miner’s Stratum listener may be `lan-connect`.
* Testing Tor egress may be `external-connect` and `tor-connect`.
* Reading protected restart history may be `privileged-read`.

The scan planner will enforce scan-profile policy.

No probe may introduce an undeclared external connection.

External-connect probes will not run merely because they are compiled into the binary.

## Configuration boundaries

Configuration may control approved probe behavior without injecting code.

Permitted configuration includes:

* enable or disable a probe
* select safe or deep scan profile
* define component bindings
* choose among documented probe modes
* configure bounded timeouts
* configure supported warning thresholds
* configure expected service relationships
* enable an explicitly declared external-connect check
* configure scan cadence
* select supported protocol variants

Configuration must not provide:

* shell commands
* executable paths for arbitrary probes
* source code
* JavaScript
* Python
* WebAssembly
* arbitrary SQL
* arbitrary filesystem reads
* arbitrary HTTP requests
* arbitrary RPC methods
* arbitrary log-to-finding expressions
* unrestricted regular expressions that emit health conclusions
* arbitrary capability identifiers

### Threshold configuration

Some evaluators require user-adjustable thresholds.

Examples:

```text
minimum disk free capacity
maximum Electrum block lag
maximum acceptable block age
restart-loop window
DATUM template-age threshold
```

Thresholds will be:

* explicitly supported by a specific evaluator
* typed
* bounded
* validated
* recorded in finding provenance
* included in report evidence where relevant

A threshold changes interpretation, not collection.

A probe must not silently change which raw fields it extracts because a user entered an unrelated configuration value.

### Signature and classifier data

First-party probes may use bundled data such as:

* known log-event signatures
* protocol-version compatibility tables
* implementation-identification patterns
* safe error-code mappings

These data files are considered part of the official probe implementation.

They will be:

* committed to the repository
* reviewed
* versioned
* embedded in or packaged with the official binary
* covered by tests
* updated only through a Redline software release

Redline v0.1 will not download classifier or signature packs independently.

## Resource governance

Every probe will run under engine-enforced budgets.

### Time limits

Every probe must:

* accept `context.Context`
* have a default timeout
* support cancellation where the underlying capability permits it
* return a structured timeout outcome
* avoid starting untracked work after cancellation

A probe cannot disable its deadline.

### Concurrency limits

Probes will be assigned concurrency classes.

Examples:

```text
network-light
network-heavy
filesystem-light
log-heavy
privileged
serial-per-component
```

The scheduler will enforce:

* global scan concurrency
* per-component concurrency
* per-provider concurrency
* per-capability constraints
* privileged-helper limits
* network connection limits

### Memory and data limits

Probe inputs and outputs must be bounded.

A probe descriptor or provider contract will define limits such as:

* maximum response size
* maximum record count
* maximum event count
* maximum collection window
* maximum observation count
* maximum string length
* maximum map or list size

A probe that encounters larger input must truncate safely or return a structured limitation.

It must not increase limits silently.

### Output validation

Before observations enter the evaluation pipeline, the engine will validate:

* observation kind registration
* schema version
* field bounds
* timestamps
* sensitivity class
* provenance
* component reference
* probe-execution reference
* declared output membership

A probe may not emit an observation kind it did not declare.

## Failure isolation

Compiled probes run inside the `redlined` process and therefore share its address space.

This creates an accepted limitation:

> Compiled first-party probes are not a security sandbox.

The following safeguards will limit accidental failures:

* per-probe panic recovery
* per-probe deadlines
* concurrency limits
* bounded capability responses
* output validation
* no direct persistence access
* no direct privileged-helper access
* no arbitrary command execution
* structured error conversion
* probe-specific fuzz testing
* race testing
* cancellation testing

A recovered probe panic will produce:

```text
probe outcome: failed
internal category: probe_panic
affected findings: unknown
```

The panic must not be presented as target-component failure.

The engine will record safe metadata such as:

* probe ID
* probe version
* component alias
* panic category
* build ID

It must not log raw probe input or sensitive local variables.

### Unrecoverable failures

Some failures, such as memory corruption, fatal runtime errors, or process-wide resource exhaustion, may still terminate the daemon.

This risk is accepted for reviewed first-party v0.1 probes.

Third-party code will not be admitted into this failure domain.

If probe-related crashes become a material operational problem, isolated probe workers become a reconsideration trigger.

## Security and privacy requirements

Every first-party probe must demonstrate that it:

1. Requests only necessary capabilities.
2. Performs only declared side effects.
3. Uses bounded reads.
4. Does not retain raw protocol or log data.
5. Does not log sensitive values.
6. Produces registered observations only.
7. Does not write directly to persistence.
8. Does not make undeclared network connections.
9. Does not expose credential material.
10. Correctly distinguishes access failure from target failure.
11. Returns `unknown` when required evidence is unavailable.
12. Does not invoke destructive actions.
13. Does not bypass the privileged-helper operation catalog.
14. Does not create hidden telemetry.
15. Does not send data to external services.

A new probe that cannot meet these requirements will not be accepted as a standard v0.1 probe.

## First-party contribution process

A community member may contribute a probe to the official repository.

Once accepted and shipped, that probe is first-party Redline code.

A probe contribution must include:

### Design documentation

* diagnostic question being answered
* target component kinds
* required and optional capabilities
* expected side effects
* data sensitivity
* observation kinds produced
* relevant findings enabled
* expected failure modes
* unsupported environments
* timeout and resource budgets

### Schemas

* versioned observation schemas
* field-purpose documentation
* field bounds
* sensitivity classifications
* API and report projections where applicable

### Tests

* successful collection
* target failure
* access failure
* permission denial
* timeout
* malformed response
* oversized response
* unsupported version
* partial evidence
* cancellation
* secret canaries
* unknown-field handling
* panic containment where practical
* architecture-boundary enforcement

### Security review

The contribution must answer:

* Could this expose credentials?
* Could it create external traffic?
* Could it broaden privileged access?
* Could it persist raw data?
* Could arbitrary user input alter execution?
* Could the target induce excessive resource use?
* Could the probe create a false pass?
* Could a malformed response crash the daemon?

### Diagnostic review

The contribution must demonstrate:

* why the observations are sufficient
* what remains unknown
* how the evaluator distinguishes pass, warning, failure, and unknown
* how the result relates to dependency-graph diagnosis
* whether the check duplicates an existing probe

Maintainer acceptance, not authorship, determines inclusion in the official catalog.

## Reproducibility and build identity

An official Redline build must be able to report:

* product version
* build identifier
* source revision
* probe catalog
* probe versions
* observation schema versions
* evaluator versions
* correlation-rule versions

A report will record the relevant versions that produced its contents.

This does not require embedding the complete source code in the report.

Official releases should aim for reproducible builds so that the distributed binary can be tied to the reviewed source tree.

The exact release-signing and reproducible-build process will be defined separately.

## Updates

New or changed probes will arrive through a normal Redline software update.

The daemon will not independently fetch executable probe updates.

This provides:

* one reviewed release unit
* one compatibility matrix
* one rollback unit
* one signed distribution boundary
* predictable probe behavior

A probe update may be urgent due to:

* protocol changes
* privacy defects
* false-positive behavior
* false-pass behavior
* target-version incompatibility
* security defects

Such updates still ship as Redline releases.

A future signed data-only update channel may be considered for narrow declarative catalogs, but it is not authorized by this ADR.

## Probe deactivation

Redline must be able to disable a compiled probe without removing it from the binary.

Reasons may include:

* user preference
* incompatible target version
* excessive resource cost
* platform restriction
* known defect
* experimental status
* temporary safety block
* scan-profile exclusion

Deactivation may occur through:

* built-in compatibility rules
* local administrator configuration
* packaged emergency denylist included in a Redline update

Redline v0.1 will not retrieve a remote kill switch.

When a probe is disabled, the scan report must distinguish:

```text
not applicable
unsupported
disabled by user
disabled by compatibility policy
not selected in this scan profile
```

A disabled required check may reduce coverage. It must not become a pass.

## Relationship to evaluators and correlation rules

This ADR primarily governs probes, but the same trust policy applies to executable evaluators and correlation rules in v0.1.

They will be:

* first-party
* compiled
* versioned
* deterministic
* free of external I/O
* tested against fixtures
* unable to persist directly
* unable to acquire capabilities

User configuration may provide bounded typed parameters.

It may not define arbitrary executable diagnostic logic.

### Why probes and rules remain distinct

The compiled-release decision does not collapse the architecture.

The pipeline remains:

```text
compiled first-party probe
        ↓
normalized observation
        ↓
compiled first-party evaluator
        ↓
finding
        ↓
compiled first-party correlation rule
        ↓
diagnosis
```

This preserves the semantic boundaries established by ADR-003 and makes a future declarative-rule system possible without redesigning collection.

## Future extension path

This ADR intentionally preserves future extension options without selecting one.

### Declarative rule packs

A future rule pack could support constrained operations such as:

* threshold comparison
* observation-presence checks
* dependency-edge predicates
* event-count thresholds
* known-safe recommendation selection

A declarative rule pack must not:

* open sockets
* read files
* access credentials
* call the privileged helper
* execute commands
* write arbitrary output
* introduce raw fields

Signed declarative rules may become suitable before executable third-party probes.

### Sandboxed WebAssembly

WebAssembly is a candidate for future executable extensions because it can provide:

* no ambient host access
* explicit imported capabilities
* memory limits
* execution-fuel limits
* deterministic interfaces
* language-neutral extension development

However, WebAssembly would still require careful design for:

* capability delegation
* schema registration
* signature trust
* extension identity
* output validation
* network policy
* secret handling
* compatibility
* report provenance
* denial-of-service resistance

The existence of a WebAssembly runtime does not automatically make extensions safe.

### External process protocol

A future extension may run as a separate unprivileged process with:

* a versioned request protocol
* narrowly projected inputs
* no secret values
* bounded execution
* operating-system sandboxing
* validated outputs

This could provide stronger crash isolation than in-process WebAssembly in some environments.

It would increase packaging and lifecycle complexity.

### Platform-native extensions

Umbrel or StartOS packages may expose platform-specific capabilities.

They do not become diagnostic plugins merely because they are platform-specific.

Diagnostic meaning must remain in reviewed Redline probes and rules unless a future extension ADR says otherwise.

## Alternatives considered

### Alternative A: Go native plugins

Go’s native plugin mechanism is rejected.

It creates tight coupling to:

* Go compiler version
* package dependency versions
* build flags
* internal package layouts
* platform support
* host-process memory and privileges

It also provides no meaningful sandbox.

A plugin would execute with the daemon’s full in-process authority.

### Alternative B: Shell-script probes

Shell-script probes are rejected.

They would create:

* arbitrary command execution
* unstable text parsing
* quoting and injection risk
* inconsistent platform behavior
* difficult resource limits
* weak typing
* unclear capability use
* dangerous privileged-helper integration
* difficult privacy review

A fixed command may be used inside a typed capability provider under ADR-004, but that does not create a general shell-probe mechanism.

### Alternative C: External executable probes

Arbitrary external probe executables are rejected for v0.1.

They provide some crash isolation but introduce:

* binary trust and signing
* installation lifecycle
* protocol compatibility
* process sandboxing
* secret delegation
* capability negotiation
* output validation
* cross-architecture packaging
* update coordination

This may be reconsidered after the core contracts stabilize.

### Alternative D: User-supplied JavaScript or Python

Embedded scripting runtimes are rejected.

They would increase:

* runtime size
* attack surface
* dependency management
* execution variability
* sandbox complexity
* risk of arbitrary I/O
* platform packaging burden

### Alternative E: User-supplied WebAssembly from the beginning

WebAssembly is not selected for v0.1.

Although safer than native plugins, it still requires a stable host API and trust model.

Designing that API before capability, observation, and report contracts have matured would freeze immature boundaries.

### Alternative F: Declarative YAML command checks

Example:

```yaml
command: journalctl
arguments:
  - ...
success_regex: ...
```

This is rejected.

It is a shell-probe system expressed as configuration.

It would allow arbitrary host inspection and weakly typed health conclusions.

### Alternative G: Remote probe marketplace

A marketplace is rejected for v0.1.

It would require:

* author identity
* signing
* review policy
* updates
* revocation
* compatibility
* sandboxing
* permission presentation
* malicious-extension response
* user trust UX

These problems are unrelated to proving Redline’s core diagnostic value.

### Alternative H: Hard-code every check without a registry

This is also rejected.

Compiled probes still need:

* stable identity
* descriptors
* versioning
* capability declarations
* lifecycle state
* resource governance
* discoverability
* tests

A registry provides controlled internal extensibility without runtime code loading.

### Alternative I: Separate process for every built-in probe

This would provide stronger crash isolation.

It is rejected for v0.1 because it would introduce:

* process startup overhead
* inter-process schema design
* resource coordination
* packaging complexity
* debugging overhead
* more difficult appliance deployment

The need for process isolation should be established through actual failures or future third-party execution.

### Alternative J: Compile platform-specific forks with different probe logic

This is rejected.

Umbrel, StartOS, and Linux packages may expose different capabilities, but should ship the same diagnostic semantics wherever possible.

Platform packages should not silently fork probe behavior.

## Consequences

### Positive consequences

* Every production probe is part of a reviewed release.
* Probe behavior is reproducible from the installed build.
* No runtime extension can inherit daemon authority.
* The privacy boundary remains easier to audit.
* Capability requests remain visible in source review.
* Reports can identify the exact probe implementation used.
* AMD64 and ARM64 packaging remains simple.
* The system avoids unstable Go plugin compatibility.
* Probe and schema evolution remain coordinated.
* The core team can change internal contracts before publishing a plugin API.
* Community contributions remain possible through the normal source-review process.
* Resource limits and output validation apply uniformly.
* A later sandboxed extension system can build on mature contracts.

### Negative consequences

* Users cannot add proprietary or local probes without rebuilding Redline.
* Community extensions require upstream acceptance.
* New protocol support must wait for a Redline release.
* The official binary will grow as the probe catalog expands.
* A defective built-in probe shares the daemon’s process.
* Redline cannot initially support a broad extension ecosystem.
* Maintainers become the review bottleneck for new probes.
* Platform vendors cannot independently ship diagnostic logic into Redline.
* Emergency probe fixes require a product update.
* Some advanced users may view the system as less flexible than script-based monitoring tools.

### Neutral consequences

* Users may still configure targets and supported thresholds.
* Platform adapters remain composable under ADR-002.
* Probe registration remains modular even though it is compile-time.
* Experimental probes may ship disabled by default.
* Future extension mechanisms remain possible.
* The web UI and mobile clients do not need to know whether a probe is compiled or sandboxed as long as contracts remain stable.

## Risks and mitigations

### Risk: The built-in probe catalog becomes monolithic and difficult to maintain

**Mitigations:**

* Organize probes by protocol and component domain.
* Keep probe interfaces narrow.
* Require stable descriptors.
* Separate collection from evaluation.
* Use shared capability clients where semantics match.
* Avoid one probe that collects an entire subsystem indiscriminately.
* Deprecate redundant probes deliberately.

### Risk: Maintainers become a contribution bottleneck

**Mitigations:**

* Publish contribution templates.
* Provide reusable contract-test suites.
* Document capability and schema requirements.
* Maintain synthetic integration environments.
* Allow community ownership of accepted first-party probe modules.
* Revisit sandboxed extensions when demand is demonstrated.

### Risk: Compiled probes increase binary size

**Mitigations:**

* Avoid embedding large raw datasets.
* Use compact versioned classifier tables.
* Measure binary growth.
* Remove obsolete implementation dependencies.
* Reconsider optional build features only if size becomes material on supported platforms.

### Risk: One probe crashes the daemon

**Mitigations:**

* Recover probe panics at scheduler boundaries.
* Fuzz protocol decoders.
* Enforce input bounds.
* Use contexts and deadlines.
* Keep raw parsers small.
* Avoid unsafe code.
* Add process isolation if real crash frequency justifies it.

### Risk: A built-in probe misuses a capability

**Mitigations:**

* Pass only declared resolved capabilities.
* Add architecture tests against direct platform imports.
* Review new capability requirements.
* Record capability usage in execution provenance.
* Enforce provider-side authority independently.
* Keep privileged-helper operations narrow even for trusted probes.

### Risk: Configuration becomes an implicit programming language

**Mitigations:**

* Support only typed documented options.
* Reject arbitrary commands and expressions.
* Bound thresholds.
* Do not expose generic request builders.
* Review additions for computational expressiveness.
* Require a new ADR before introducing a rule language.

### Risk: A protocol changes faster than Redline releases

**Mitigations:**

* Prefer stable protocol surfaces.
* Preserve structured unsupported-version outcomes.
* Release focused compatibility updates.
* Keep protocol decoders modular.
* Consider signed data-only compatibility catalogs later for narrowly safe cases.

### Risk: Experimental probes become de facto stable

**Mitigations:**

* Disable them by default.
* Label them in reports and the UI.
* Exclude them from default health summaries unless explicitly selected.
* Require an explicit graduation review.
* Do not let prolonged existence substitute for stabilization.

### Risk: Probe versions become meaningless

**Mitigations:**

* Define version-change rules.
* Record versions in executions and reports.
* Require version updates during code review when semantics change.
* Add fixtures comparing old and new behavior.
* Keep observation versions separate.

### Risk: Future plugin design is constrained by internal Go interfaces

**Mitigations:**

* Treat Go probe interfaces as internal.
* Version external schemas independently.
* Define future plugin contracts in language-neutral terms.
* Expose capabilities through narrow semantic operations.
* Do not promise that third-party extensions will implement the current Go interface.

## Testing strategy

### Probe contract tests

Every probe must pass a reusable contract suite verifying:

* descriptor validity
* stable identity
* declared output kinds
* deadline compliance
* cancellation behavior
* capability-denial behavior
* missing-required-capability behavior
* optional-capability degradation
* bounded observation count
* output-schema validation
* no direct persistence access
* no undeclared side effects

### Protocol-decoder tests

Protocol probes must include:

* valid messages
* malformed messages
* oversized messages
* unexpected fields
* unsupported versions
* partial responses
* timeouts
* connection resets
* malicious nesting
* invalid encoding
* reflected-secret error text

### Privacy tests

Canary secrets must be inserted into:

* RPC responses
* protocol errors
* logs
* status documents
* capability errors

Tests must verify that they do not appear in:

* observations
* findings
* diagnoses
* logs
* SQLite
* API responses
* reports
* panic output

### Resource tests

Tests must verify:

* timeout enforcement
* global concurrency limits
* per-provider concurrency
* memory bounds
* response-size limits
* event-count limits
* cancellation cleanup
* no lingering goroutines after repeated scans

### Registry tests

The registry must reject:

* duplicate IDs
* invalid versions
* missing descriptors
* unknown capabilities
* undeclared observation kinds
* forbidden side effects
* invalid scan modes
* invalid stability states
* invalid resource budgets

### Architecture tests

Automated checks will enforce that:

* probe packages do not import storage implementations
* probe packages do not import API or report packages
* probes do not import platform implementations
* probes do not import privileged-helper clients
* evaluator and correlation packages do not perform I/O
* no plugin scanning or dynamic loading path exists
* production configuration cannot specify executable code
* only registered probes can enter scan plans

### Build-manifest tests

CI will verify that:

* the generated probe catalog matches registered probes
* probe versions are present
* observation schemas exist
* official build metadata includes the catalog digest
* AMD64 and ARM64 builds contain the expected catalog
* platform packaging does not silently omit core probes

## Validation criteria

ADR-007 will be considered successfully implemented when:

1. Every production probe is compiled into an official Redline binary.
2. The daemon scans no plugin directory.
3. Configuration cannot provide executable probe code.
4. No Go native plugin mechanism is linked or used.
5. No arbitrary shell or external-executable probe interface exists.
6. Every probe has a stable ID and version.
7. Every probe publishes a valid static descriptor.
8. Every probe declares required and optional capabilities.
9. Every probe declares side-effect and sensitivity classes.
10. Every probe declares its observation kinds.
11. The registry rejects invalid or duplicate registrations.
12. The active probe catalog is exposed through safe metadata.
13. Reports record the relevant probe versions.
14. Probes receive only resolved capabilities.
15. Probes cannot access persistence directly.
16. Probes cannot call the privileged helper directly.
17. Per-probe timeouts and cancellation are enforced.
18. Scheduler concurrency and resource limits are enforced.
19. Probe panics produce internal failures and unknown findings rather than target failures.
20. Raw probe input does not cross the normalization boundary.
21. Experimental probes are disabled by default.
22. Stable probes pass contract, privacy, malformed-input, and resource tests.
23. User thresholds are typed, bounded, and recorded in finding provenance.
24. New probes arrive only through a Redline software release.
25. AMD64 and ARM64 official builds expose the same core probe catalog.
26. Platform packages do not fork diagnostic probe semantics.
27. First-party community contributions follow the same review path as maintainer code.
28. No remote kill switch or executable probe update channel exists.
29. The first Bitcoin and system probes run through the same registry and scheduler.
30. The architecture leaves future language-neutral sandboxing possible without making the Go interface public.

## Reconsideration triggers

This ADR should be revisited if:

1. Users demonstrate substantial demand for local custom probes.
2. Community contribution volume exceeds the maintainers’ review capacity.
3. Platform vendors require independently released diagnostics.
4. Proprietary integrations become commercially important.
5. Protocol changes require updates more rapidly than full Redline releases can support.
6. Built-in probes repeatedly crash or destabilize the daemon.
7. Binary size becomes material on supported hardware.
8. A stable capability and observation contract suitable for third parties emerges.
9. Signed declarative rule packs can safely cover meaningful extension use cases.
10. A WebAssembly host can enforce strict capability, memory, execution, and privacy limits.
11. External-process isolation becomes operationally practical.
12. A third-party ecosystem becomes a core product goal.
13. A supported platform requires diagnostics to execute outside the Redline process.
14. First-party-only distribution materially prevents adoption.
15. Independent security review recommends stronger isolation even for built-in probes.

A reconsideration trigger does not authorize ad hoc runtime loading.

Any executable extension mechanism requires a new ADR defining:

* extension identity
* trust and signing
* installation and update lifecycle
* revocation
* capability grants
* secret access
* network access
* privileged-helper access
* resource limits
* sandbox guarantees
* schema registration
* version negotiation
* report provenance
* crash isolation
* platform support
* user-consent UX

## Final decision statement

SATOSHI//REDLINE v0.1 will ship only first-party diagnostic probes, evaluators, and correlation rules compiled into official Redline binaries.

Probes will remain modular and registry-driven, but their executable behavior will not be supplied or replaced at runtime.

Configuration may select probes, define targets, and adjust explicitly supported bounded parameters. It may not introduce commands, scripts, executable rules, arbitrary requests, or unreviewed capabilities.

Every probe will declare its identity, version, applicability, capabilities, side effects, sensitivity, resource budget, and observation outputs. The scheduler and capability system will enforce those declarations.

Community-written probes may become first-party through normal source review and release.

A future sandboxed extension system remains possible, but it will be designed only after Redline’s capability, evidence, privacy, and compatibility contracts have matured.

The central rule established by this ADR is:

> Redline will stabilize the trust boundary before it opens the extension boundary.
