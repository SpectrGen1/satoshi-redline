# ADR-003: Separate Observations, Findings, and Diagnoses

* **Date:** 2026-07-30
* **Decision owners:** SATOSHI//REDLINE maintainers
* **Depends on:**

  * ADR-001 — Use a Go Modular Monolith for the Diagnostic Backend
  * ADR-002 — Use Capability-Based, Composable Platform Adapters
* **Scope:** Diagnostic data model, evidence lineage, uncertainty, health interpretation, cross-layer conclusions, persistence, reports, and public diagnostic schemas

## Context

SATOSHI//REDLINE must explain where a Bitcoin infrastructure stack stopped behaving correctly.

To do this honestly, the system must distinguish between three fundamentally different kinds of information:

1. A fact collected from a system.
2. An interpretation of one or more facts.
3. A conclusion about how failures across multiple components relate.

For example:

```text
Bitcoin reports block height 910,123.
```

is not the same kind of statement as:

```text
Bitcoin is synchronized.
```

The first is an observation. The second is a finding based on thresholds, time, network context, and additional evidence.

Likewise:

```text
Fulcrum is 47 blocks behind Bitcoin.
```

does not by itself establish:

```text
Fulcrum is the root cause of Sparrow displaying stale wallet data.
```

That conclusion requires a known dependency relationship and evidence about the other components in the path.

If these layers are combined into one generic result object, several problems arise:

* Raw facts become indistinguishable from health judgments.
* Threshold changes can alter the apparent meaning of historical data.
* Platform access failures can be mistaken for component failures.
* A downstream symptom can be mislabeled as a root cause.
* The UI may present certainty that the engine does not possess.
* Reports cannot show how a conclusion was reached.
* Correlation rules become difficult to test independently.
* Support personnel cannot distinguish observed evidence from Redline’s interpretation.
* Future rule improvements require rerunning system probes unnecessarily.
* “Unknown” becomes an ambiguous bucket for missing evidence, unsupported checks, and inconclusive reasoning.

The original product specification proposed a single result shape:

```json
{
  "status": "pass | warning | failure | unknown",
  "component": "",
  "layer": "",
  "evidence": [],
  "impact": "",
  "recommendation": ""
}
```

This shape is suitable as a simplified presentation model, but it is not sufficiently precise as Redline’s internal diagnostic model.

The internal architecture requires stronger separation.

## Decision

SATOSHI//REDLINE will model diagnostic reasoning as a staged, traceable pipeline:

```text
Probe execution
      ↓
Observations
      ↓
Findings
      ↓
Diagnoses
      ↓
Incidents and reports
```

The three central domain entities will be:

* **Observation** — a normalized fact collected from a capability provider
* **Finding** — a health interpretation derived from observations
* **Diagnosis** — a cross-component explanation derived from findings and dependency relationships

These entities will be independently versioned, persisted, and addressable by stable identifiers.

A later-stage object may reference earlier-stage objects, but an earlier-stage object may not contain conclusions from a later stage.

The dependency direction is:

```text
Diagnosis → Findings → Observations
```

Never:

```text
Observation → embedded diagnosis
```

Every user-visible failure, warning, or root-cause claim must be traceable to evidence through this chain.

The core semantic rule established by this ADR is:

> Redline must preserve the boundary between what the system reported, what Redline inferred from it, and what Redline believes explains the wider failure.

## Decision drivers

The decision drivers, in priority order, are:

1. Prevent unsupported or overstated conclusions.
2. Preserve evidence for every health claim.
3. Make uncertainty explicit and explainable.
4. Support cross-layer root-cause analysis.
5. Allow diagnostic rules to evolve independently of data collection.
6. Distinguish access failures from target-system failures.
7. Preserve historical meaning when thresholds or rules change.
8. Support expert inspection without overwhelming non-expert users.
9. Make diagnostic logic deterministic and independently testable.
10. Provide stable contracts for reports, mobile clients, and future support tooling.

## Semantic model

### Probe execution

A probe execution records an attempt to collect evidence.

It answers:

* Which probe ran?
* Against which component?
* Which capability provider was used?
* When did it run?
* Did collection complete?
* Was collection partial?
* Why was evidence unavailable?
* Which observations were produced?

A probe execution is necessary because failed collection cannot be represented honestly as an observation about the target.

For example:

```text
Redline lacked permission to read the Bitcoin RPC cookie.
```

is information about Redline’s access path.

It is not evidence that Bitcoin RPC is down.

A conceptual probe execution structure is:

```go
type ProbeExecution struct {
    ID              ProbeExecutionID
    ScanID          ScanID
    ProbeID         ProbeID
    ProbeVersion    string
    ComponentID     ComponentID
    CapabilityUses  []CapabilityUse
    StartedAt       time.Time
    FinishedAt      time.Time
    Outcome         ProbeOutcome
    Limitation      *CollectionLimitation
    ObservationIDs  []ObservationID
}
```

Supported outcomes should include:

```text
completed
partial
unavailable
failed
cancelled
```

Definitions:

* **completed** — the probe collected all evidence required by its contract.
* **partial** — some useful evidence was collected, but the probe could not complete its full collection plan.
* **unavailable** — the probe could not run because a required capability or binding was unavailable.
* **failed** — the probe ran but encountered an execution or protocol error.
* **cancelled** — the scan or probe was intentionally cancelled.

These outcomes describe evidence collection. They do not describe the health of the target component.

### Observation

An observation is a normalized, immutable fact obtained from a capability provider during a probe execution.

Examples:

```text
Bitcoin reported block height 910,123.
Bitcoin reported initialblockdownload=false.
The most recent block timestamp was 184 seconds old.
Fulcrum reported height 910,076.
The DATUM Stratum port accepted a TCP connection.
bitcoind.service had restarted 11 times in 20 minutes.
The Bitcoin data volume had 8.2 GiB available.
```

An observation must not contain a health status.

For example, the following is not an observation:

```text
Disk space is critically low.
```

It is a finding.

The corresponding observation is:

```text
The Bitcoin data volume has 8.2 GiB available and 3.1% free.
```

A conceptual observation structure is:

```go
type Observation struct {
    ID               ObservationID
    ScanID           ScanID
    ProbeExecutionID ProbeExecutionID
    ComponentID      ComponentID
    Kind             ObservationKind
    SchemaVersion    uint
    ObservedAt       time.Time
    Validity         ValidityWindow
    Value            ObservationValue
    Quality          EvidenceQuality
    Provenance       EvidenceProvenance
    Sensitivity      SensitivityClass
}
```

An observation must include:

* a typed observation kind
* the component being observed
* the time of observation
* the probe execution that produced it
* the capability provider used
* a normalized value
* evidence-quality metadata
* sensitivity classification
* schema version

Observation values must be typed and bounded. They must not be arbitrary unstructured maps when a stable domain type can be defined.

Good:

```go
type BitcoinChainTipObservation struct {
    BlockHeight         int64
    HeaderHeight        int64
    BestBlockHashAlias  string
    BlockTime           time.Time
    InitialBlockDownload bool
}
```

Poor:

```go
map[string]any
```

Raw RPC responses, unrestricted command output, and unredacted logs are not observations and must not be persisted as though they were normalized evidence.

### Finding

A finding is a health assertion derived from one or more observations, probe-execution outcomes, or narrowly defined absence-of-evidence conditions.

Examples:

```text
Bitcoin is synchronized.
Bitcoin RPC is unreachable from Redline.
Fulcrum is unacceptably behind Bitcoin.
The Bitcoin data volume is approaching exhaustion.
DATUM has not refreshed its template since the Bitcoin tip changed.
Restart-loop analysis is unavailable because service history could not be read.
```

A finding answers:

* What condition was evaluated?
* What was the result?
* Which component does it concern?
* Which evidence supports it?
* Which rule produced it?
* How severe is the impact?
* How confident is Redline?
* What evidence was unavailable?
* How long should the finding remain valid?

A conceptual finding structure is:

```go
type Finding struct {
    ID                  FindingID
    ScanID              ScanID
    Code                FindingCode
    EvaluatorID         EvaluatorID
    EvaluatorVersion    string
    ComponentID         ComponentID
    Applicability       Applicability
    Status              FindingStatus
    Severity            Severity
    Confidence          Confidence
    Evidence            []EvidenceReference
    MissingEvidence     []MissingEvidence
    SummaryKey          MessageKey
    DetailParameters    map[string]TypedValue
    Impact              Impact
    RecommendationIDs   []RecommendationID
    EvaluatedAt         time.Time
    Validity            ValidityWindow
}
```

Finding statuses remain:

```text
pass
warning
failure
unknown
```

These statuses apply only to findings and presentation-level summaries. They do not apply to raw observations.

### Diagnosis

A diagnosis is a cross-component explanation derived from findings, observations, component topology, and dependency-edge requirements.

A diagnosis may identify:

* a failed dependency edge
* a likely root-cause component
* a contributing factor
* a cluster of symptoms with no determined cause
* affected downstream components
* alternative plausible causes
* uncertainty that prevents a stronger conclusion

Examples:

```text
The Bitcoin node is synchronized, but Fulcrum is 47 blocks behind.
The break point is the Fulcrum indexing layer.
Wallets using this backend may display stale history.
```

```text
DATUM is running and its Stratum listener is reachable, but it has not
received a fresh template since the Bitcoin tip changed.
The likely break point is the DATUM-to-Bitcoin RPC dependency.
```

```text
Sparrow cannot reach its configured Electrum endpoint.
Redline cannot determine whether the cause is the server, firewall, or
incorrect wallet configuration because host firewall and wallet settings
were unavailable.
```

A conceptual diagnosis structure is:

```go
type Diagnosis struct {
    ID                  DiagnosisID
    ScanID              ScanID
    Code                DiagnosisCode
    CorrelationRuleID   CorrelationRuleID
    RuleVersion         string
    Classification      DiagnosisClassification
    Confidence          Confidence
    PrimaryComponentID  *ComponentID
    BreakPoint          *DependencyBreakPoint
    FindingRefs         []FindingID
    ObservationRefs     []ObservationID
    AffectedComponents  []ComponentID
    ContributingFactors []FindingID
    Alternatives        []DiagnosticAlternative
    ExplanationKey      MessageKey
    ExplanationParams   map[string]TypedValue
    EvaluatedAt         time.Time
}
```

Diagnosis classifications should include:

```text
root_cause
break_point
contributing_factor
symptom_cluster
inconclusive
```

These terms have distinct meanings.

* **root_cause** — Redline has sufficient evidence that the identified condition explains the observed failure chain.
* **break_point** — Redline has identified where a dependency stopped being satisfied but may not know the underlying reason.
* **contributing_factor** — the condition worsens or participates in the incident but is not sufficient to explain it alone.
* **symptom_cluster** — related failures were grouped, but causality is not established.
* **inconclusive** — the evidence does not support a reliable cross-layer explanation.

Redline should prefer a precise break point over an unjustified root-cause claim.

## Required invariants

### Observation invariants

Every observation must:

1. Reference exactly one probe execution.
2. Reference the component it describes.
3. Use a registered observation kind and schema version.
4. Include an observation timestamp.
5. Include capability-provider provenance.
6. Contain only normalized, approved fields.
7. Have a sensitivity classification.
8. Be immutable after creation.
9. Avoid health language such as “healthy,” “broken,” or “critical.”
10. Avoid recommendations or causal claims.

An observation may be superseded by a later observation, but it is never edited to reflect the newer state.

### Finding invariants

Every finding must:

1. Reference a stable finding code.
2. Identify the evaluator and evaluator version.
3. State its applicability separately from its status.
4. Reference supporting evidence or explicitly identify missing evidence.
5. Keep severity separate from confidence.
6. Avoid claiming a cross-component root cause.
7. Include an evaluation timestamp.
8. Be reproducible from its declared inputs and evaluator version.
9. Use parameterized messages rather than treating rendered prose as canonical data.
10. Never report `pass` when a required input is unavailable.

### Diagnosis invariants

Every diagnosis must:

1. Reference the correlation rule and version that produced it.
2. Reference supporting findings and, where necessary, observations.
3. Identify the relevant dependency path or symptom grouping.
4. Separate confirmed evidence from alternatives.
5. State confidence explicitly.
6. Avoid claiming a unique root cause when equally plausible alternatives remain.
7. Preserve downstream symptoms even when grouped beneath an upstream cause.
8. Identify the affected components.
9. Be reproducible from a specific graph snapshot and evidence set.
10. Prefer `break_point` or `inconclusive` when causality is not established.

## Applicability and status

Applicability must remain separate from diagnostic status.

Supported applicability values:

```text
applicable
not_applicable
undetermined
```

Examples:

* A pruning-related check is `not_applicable` when the node is not pruned.
* A TLS-certificate check is `not_applicable` to a plaintext local Electrum endpoint.
* A restart-loop check may have `undetermined` applicability if Redline cannot determine whether the component is managed by systemd, Docker, or another supervisor.
* An applicable check with inaccessible evidence becomes `unknown`.

`not_applicable` must not be represented as `pass`.

A check cannot pass when the condition does not apply.

## Status, severity, and confidence are independent

Redline will not compress health, impact, and certainty into one field.

### Status

Status describes the evaluated condition:

```text
pass
warning
failure
unknown
```

### Severity

Severity describes potential or observed impact:

```text
none
informational
low
medium
high
critical
```

A passing finding normally has severity `none`.

An unknown finding may still carry potential severity when the unavailable check concerns a critical dependency. The UI must present this carefully:

```text
Bitcoin data-volume writeability: unknown
Potential impact if unavailable: critical
Reason: mount inspection was denied
```

It must not render the component itself as critically failed.

### Confidence

Confidence describes how strongly the evidence supports the finding or diagnosis:

```text
low
medium
high
```

Confidence is ordinal rather than a pseudo-precise percentage.

A high-severity, low-confidence diagnosis must remain visibly different from a high-severity, high-confidence diagnosis.

The UI must not use severity as a substitute for certainty.

## Unknown semantics

`unknown` means:

> The condition is applicable or may be applicable, but Redline cannot establish pass, warning, or failure from the available evidence.

Every unknown finding must contain at least one structured reason.

Initial unknown reasons include:

```text
capability_unavailable
permission_denied
platform_restriction
component_not_discovered
binding_ambiguous
not_configured
unsupported_version
timeout
protocol_error
insufficient_evidence
stale_evidence
conflicting_evidence
user_disabled
scan_cancelled
```

Unknown must not be used for:

* a check that does not apply
* a component known not to exist
* an evaluator implementation bug
* an arbitrary fallback after unexpected errors
* a condition that clearly failed

Unexpected internal errors must be recorded as engine errors. They may cause dependent findings to become unknown, but the engine error and diagnostic uncertainty must remain distinguishable.

## Evidence references and lineage

Every finding and diagnosis must expose machine-readable evidence lineage.

An evidence reference should identify:

```go
type EvidenceReference struct {
    Kind     EvidenceReferenceKind
    ID       string
    Role     EvidenceRole
}
```

Evidence roles may include:

```text
supports
contradicts
bounds
contextualizes
establishes_dependency
establishes_timing
```

This allows a finding to explain not only which evidence was used but how it was used.

Example:

```json
{
  "code": "electrum.sync-lag",
  "status": "failure",
  "evidence": [
    {
      "kind": "observation",
      "id": "obs-bitcoin-tip",
      "role": "contextualizes"
    },
    {
      "kind": "observation",
      "id": "obs-fulcrum-tip",
      "role": "supports"
    }
  ]
}
```

Reports may render a simplified evidence summary, but the underlying references must remain available for expert inspection.

## Temporal semantics

Cross-layer diagnosis depends on time.

A Bitcoin height observed at 07:50:00 and an Electrum height observed at 08:20:00 cannot safely be compared as though they represent one system snapshot.

Every observation therefore includes:

* `observed_at`
* optional validity or freshness duration
* source clock information where relevant
* scan identifier
* evidence-quality information

Evaluators must define acceptable observation skew.

Example:

```text
bitcoin tip and electrum tip observations must be no more than 15 seconds apart
```

If the skew exceeds the evaluator’s tolerance, the result becomes unknown or the probe must refresh the older observation.

Historical observations may be used for trends, but current health findings must not silently combine current and stale evidence.

Examples:

* Current free disk space may be combined with a seven-day consumption trend if both roles are explicit.
* Yesterday’s successful RPC response cannot be used to claim that RPC is reachable now.
* A restart loop requires a defined historical window.
* A causal diagnosis based on event ordering must account for timestamp quality and possible clock drift.

## Evidence quality

Observations should carry evidence-quality metadata independent of their value.

Relevant dimensions include:

```text
directness
freshness
completeness
source_authority
timestamp_quality
```

Examples:

* A Bitcoin RPC response is direct evidence of RPC behavior.
* A Docker container state is indirect evidence of application behavior.
* A platform health flag may be authoritative about platform state but insufficient to establish protocol correctness.
* A log-derived miner count may be less current than a live DATUM metric.
* An observation from a degraded capability may remain useful while lowering finding confidence.

The initial implementation may represent quality with a small structured enum rather than a numerical score.

## Root-cause semantics

Redline will not force every incident to have one root cause.

A diagnosis may identify a root cause only when:

1. The relevant dependency relationship is known.
2. The upstream failure is directly or strongly evidenced.
3. The failure explains the downstream symptoms.
4. The timing is compatible with the proposed causal sequence.
5. No equally plausible alternative remains supported by the available evidence.
6. The correlation rule explicitly supports a root-cause classification.

When these conditions are not met, Redline should use a weaker but more accurate classification.

Example:

```text
Confirmed:
Sparrow cannot reach the configured Electrum endpoint.

Break point:
Wallet → Electrum connectivity.

Not determined:
Whether the endpoint is down, incorrectly configured, blocked by a firewall,
or unreachable from the wallet’s network.
```

This is a useful diagnosis even without a root cause.

### Multiple causes

A failure may have multiple causes or contributing conditions.

For example:

```text
Bitcoin is repeatedly restarting because its data volume is full.
Fulcrum is behind because Bitcoin is repeatedly unavailable.
The wallet is stale because Fulcrum is behind.
```

The diagnosis model should represent:

* disk exhaustion as the likely root cause
* Bitcoin restart instability as an intermediate failure
* Fulcrum lag as a downstream failure
* stale wallet data as user impact

It should not flatten all four into unrelated red failures.

### Alternative diagnoses

When several causes remain plausible, Redline may provide ranked alternatives:

```text
Primary possibility:
DATUM cannot authenticate to Bitcoin RPC.

Alternative:
DATUM is connected to a different Bitcoin node than the one Redline inspected.

Unresolved because:
DATUM configuration access was unavailable.
```

Alternatives must reference the evidence that supports and weakens them.

## Pass findings and positive evidence

Redline may produce explicit pass findings, but a pass is a health interpretation rather than an absence of errors.

A pass must be supported by positive evidence.

For example:

```text
Bitcoin RPC reachable: pass
```

requires a valid RPC response.

```text
Bitcoin synchronized: pass
```

requires defined synchronization criteria.

```text
Disk healthy: pass
```

cannot be generated merely because no disk error was found. It requires the specific checks needed by that evaluator.

Summary views must distinguish:

```text
No failures detected with complete required evidence
```

from:

```text
No failures detected, but several checks were unavailable
```

## Aggregation and presentation

The report layer may aggregate findings for readability, but aggregation must not erase the underlying objects.

A component summary might render:

```text
Fulcrum: Failure

Primary issue:
47 blocks behind Bitcoin.

Confirmed working:
Process running.
TCP port reachable.
TLS handshake valid.

Unknown:
Restart history unavailable on this platform.
```

This summary is derived from several findings. It is not itself the canonical diagnostic record.

### Component status

A component’s displayed status will be derived from applicable findings using an explicit aggregation policy.

The initial policy should generally be:

1. Any critical or high-severity failure makes the component display as failed.
2. Lower-severity failures may display as failed or warning according to product policy.
3. Warnings display as warning when no overriding failure exists.
4. Unknown required checks prevent an unqualified healthy state.
5. Pass is shown only when required checks pass and coverage is sufficient.
6. Not-applicable checks do not reduce coverage.

The exact aggregation algorithm should be separately versioned because it affects presentation, not the meaning of individual findings.

### Diagnosis-first incident views

When a diagnosis reliably explains several findings, the UI should lead with the diagnosis and group downstream symptoms beneath it.

It must not delete or hide the individual findings from expert inspection.

Example:

```text
Likely root cause: Bitcoin data volume full

Affected:
- Bitcoin Core restarting
- Fulcrum indexing stalled
- Sparrow wallet data stale
- DATUM template generation unavailable
```

## Persistence

Normalized observations, findings, and diagnoses may be persisted.

The following must not be persisted as ordinary diagnostic evidence:

* raw RPC responses
* raw logs
* authorization headers
* RPC cookies
* passwords
* onion addresses
* payout addresses
* external IP addresses
* unrestricted command output
* unredacted configuration files

Persisted diagnostic objects must be immutable.

A later evaluator may produce a new finding from an existing observation, but it does not overwrite the previous finding.

This allows Redline to answer:

* What did the original rule conclude?
* Which rule version produced that conclusion?
* Would the current rule interpret the same evidence differently?

Retention policies may remove old diagnostic objects, but retained objects must preserve their original semantics.

## Rule and schema versioning

Every observation kind, finding evaluator, and correlation rule must be versioned.

Relevant identifiers include:

```text
bitcoin.chain-tip/v1
bitcoin.sync-state/v1
electrum.sync-lag/v1
datum.template-staleness/v1
correlation.wallet-electrum-breakpoint/v1
```

A version change is required when the meaning of an output changes incompatibly.

Threshold changes that materially change a pass into a warning or failure must be traceable through evaluator configuration or version.

Rendered English text is not the stable contract.

Stable contracts are:

* observation kinds
* typed fields
* finding codes
* diagnosis codes
* evidence references
* evaluator identifiers
* rule versions
* structured message parameters

This permits wording to improve without invalidating stored diagnostic data.

## Evaluator purity and reproducibility

Finding evaluators and correlation rules should be deterministic functions of:

* declared observations
* declared probe outcomes
* component graph snapshot
* evaluator configuration
* evaluator or rule version
* evaluation time where explicitly required

They must not perform undeclared platform access.

A finding evaluator must not open a socket, read a log, inspect Docker, or call Bitcoin RPC.

Collection belongs to probes and capabilities.

Interpretation belongs to evaluators.

This allows the system to:

* unit-test rules with fixtures
* replay diagnostic logic
* compare evaluator versions
* explain conclusions
* avoid inconsistent results caused by hidden I/O

## Alternatives considered

### Alternative A: One generic diagnostic result object

This would combine status, evidence, impact, and recommendation into one structure.

It is rejected as the internal model because it conflates collection, interpretation, and causality.

It may still be used as a simplified report projection.

### Alternative B: Observations with embedded health status

For example:

```json
{
  "metric": "disk_free",
  "value": 3.1,
  "status": "critical"
}
```

This is rejected because the status depends on thresholds, context, and policy rather than the observed value itself.

The same observation may support different findings under different conditions.

### Alternative C: Findings without retaining observations

This would reduce storage and schema complexity.

It is rejected because Redline would lose:

* evidence traceability
* rule replay
* expert inspection
* historical reinterpretation
* the ability to distinguish collection from evaluation errors

### Alternative D: One diagnosis per scan

This is rejected because real stacks may contain unrelated failures or multiple contributing causes.

A scan may produce zero, one, or several diagnoses.

### Alternative E: Always select a root cause

This is rejected because it would create false certainty.

Identifying a break point or an unresolved symptom cluster is preferable to inventing causality.

### Alternative F: Numerical confidence percentages

This is rejected for the initial implementation.

Values such as `83% confidence` would imply a calibrated statistical model that Redline does not possess.

Ordinal confidence with explicit evidence is more honest and easier to govern.

### Alternative G: Treat unavailable evidence as a passing check

This is rejected because it violates the core product principle and creates fake green states.

### Alternative H: Treat every unavailable check as a failure

This is also rejected.

Failure to observe a condition is not proof that the component failed.

Unavailable evidence produces explicit uncertainty.

## Consequences

### Positive consequences

* Every conclusion can be traced to concrete evidence.
* Raw facts remain stable when diagnostic thresholds change.
* Cross-layer reasoning becomes independently testable.
* Restricted platform access is represented honestly.
* The UI can serve both non-experts and experts from the same underlying model.
* Redline can identify break points without overstating root causes.
* Historical findings retain their original rule context.
* Multiple causes and alternative explanations can be represented.
* Pass states require positive evidence.
* Reports can explain exactly why a conclusion was reached.
* Probe collection and diagnostic evaluation can evolve independently.

### Negative consequences

* The domain model is more complex than a single result structure.
* More identifiers and versioned schemas must be governed.
* Evidence lineage increases storage and implementation overhead.
* Developers must maintain strict semantic boundaries.
* Aggregation for user-friendly presentation requires an additional layer.
* The distinction between finding and diagnosis may initially be unfamiliar to contributors.
* Re-evaluation and historical replay require careful configuration versioning.
* Temporal consistency becomes an explicit engineering concern.

### Neutral consequences

* Reports may still expose a simplified result shape.
* Some simple checks may produce one observation and one finding with an obvious relationship.
* Not every scan will produce a diagnosis.
* Not every failure finding will participate in a cross-layer incident.
* Incident lifecycle remains a separate concern built on top of findings and diagnoses.

## Risks and mitigations

### Risk: The model becomes academically precise but cumbersome

**Mitigations:**

* Keep the initial observation and finding catalog small.
* Provide constructors and helper libraries.
* Generate repetitive schema code where appropriate.
* Use simplified report projections for common UI paths.
* Require complexity only where it preserves meaningful distinctions.

### Risk: Developers place conclusions in observations

**Mitigations:**

* Observation packages must not import status, severity, recommendation, or diagnosis types.
* Naming reviews should reject health language in observation kinds.
* Architecture tests should enforce dependency direction.
* Contract tests should verify normalized values independently of thresholds.

### Risk: Findings become hidden probes

**Mitigations:**

* Evaluators must be pure and receive all inputs explicitly.
* Evaluator packages must not import platform or capability providers.
* Tests must reproduce findings entirely from fixtures.
* Undeclared I/O in evaluator code is prohibited.

### Risk: Diagnoses overstate causality

**Mitigations:**

* Require explicit diagnosis classification.
* Require confidence and alternatives.
* Define rule-specific causal requirements.
* Prefer break-point classification.
* Review every root-cause rule with positive, negative, and ambiguous fixtures.
* Keep rendered language aligned with confidence.

### Risk: Old evidence is combined with current evidence

**Mitigations:**

* Require observation timestamps.
* Define skew and freshness tolerances per evaluator.
* Reject stale inputs unless a rule explicitly uses history.
* Display the relevant time window in expert views.
* Track clock-quality observations where timing is important.

### Risk: Unknown results make the product appear unhelpful

**Mitigations:**

* Explain exactly which evidence is missing.
* Continue running independent checks.
* Group unknowns by access limitation.
* State what Redline did establish.
* Explain whether deep scan or configuration would resolve the uncertainty.
* Avoid hiding uncertainty behind reassuring language.

### Risk: Finding and diagnosis schemas become unstable

**Mitigations:**

* Use stable codes and versioned schemas.
* Keep rendered text outside canonical identity.
* Require migrations for persisted schema changes.
* Add compatibility tests for exported reports.
* Avoid exposing internal Go structures directly as public schemas.

## Testing strategy

### Observation tests

Tests must verify:

* correct normalization
* provenance retention
* timestamp handling
* sensitivity classification
* bounded values
* absence of forbidden raw fields
* immutability after creation

### Finding evaluator tests

Each evaluator must include:

* positive pass fixtures
* warning fixtures
* failure fixtures
* missing-evidence fixtures
* stale-evidence fixtures
* contradictory-evidence fixtures
* boundary-value tests
* versioned expected outputs

### Correlation-rule tests

Each correlation rule must include:

* confirmed root-cause scenario
* break-point-only scenario
* multiple plausible causes
* unrelated simultaneous failures
* missing dependency edge
* stale or temporally inconsistent evidence
* downstream symptom grouping
* recovery scenario

### Traceability tests

For every user-visible failure or diagnosis:

* all evidence references must resolve
* referenced evidence must belong to the relevant scan or explicitly declared historical window
* rule and evaluator identifiers must exist
* rendered explanation parameters must be present
* missing evidence must be structured
* no diagnosis may reference deleted or inaccessible canonical evidence

### Golden report tests

Representative scan fixtures should produce stable expert and simplified reports.

Golden tests should verify both:

* diagnostic meaning
* appropriate uncertainty language

## Validation criteria

ADR-003 will be considered successfully implemented when:

1. Observations contain facts but no health statuses.
2. Findings are reproducible from declared evidence and evaluator versions.
3. Diagnoses are reproducible from findings, observations, and a graph snapshot.
4. Every failure and warning references supporting evidence.
5. Every unknown finding contains a structured reason.
6. A missing capability cannot produce a pass.
7. Not-applicable checks are not represented as pass or unknown.
8. Severity and confidence are independently represented.
9. A break point can be reported without claiming a root cause.
10. Multiple plausible causes can be preserved as alternatives.
11. Raw protocol responses and logs are absent from persisted observations.
12. Historical observations remain unchanged when rules are updated.
13. Observation freshness and skew are enforced.
14. A simplified report can be generated without discarding expert evidence.
15. Architecture tests prevent evaluators and correlation rules from performing platform I/O.
16. The first Bitcoin-to-Electrum diagnosis can show its complete evidence chain.
17. A restricted-platform scan explains uncertainty without presenting a fake healthy state.
18. Root-cause wording changes according to diagnosis classification and confidence.

## Reconsideration triggers

This ADR should be revisited if:

1. The three-layer model proves unable to represent important diagnostic scenarios.
2. A fourth canonical reasoning layer becomes repeatedly necessary.
3. Evidence storage becomes impractical on supported hardware.
4. Re-evaluation of historical observations creates unacceptable schema complexity.
5. The product adopts probabilistic or machine-learned diagnosis requiring calibrated confidence.
6. Remote agents produce evidence that cannot fit the current provenance model.
7. Continuous monitoring requires a materially different temporal model.
8. Automated remediation requires state transitions not represented here.
9. Third-party rule packs require a more constrained public evidence language.
10. Users consistently cannot understand the distinction between findings and diagnoses even after presentation-layer improvements.

A reconsideration trigger requires a new ADR based on observed implementation experience.

## Final decision statement

SATOSHI//REDLINE will represent diagnostic reasoning through separate, traceable objects for observations, findings, and diagnoses.

Observations record what was measured.

Findings state what those measurements mean for one condition or component.

Diagnoses explain how failures relate across the stack and identify a root cause only when the evidence supports that level of certainty.

Missing evidence will produce explicit uncertainty. A failed dependency edge may be identified without claiming that its underlying cause is known. Every user-visible conclusion will remain traceable to normalized evidence and the versioned rule that interpreted it.

The central rule established by this ADR is:

> Facts, health judgments, and causal explanations are different kinds of knowledge and must remain different kinds of data.
