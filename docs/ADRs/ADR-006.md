# ADR-006: Version External API and Report Schemas Independently from Internal Models

* **Date:** 2026-07-30
* **Decision owners:** SATOSHI//REDLINE maintainers
* **Depends on:**

  * ADR-001 — Use a Go Modular Monolith for the Diagnostic Backend
  * ADR-002 — Use Capability-Based, Composable Platform Adapters
  * ADR-003 — Separate Observations, Findings, and Diagnoses
  * ADR-004 — Run the Main Daemon Unprivileged and Isolate Deep-Scan Access in an Optional Privileged Helper
  * ADR-005 — Do Not Persist Raw Logs or Protocol Responses
* **Scope:**

  * Local HTTP API
  * Server-Sent Events
  * JSON report exports
  * Machine-readable diagnostic schemas
  * Finding and diagnosis identifiers
  * Client compatibility
  * Schema publication, validation, migration, and deprecation
* **Excluded from scope:**

  * Internal SQLite schema versioning
  * Privileged-helper protocol details already governed by ADR-004
  * UI visual design
  * Remote API authentication
  * Hosted commercial APIs
  * Third-party plugin contracts
  * Exact report-retention policy

## Context

SATOSHI//REDLINE will initially ship as a local application whose daemon, CLI, and embedded web interface are released together.

That could make formal external contracts appear unnecessary.

The product roadmap, however, includes several consumers that will not necessarily update in lockstep with the daemon:

* the bundled browser UI
* command-line clients
* exported diagnostic-report viewers
* support tooling
* future iOS and Android applications
* future browser extensions or integrations
* future monitoring clients
* users retaining reports generated by older releases
* human troubleshooting workflows where a report is sent to another person running a different Redline version

The diagnostic model will also evolve.

New releases may add:

* component types
* observation kinds
* finding codes
* diagnosis codes
* evidence fields
* coverage metadata
* report sections
* scan modes
* protocol integrations
* remediation references
* incident-history data

If internal Go structs are serialized directly, ordinary refactoring can accidentally become a public breaking change.

For example:

* renaming a Go field could rename a JSON property
* splitting a domain type could change response shape
* replacing an enum could invalidate old clients
* changing a zero value could alter omission behavior
* adding internal provenance could unintentionally expose sensitive data
* changing database storage could alter report output
* an implementation-specific field could become impossible to remove after clients begin depending on it

The product version cannot safely serve as the schema version.

A Redline `0.8.0` daemon may still implement API version 1 and report format version 1. A later `2.3.0` release may continue reading reports produced by much older releases.

Similarly, a finding’s evaluator version is not the same as the API version that transports the finding.

Several distinct forms of compatibility therefore need independent treatment:

```text id="s4g6pl"
Product release compatibility
HTTP API compatibility
Event-stream compatibility
Report-format compatibility
Observation-kind compatibility
Finding and diagnosis identifier stability
Evaluator and correlation-rule reproducibility
Internal database migration
```

Without explicit governance, these versions will either become conflated or omitted entirely.

Redline also has unusually strict privacy constraints.

An external schema is not merely a serialization convenience. It is an allowlist of information that may cross a boundary.

The API and report layers must not gain fields simply because internal objects contain them.

The architecture therefore needs stable, reviewable contracts that:

* remain independent of internal Go types
* preserve older report readability
* allow compatible additions
* reject ambiguous or unsafe changes
* support generated TypeScript clients
* remain usable offline
* expose uncertainty and evidence faithfully
* do not create alternate paths around ADR-005

## Decision

SATOSHI//REDLINE will maintain explicit, versioned external schemas for:

1. The local HTTP API
2. Server-Sent Event envelopes and payloads
3. Exported JSON diagnostic reports
4. Exportable observation representations
5. Exportable findings and diagnoses
6. Component and dependency-graph projections
7. Error responses
8. Stable diagnostic code registries

Internal Go domain models, platform-provider models, capability responses, and database records will not be serialized directly as public contracts.

Every external response or report will be produced through an explicit mapping layer:

```text id="pdiydb"
Internal domain model
        ↓
Boundary-specific projection
        ↓
Versioned transport schema
        ↓
Schema validation
        ↓
API response or report export
```

The reverse path will use a corresponding reader:

```text id="4cm12m"
Versioned external document
        ↓
Schema validation
        ↓
Version-specific transport model
        ↓
Migration or mapping
        ↓
Internal read model
```

The initial local HTTP API will use a major version in its path:

```text id="vjmu19"
/api/v1/
```

The initial exported JSON report format will be:

```text id="wwcds7"
urn:satoshi-redline:schema:report:v1
```

Observation kinds, finding codes, diagnosis codes, and other independently evolving semantic contracts will carry their own stable identifiers and versions.

The central decision is:

> Redline’s external contracts will be intentionally designed, explicitly versioned, and mapped from internal models. Internal implementation types will never become public schemas by accident.

## Decision drivers

The decision drivers, in priority order, are:

1. Preserve compatibility between daemon, UI, CLI, mobile clients, and support tooling.
2. Ensure reports remain interpretable after the producing release is obsolete.
3. Prevent internal refactoring from silently changing external behavior.
4. Make every externally visible field an explicit privacy decision.
5. Allow diagnostic schemas to evolve without freezing the entire product.
6. Keep observation, finding, and diagnosis semantics reproducible.
7. Support generated clients without making generated types the domain model.
8. Define strict rules for compatible and breaking changes.
9. Make unknown future diagnostic codes survivable by older clients.
10. Keep all schemas available offline and tied to product releases.

## Contract categories

Redline will distinguish among several contract categories.

### Product version

The product version identifies a Redline software release.

Example:

```text id="d6wwd6"
0.1.0
0.7.2
1.0.0
```

It describes the application release, not the shape of every external document.

A product version may:

* add fields compatibly to API v1
* add new observation kinds
* add new finding codes
* continue producing report v1
* support more than one report version
* support more than one API major during a transition

### HTTP API major version

The HTTP API major version appears in the path:

```text id="2n5s3a"
/api/v1/scans
/api/v1/components
/api/v1/incidents
/api/v1/reports
/api/v1/meta
```

A new major version is required when an existing client cannot continue operating correctly under the documented compatibility rules.

Examples:

```text id="ebt8jq"
/api/v1/
/api/v2/
```

Compatible additions do not require a new path.

### API contract revision

Within one API major, the OpenAPI document will have a contract revision.

Example:

```text id="skk8ol"
1.0.0
1.1.0
1.2.1
```

This revision describes the published contract document, not the Redline product.

Contract-revision semantics are:

* **major** — corresponds to the API path major
* **minor** — backward-compatible additions or clarifications
* **patch** — corrections that do not alter valid behavior or structure

The API path remains the authoritative runtime compatibility boundary.

### Report-format major version

Each exported JSON report will declare a format identifier and major version.

Example:

```json id="kty72v"
{
  "format": "satoshi-redline-report",
  "schema_id": "urn:satoshi-redline:schema:report:v1",
  "format_version": 1
}
```

Report format versions are independent of API versions.

The first report may be produced through API v1, but report v1 must remain readable even after API v1 is retired.

### Semantic object version

Observation kinds and other independently evolving semantic objects carry their own versions.

Examples:

```text id="iswo32"
bitcoin.chain.tip/v1
filesystem.capacity/v1
electrum.sync-lag/v1
datum.template-freshness/v1
```

This version describes the meaning and field structure of that specific object.

### Evaluator and rule version

A finding records the evaluator version that interpreted its evidence.

A diagnosis records the correlation-rule version that produced it.

Examples:

```text id="1zce52"
bitcoin.sync-state evaluator 1.2.0
electrum.sync-lag evaluator 1.0.1
wallet-electrum-breakpoint rule 1.1.0
```

These versions support reproducibility under ADR-003. They do not change the surrounding API or report format unless the transported structure itself changes incompatibly.

### Database schema version

SQLite migrations are internal implementation details.

The database schema version is not exposed as the API version or report version.

An internal migration may occur without changing any public contract.

## Source of truth

External schemas will be maintained schema-first.

The repository will contain authoritative contract files such as:

```text id="4r5zrx"
schemas/
├── api/
│   └── v1/
│       ├── openapi.yaml
│       ├── events.schema.json
│       └── errors.schema.json
│
├── reports/
│   └── v1/
│       ├── report.schema.json
│       ├── component.schema.json
│       ├── observation.schema.json
│       ├── finding.schema.json
│       └── diagnosis.schema.json
│
├── observations/
│   ├── bitcoin.chain.tip/
│   │   └── v1.schema.json
│   ├── filesystem.capacity/
│   │   └── v1.schema.json
│   └── electrum.chain.tip/
│       └── v1.schema.json
│
└── registries/
    ├── finding-codes.json
    ├── diagnosis-codes.json
    ├── recommendation-ids.json
    └── unknown-reasons.json
```

OpenAPI will define the HTTP API.

JSON Schema will define report documents and independently versioned exported objects.

The schemas will be:

* committed to source control
* reviewed like application code
* embedded in release artifacts
* included in source distributions
* available through a read-only local metadata endpoint
* usable without internet access
* tested against examples and generated payloads

The schemas will use stable URN identifiers rather than requiring a public schema website.

Example:

```text id="as6mns"
urn:satoshi-redline:schema:report:v1
urn:satoshi-redline:schema:observation:bitcoin.chain.tip:v1
```

A future public schema website may mirror these files, but report validation must not depend on network access.

## Internal models are not transport models

The Go domain model will remain independent of HTTP and report serialization.

For example:

```go id="yd6qg2"
type Finding struct {
    ID                FindingID
    Code              FindingCode
    ComponentID       ComponentID
    Status            FindingStatus
    Severity          Severity
    Confidence        Confidence
    Evidence          []EvidenceReference
    MissingEvidence   []MissingEvidence
    Evaluator         EvaluatorReference
    EvaluatedAt       time.Time
}
```

The API representation may be:

```go id="sk8h7x"
type FindingResponseV1 struct {
    ID              string                    `json:"id"`
    Code            string                    `json:"code"`
    ComponentID     string                    `json:"component_id"`
    Status          string                    `json:"status"`
    Severity        string                    `json:"severity"`
    Confidence      string                    `json:"confidence"`
    Evidence        []EvidenceReferenceV1     `json:"evidence"`
    MissingEvidence []MissingEvidenceV1       `json:"missing_evidence,omitempty"`
    Evaluator       EvaluatorReferenceV1      `json:"evaluator"`
    EvaluatedAt     string                    `json:"evaluated_at"`
}
```

The report representation may be stricter:

```go id="w61gg2"
type ExportFindingV1 struct {
    ID              string                `json:"id"`
    Code            string                `json:"code"`
    ComponentAlias  string                `json:"component"`
    Status          string                `json:"status"`
    Severity        string                `json:"severity"`
    Confidence      string                `json:"confidence"`
    Evidence        []ExportEvidenceV1    `json:"evidence"`
    Evaluator       EvaluatorReferenceV1  `json:"evaluator"`
    EvaluatedAt     string                `json:"evaluated_at"`
}
```

The report projection may omit local-sensitive identifiers that the local API is allowed to expose.

Mapping code will be explicit.

Reflection-based automatic exposure of arbitrary domain fields is prohibited.

## Initial API surface

The initial API will use resource-oriented endpoints.

A likely v1 surface is:

```text id="jrs5zm"
GET    /api/v1/meta
GET    /api/v1/components
GET    /api/v1/components/{component_id}
POST   /api/v1/scans
GET    /api/v1/scans
GET    /api/v1/scans/{scan_id}
POST   /api/v1/scans/{scan_id}/cancel
GET    /api/v1/scans/{scan_id}/observations
GET    /api/v1/scans/{scan_id}/findings
GET    /api/v1/scans/{scan_id}/diagnoses
GET    /api/v1/scans/{scan_id}/graph
GET    /api/v1/incidents
GET    /api/v1/incidents/{incident_id}
POST   /api/v1/reports
GET    /api/v1/reports/{report_id}
GET    /api/v1/events
```

Endpoint details may change during implementation, but the versioning rules established by this ADR apply from the first externally consumed release.

### Metadata endpoint

`GET /api/v1/meta` will expose compatibility information such as:

```json id="euj7tb"
{
  "product_version": "0.1.0",
  "api": {
    "major": 1,
    "contract_revision": "1.0.0"
  },
  "report_formats": {
    "write": [1],
    "read": [1]
  },
  "event_schema": 1,
  "features": [
    "safe-scan",
    "deep-scan",
    "json-report-v1"
  ]
}
```

Clients must discover supported contracts through metadata rather than inferring them from the product version.

### Resource identifiers

Public identifiers will be JSON strings and must be treated as opaque by clients.

Examples:

```text id="5ctkqw"
scan_01K...
obs_01K...
finding_01K...
diagnosis_01K...
component_bitcoin_primary
```

The implementation may use UUIDv7, ULID, or another internal representation.

Clients must not depend on:

* embedded timestamps
* prefixes
* lexical ordering
* identifier length
* internal database keys

Prefixes may aid debugging but are not semantic contracts.

## JSON representation rules

All API and report schemas will follow common serialization rules.

### Property naming

JSON properties will use `snake_case`.

Examples:

```text id="zltldb"
component_id
observed_at
missing_evidence
format_version
```

### Timestamps

Timestamps will use RFC 3339 with an explicit UTC offset.

Canonical output will use UTC:

```text id="q5v5hv"
2026-07-30T14:25:31Z
```

Subsecond precision may be included where diagnostically useful.

A timestamp without a timezone is invalid.

### Durations

Durations will be represented as integer milliseconds unless a more suitable unit is explicitly part of the field name.

Examples:

```json id="wi9s87"
{
  "latency_ms": 84,
  "timeout_ms": 5000
}
```

Human-readable duration strings are presentation values, not canonical machine fields.

### Byte quantities

Byte quantities will be represented as non-negative JSON integers.

Public schemas will constrain numeric values to the exact-integer range safely representable by common JSON clients:

```text id="zqcve8"
0 through 9,007,199,254,740,991
```

This range supports approximately nine petabytes and is sufficient for supported Redline targets.

Values outside the supported range must produce a structured limitation rather than silent precision loss.

### Percentages and ratios

Ratios will be represented consistently.

Where exact ratios matter, the schema should prefer:

```json id="dluq8x"
{
  "used_bytes": 96800000000,
  "total_bytes": 100000000000
}
```

A derived display percentage may be included as a convenience but must not replace the underlying values.

When a ratio is transported directly, its range and meaning must be documented.

### Null and absence

Absent and `null` have different meanings.

The schema must define them explicitly.

General rule:

* An omitted optional property means the property was not included under this contract or is not applicable to this representation.
* A `null` property means the property is part of the representation, but its value is explicitly unknown or unavailable.

Schemas should avoid nullable fields when a structured state is clearer.

Example:

```json id="sbd02q"
{
  "exit_code": null,
  "exit_code_state": "not_observed"
}
```

may be less desirable than:

```json id="rmf7yz"
{
  "exit": {
    "observed": false
  }
}
```

### Enumerations

Enums will be classified as either closed or extensible.

Closed enums include core semantic states such as:

```text id="v4119i"
pass
warning
failure
unknown
```

Adding a new value to a closed enum is a breaking change.

Extensible registries include values such as:

```text id="w5bl09"
finding codes
diagnosis codes
recommendation IDs
observation kinds
component kinds
```

Clients must tolerate unknown registry values and render a generic fallback.

This distinction prevents every new diagnostic rule from requiring an API major version.

### Free-form objects

External schemas will not contain unrestricted free-form metadata objects by default.

Fields such as:

```text id="2kt49n"
metadata
extra
debug
attributes
extensions
```

with arbitrary values are prohibited unless a future ADR defines a constrained extension system.

This preserves the privacy and persistence boundaries established by ADR-005.

## Compatibility rules

Compatibility is defined by documented client behavior, not merely by whether JSON still parses.

### Backward-compatible API changes

The following are generally compatible within an API major:

* adding a new endpoint
* adding a new optional response field
* adding an optional request field with unchanged default behavior
* adding a new finding or diagnosis code to an extensible registry
* adding a new component kind
* adding a new observation kind
* adding a new Server-Sent Event type when clients are required to ignore unknown event types
* clarifying documentation without changing semantics
* broadening a numeric range without reducing precision
* adding an optional link or presentation hint

### Breaking API changes

The following require a new API major unless the affected field or endpoint was explicitly experimental:

* removing or renaming an endpoint
* removing or renaming a response field
* changing a field’s type
* changing a field’s meaning
* making an optional field required
* changing a required field to have materially different semantics
* changing a closed enum
* changing default behavior in a way that alters client decisions
* changing identifier stability
* changing pagination semantics
* changing timestamp or unit conventions
* changing error-category meaning
* introducing mandatory client behavior for a previously ignorable field
* exposing a previously local operation as remotely state-changing
* changing a successful response into a different structural shape

A change can be breaking even when the JSON property names remain identical.

### Compatible report changes

Report compatibility is stricter because reports are archival documents.

Within report format v1, Redline may:

* add optional sections
* add optional fields
* add new extensible registry values
* add newly supported observation kinds
* add newly supported recommendation IDs
* add producer metadata
* add optional presentation hints

A report v1 reader must:

* ignore unknown optional fields
* preserve the meaning of known fields
* tolerate unknown finding and diagnosis codes
* reject invalid changes to closed semantics
* explain unsupported object kinds rather than crashing

### Breaking report changes

A new report major version is required when:

* a required field is removed or renamed
* the meaning of a required field changes
* a canonical unit changes
* evidence-reference semantics change
* identity or dependency relationships are represented differently
* privacy semantics change materially
* an existing section becomes incompatible
* closed status, severity, confidence, or applicability semantics change
* a report can no longer be safely interpreted under v1 rules

## Strict writers and tolerant readers

Redline will follow a bounded form of strict-writer, tolerant-reader behavior.

### Writers

A writer must:

* emit only fields defined by its declared schema
* satisfy all required constraints
* use canonical units and timestamp forms
* avoid deprecated fields when a replacement exists
* validate the complete output before transmission or export
* never include private internal fields
* never include arbitrary extension fields

### Readers

A reader may:

* ignore unknown optional properties
* accept unknown extensible registry values
* render generic representations for unknown diagnostic codes
* preserve known data even when an unfamiliar optional section is present

A reader must reject:

* unsupported major versions
* malformed required fields
* invalid closed-enum values
* contradictory schema identifiers
* unsafe or forbidden fields
* invalid evidence references
* data that cannot be interpreted without guessing

Tolerance must not become silent semantic invention.

## Diagnostic-code stability

### Finding codes

Finding codes identify a stable diagnostic condition.

Examples:

```text id="f6pj3r"
bitcoin.rpc.reachable
bitcoin.chain.synchronized
bitcoin.chain.tip-freshness
electrum.endpoint.reachable
electrum.chain.sync-lag
filesystem.capacity-pressure
datum.template-staleness
```

A finding code’s core meaning must not change.

A code may retain the same identity while:

* wording improves
* remediation guidance improves
* new optional evidence is added
* evaluator implementation is optimized
* threshold configuration is made explicit

A new finding code is required when the asserted condition materially changes.

### Diagnosis codes

Diagnosis codes identify stable cross-layer explanations.

Examples:

```text id="as24u2"
bitcoin.storage-capacity-risk
wallet-backend.electrum-indexing-breakpoint
mining.datum-bitcoin-rpc-breakpoint
```

A diagnosis code must not change from a break-point claim into a confirmed-root-cause claim without a new code or explicit classification change governed by the schema.

### Code registries

Registries will include:

```text id="c6n1de"
code
title key
description
introduced in product version
deprecated status
replacement code, if any
expected evidence roles
default impact category
```

Rendered English text is not the stable identity.

Clients must retain unknown codes and use generic rendering based on:

* status
* severity
* confidence
* component
* structured explanation parameters

## Message rendering and localization

Canonical API and report objects will use stable message keys and typed parameters.

Example:

```json id="m3ddyb"
{
  "message": {
    "key": "finding.electrum.sync_lag.summary",
    "parameters": {
      "lag_blocks": 47,
      "allowed_lag_blocks": 3
    }
  }
}
```

The local API may also include server-rendered English text as a convenience:

```json id="fpvazv"
{
  "rendered": "Fulcrum is 47 blocks behind Bitcoin."
}
```

The rendered string is not canonical.

Clients should prefer local rendering when localization is required.

Reports intended for human sharing may include both:

* stable message key and parameters
* rendered text produced by the exporting Redline version

This preserves immediate readability while retaining machine interpretation.

Changing rendered wording does not require a schema version change when keys and parameters retain their meaning.

## API request semantics

### Idempotency

Read operations are naturally idempotent.

Scan creation is not inherently idempotent.

The initial local API may support an optional client-generated idempotency key for actions such as:

```text id="vut7ki"
POST /api/v1/scans
POST /api/v1/reports
```

If implemented, the key’s scope and retention must be documented.

The absence of idempotency support does not change schema compatibility but affects client retry behavior and must be explicit in OpenAPI.

### Cancellation

Scan cancellation will be modeled as an explicit action:

```text id="984gev"
POST /api/v1/scans/{scan_id}/cancel
```

The response will describe whether cancellation was:

```text id="flv2dc"
accepted
already-completed
already-cancelled
not-cancellable
```

Clients must not infer cancellation from connection termination.

### Pagination

List endpoints that can grow will use opaque cursor pagination.

Example:

```json id="jh0ebm"
{
  "items": [],
  "next_cursor": "opaque-value"
}
```

Clients must treat the cursor as opaque.

Changing from offset to cursor pagination within an existing endpoint would be breaking unless the original contract explicitly allowed both.

### Filtering and ordering

Filters and sort orders must be explicitly enumerated.

Unknown filter parameters will produce a structured client error rather than being silently ignored.

Default ordering must be documented.

## Error schema

All API errors will use a stable envelope.

Example:

```json id="2dvuei"
{
  "error": {
    "code": "scan_not_found",
    "message": "The requested scan does not exist.",
    "request_id": "request_01K...",
    "retryable": false,
    "details": {
      "scan_id": "scan_01K..."
    }
  }
}
```

The canonical fields are:

```text id="3py67u"
code
message
request_id
retryable
details
```

`details` must be a code-specific typed object, not unrestricted metadata.

Errors must not expose:

* raw provider errors
* stack traces
* protocol responses
* filesystem paths
* credentials
* external addresses
* helper payloads
* internal database statements

Error codes are an extensible registry.

Clients must tolerate unknown error codes while honoring HTTP status and `retryable`.

An existing error code’s meaning must not change materially.

## Server-Sent Events

Server-Sent Events will provide live scan and incident updates.

Every event payload will use a common envelope.

Example:

```json id="yywwsi"
{
  "event_schema": 1,
  "event_id": "event_01K...",
  "event_type": "scan.probe.completed",
  "occurred_at": "2026-07-30T14:25:31Z",
  "scan_id": "scan_01K...",
  "payload": {
    "probe_id": "bitcoin.chain-state",
    "component_id": "bitcoin.primary",
    "outcome": "completed"
  }
}
```

Initial event types may include:

```text id="pq574f"
scan.created
scan.started
scan.inventory.updated
scan.probe.started
scan.probe.completed
scan.finding.created
scan.diagnosis.created
scan.completed
scan.cancelled
incident.opened
incident.updated
incident.resolved
```

Clients must ignore unknown event types.

SSE events are notifications, not the canonical state store.

After receiving an event, a client may fetch the relevant resource through the HTTP API.

A client that disconnects may miss events. Reconnection and `Last-Event-ID` support may improve continuity, but clients must be able to recover by fetching current resource state.

Event payloads must not become the only representation of a finding or diagnosis.

## Report format

### Canonical report

The canonical shareable report will be JSON.

HTML and other human-readable forms will be derived artifacts.

The JSON report is the machine-readable record against which compatibility is defined.

### Report envelope

Report v1 will include an envelope similar to:

```json id="64hyno"
{
  "format": "satoshi-redline-report",
  "schema_id": "urn:satoshi-redline:schema:report:v1",
  "format_version": 1,
  "report_id": "report_01K...",
  "generated_at": "2026-07-30T14:25:31Z",
  "producer": {
    "name": "SATOSHI//REDLINE",
    "product_version": "0.1.0",
    "build_id": "..."
  },
  "privacy": {
    "profile": "shareable",
    "validation": "passed"
  },
  "scan": {},
  "coverage": {},
  "inventory": {},
  "findings": [],
  "diagnoses": [],
  "recommendations": []
}
```

### Self-contained interpretation

A report must contain enough structured information to understand its conclusions without access to the originating Redline database.

It should include:

* producer version
* report schema version
* scan timing
* scan mode
* platform coverage
* component aliases and kinds
* relevant dependency edges
* exported observations
* findings
* diagnoses
* evaluator and rule versions
* evidence references
* unknown reasons
* recommendation identifiers
* rendered summaries where useful

It must not include:

* raw logs
* raw protocol responses
* raw platform documents
* database exports
* secret references
* external addresses
* onion addresses
* payout addresses
* unrestricted configuration
* arbitrary debug metadata

### Report immutability

An exported report is immutable.

A newer Redline version may:

* read it
* validate it
* render it
* migrate it into an internal read model
* create a new derived report

It must not silently rewrite the original report in place.

If a report is converted from v1 to v2, the resulting document must:

* receive a new report ID
* record that it was derived from another report
* preserve the original file
* identify the migration tool and version
* disclose any information that could not be represented

### Archival support

Report schemas are archival contracts.

The project will retain:

* report schema files
* version-specific readers
* test fixtures
* migration code where needed

The current Redline release should continue reading every stable report major previously released unless a security reason makes parsing unsafe.

If a report can no longer be fully interpreted, Redline must provide a precise compatibility error rather than treating it as corrupt.

## HTML reports

An HTML report will be generated from the validated JSON report projection.

The HTML format is not the canonical machine contract.

An HTML report may:

* embed the sanitized JSON report
* render the dependency graph
* provide expandable evidence
* include static CSS and JavaScript
* function without network access

It must not:

* load external scripts
* contact Redline automatically
* upload data
* depend on a live daemon
* contain more diagnostic data than the JSON report from which it was generated
* include hidden raw payloads

The HTML generator version may change without changing report format v1, provided the embedded canonical data remains valid and the rendered meaning does not change.

## Schema evolution

### Adding an optional field

An optional field may be added within an existing major when:

* old readers can safely ignore it
* new writers do not require old readers to understand it
* its absence has a defined meaning
* it passes privacy review
* it does not alter the interpretation of existing fields

### Deprecating a field

A field may be marked deprecated within the current major.

Deprecation metadata should include:

* reason
* replacement
* first deprecated contract revision
* expected removal major

Writers should stop emitting deprecated fields after clients have migrated where practical.

The field may not be removed until a new major.

### Renaming a field

Renaming is treated as removal plus addition and is therefore breaking.

Within the same major, a new field may be added while the old field remains deprecated.

### Changing units

Changing from seconds to milliseconds, bytes to mebibytes, or blocks to time is breaking unless a new distinctly named field is introduced.

Units should appear in field names where ambiguity is plausible.

### Changing requiredness

Making an optional response field required may be compatible for readers but can break stored documents, test fixtures, and writers.

Requiredness changes will therefore be treated conservatively.

Making an optional request field required is breaking.

Removing a requirement may be compatible only if omitted behavior is clearly defined.

### Changing semantic meaning

Changing meaning is always breaking, even when the JSON shape is unchanged.

For example, changing:

```text id="p4ke6k"
block_age_seconds
```

from “age relative to Redline’s local clock” to “age relative to a network-adjusted clock” requires either:

* a new field
* a new observation-kind version
* a new containing schema major

depending on scope.

## Experimental contracts

The project may need to experiment before stabilizing a contract.

Experimental endpoints or fields must be explicitly namespaced or marked.

Examples:

```text id="pj0w4m"
/api/experimental/
```

or:

```json id="bhbhja"
{
  "experimental": {
    "graph_explanation_v0": {}
  }
}
```

Experimental data:

* is not covered by stable compatibility guarantees
* must remain isolated from stable required fields
* must still obey privacy and raw-data restrictions
* must not be consumed by the production bundled UI without explicit handling
* must not silently become stable through prolonged accidental use

An experimental contract must graduate through explicit schema review.

Stable `/api/v1` fields are never implicitly experimental merely because the product version is below 1.0.

## Client behavior

### Bundled web UI

The bundled web UI will use a generated TypeScript client based on OpenAPI.

The generated client is a transport layer, not the UI state model.

UI code should map transport objects into presentation models where useful.

The UI must:

* check API-major compatibility
* tolerate unknown extensible codes
* ignore unknown SSE event types
* display unsupported report objects generically
* avoid assuming product and API versions are identical
* preserve explicit unknown states

### CLI

The CLI may use internal application code for one-shot scans, but when acting as an API client it must obey the same public contract as other clients.

The CLI must not depend on private daemon structs merely because both are written in Go.

### Future mobile clients

Mobile clients will use the metadata endpoint to determine compatibility.

A client must not connect successfully and then guess at unrecognized required semantics.

When an API major is unsupported, the client should provide a clear compatibility message.

## Compatibility support policy

### API majors

The daemon will always support the API major required by its bundled web UI.

When a new stable API major is introduced, the project should support the immediately previous major for at least two subsequent stable product releases unless:

* maintaining it creates a material security risk
* it would violate privacy guarantees
* the previous contract was explicitly marked experimental

The precise retirement release must be announced through:

* metadata
* release notes
* OpenAPI deprecation markers
* `Deprecation` and `Sunset` response headers where applicable

Because the application is initially local and bundled, this policy is a target rather than a promise of indefinite parallel API maintenance.

### Report majors

Report-reader support is longer-lived.

Stable report formats should remain readable indefinitely where safely practical.

A writer may eventually stop producing an old report version while continuing to read it.

### Observation and diagnostic codes

Stable codes will not be removed from registries merely because the corresponding probe is no longer active.

They may be marked deprecated and associated with replacements.

Old reports remain interpretable through their original codes and evaluator versions.

## Code generation

OpenAPI will be used to generate:

* TypeScript API client types
* TypeScript request helpers
* optional Go transport scaffolding
* schema documentation
* contract examples

Generated code will not define the domain model.

The mapping between domain and transport types will remain explicit and testable.

The project will pin code-generation tool versions.

Generated artifacts must be reproducible.

CI will fail if:

* generated clients are out of date
* generated schemas differ from committed artifacts
* a breaking change is introduced without a major-version decision
* examples no longer validate
* transport mappings omit required fields

The architecture must not depend on one code generator’s proprietary annotations.

The authoritative contract remains OpenAPI and JSON Schema.

## Validation

### Runtime API validation

Production response validation may be selectively enabled depending on performance.

At minimum:

* request payloads will be validated
* report exports will always be validated
* development and CI builds will validate all representative API responses
* integration tests will validate every endpoint against OpenAPI

A response that fails schema validation must not be sent as though it were valid.

The server should produce a safe internal error and record the contract violation without logging the invalid payload.

### Report validation

Every report must pass:

1. projection construction
2. privacy allowlist validation
3. forbidden-data scanning
4. JSON Schema validation
5. evidence-reference integrity checks
6. identifier-reference integrity checks
7. canonical serialization checks

before it is presented as successfully exported.

### Imported-report validation

A report reader will:

1. inspect the minimal envelope
2. select the exact versioned schema
3. enforce size and nesting limits
4. validate the document
5. map it into a version-specific transport type
6. migrate it into an internal read model
7. preserve unsupported optional sections as unsupported, not trusted data

The reader must not deserialize arbitrary polymorphic types based solely on attacker-controlled class names or package paths.

## Schema migration

### Reports

Each report major will have a dedicated reader.

Conceptually:

```text id="5jyv8m"
report v1 JSON
      ↓
ReportV1 transport model
      ↓
v1-to-read-model mapper
      ↓
Current internal report view
```

When report v2 exists:

```text id="a518wr"
report v2 JSON
      ↓
ReportV2 transport model
      ↓
v2-to-read-model mapper
      ↓
Current internal report view
```

Readers should not first mutate all old reports into the newest JSON representation unless a user explicitly requests conversion.

### API

The server may map multiple API majors onto the same internal application services.

Example:

```text id="lgjdu8"
API v1 handler ─┐
                ├── current application service
API v2 handler ─┘
```

Compatibility code belongs at the transport boundary.

The domain model must not be distorted solely to preserve an old transport shape.

## Privacy review of schema changes

Every new external field must answer:

1. What diagnostic or client purpose requires this field?
2. Is the field local-sensitive, normalized-safe, or export-safe?
3. Could it contain a forbidden identifier?
4. Does it originate from raw external input?
5. Is its value bounded?
6. Can it be represented as an enum, count, alias, or category instead?
7. Does the report need it, or only the local API?
8. How will older clients behave when it appears?
9. What is the retention implication?
10. Does its addition change any existing privacy promise?

A field will not be added merely because the information is already present internally.

## Contract tests

### OpenAPI tests

CI will verify:

* schema validity
* operation-ID uniqueness
* example validity
* stable path behavior
* request and response conformance
* no undocumented responses
* no generic untyped response objects
* no raw payload fields
* no accidental breaking changes

### JSON Schema tests

Each report and observation schema will include:

* minimal valid fixture
* complete valid fixture
* invalid-type fixtures
* missing-required-field fixtures
* unknown-closed-enum fixtures
* additional-property fixtures
* forbidden-data fixtures
* forward-compatible optional-field fixtures

### Compatibility-diff tests

CI will compare a proposed contract against the latest released contract.

The check should flag:

* removed fields
* renamed fields
* type changes
* new required fields
* enum changes
* response-shape changes
* changed constraints
* removed endpoints
* altered status codes
* semantic changes that require human confirmation

Automated tooling cannot detect every semantic change. Human review remains required.

### Golden tests

Representative internal domain fixtures will be mapped into:

* API v1 JSON
* report v1 JSON
* SSE v1 events
* HTML report output

Golden tests will verify stable behavior.

Golden output should not prevent compatible additions, but changes must be reviewed intentionally.

### Cross-version tests

When more than one version exists, tests will verify:

* old clients against new servers
* new clients against supported old servers
* old reports read by new software
* report migration behavior
* unsupported major-version errors
* deprecation metadata

## Alternatives considered

### Alternative A: Serialize internal Go structs directly

This is rejected.

It would couple public contracts to:

* Go field layout
* JSON tags
* internal refactoring
* zero-value behavior
* package ownership
* implementation-specific fields

It would also increase the risk of exposing internal sensitive data accidentally.

### Alternative B: Use the product version as every schema version

This is rejected.

Product releases and contracts evolve at different rates.

The approach would make compatibility impossible to reason about and would imply needless breakage with every release.

### Alternative C: Version every endpoint independently

This is rejected for the initial architecture.

Per-endpoint versions provide flexibility but create a difficult compatibility matrix for a small team.

A major-versioned API surface with independently versioned semantic objects is sufficient.

### Alternative D: Put the API version only in an HTTP header

This is rejected.

Header-only negotiation is less visible, harder to inspect manually, and more difficult for reverse proxies and basic clients.

The major version will appear in the path.

Headers may still communicate contract revisions and deprecation.

### Alternative E: Use content-type vendor media versions

Example:

```text id="4y11wo"
application/vnd.satoshi-redline.v1+json
```

This can be useful for complex public APIs but is not selected as the primary version mechanism for the local API.

The added negotiation complexity does not provide enough value over `/api/v1`.

Report files may use a Redline-specific MIME type later without changing the schema decision.

### Alternative F: Version reports using only the producer version

This is rejected.

A report reader should not need a table of every product release to infer document shape.

The report declares its own schema directly.

### Alternative G: Preserve forward compatibility through a generic `extensions` map

This is rejected for v1.

An arbitrary extension map would weaken:

* schema validation
* privacy review
* client predictability
* ADR-005’s data minimization

Future extensions must use registered, namespaced, versioned schemas.

### Alternative H: Treat all enums as open strings

This is rejected.

Core states such as `pass`, `failure`, and `unknown` require stable closed semantics.

The design distinguishes closed enums from extensible registries.

### Alternative I: Generate domain types from OpenAPI

This is rejected.

Transport concerns would leak into the diagnostic engine, and the domain model would become constrained by JSON representation.

Generated types remain at the boundary.

### Alternative J: Support only reports from the current release

This is rejected.

Reports are intended to be shared and retained. Requiring the exact producing release would undermine support workflows and user trust.

## Consequences

### Positive consequences

* Internal Go refactoring does not automatically break clients.
* Every exposed field receives explicit design and privacy review.
* Reports remain interpretable across product releases.
* Mobile and external clients can evolve independently.
* The bundled web UI consumes the same documented API available to other clients.
* New finding and diagnosis codes can be added without an API-major change.
* Older clients can render unknown diagnostics generically.
* Report exports remain self-describing and offline-readable.
* Schema validation catches accidental drift.
* API, report, evaluator, and product versions remain conceptually distinct.
* Multiple API majors can map onto one internal application service.
* Stable message keys permit future localization.
* The system avoids hidden arbitrary metadata channels.
* Compatibility policy becomes testable in CI.

### Negative consequences

* Domain-to-transport mapping adds implementation work.
* The project must maintain multiple related schemas.
* Code generation adds tooling and version pinning.
* Old report readers and API versions create maintenance obligations.
* Developers must classify changes as compatible or breaking.
* Adding a field requires more review than modifying an internal struct.
* The distinction among product, API, report, object, and evaluator versions introduces conceptual complexity.
* Some duplicated structures between API and report schemas are unavoidable.
* Report migrations require long-term fixtures and tests.
* Strict schemas may slow experimental development unless experimental boundaries are used deliberately.

### Neutral consequences

* The local API remains loopback-only under a separate security decision.
* SQLite migrations continue independently.
* The browser UI may use presentation models distinct from generated client types.
* HTML reports remain derived rather than canonical.
* A future hosted service may reuse some schemas but requires its own ADR.
* The privileged-helper protocol remains separately governed.

## Risks and mitigations

### Risk: Contract sprawl overwhelms a small team

**Mitigations:**

* Begin with one API major and one report major.
* Reuse shared JSON Schema definitions where semantics truly match.
* Keep the initial endpoint surface small.
* Avoid versioning individual fields.
* Add independent object versions only where semantic evolution requires them.
* Automate generation, validation, and compatibility checks.

### Risk: External contracts freeze an immature design

**Mitigations:**

* Keep experimental work explicitly outside stable `/api/v1`.
* Stabilize only user-facing contracts needed by real clients.
* Use optional fields for compatible growth.
* Avoid exposing internal details preemptively.
* Introduce v2 when a genuinely better model justifies it rather than distorting v1 indefinitely.

### Risk: Mapping code drifts from schemas

**Mitigations:**

* Generate transport types where practical.
* Validate representative responses in CI.
* Use exhaustive mapping tests.
* Fail builds when generated clients are stale.
* Validate every exported report at runtime.

### Risk: Older clients mishandle new diagnostic codes

**Mitigations:**

* Define codes as extensible registries.
* Require generic fallback rendering.
* Include status, severity, confidence, and safe message text.
* Test the bundled UI with unknown-code fixtures.
* Do not encode client-critical branching solely in a finding code.

### Risk: Adding enum values breaks strict clients

**Mitigations:**

* Mark enums as closed or extensible explicitly.
* Add values to closed enums only in a new major.
* Prefer registries for expanding diagnostic catalogs.
* Include compatibility tests using strict generated clients.

### Risk: Old reports become unsafe to parse

**Mitigations:**

* Enforce input size, nesting, and collection limits.
* Use version-specific typed readers.
* Do not use unsafe polymorphic deserialization.
* Preserve schema files and security patches.
* Reject a report when safe parsing cannot be maintained.

### Risk: API and report projections diverge semantically

**Mitigations:**

* Map both from the same domain model.
* Reuse semantic definitions where privacy permits.
* Add cross-projection tests.
* Document intentional omissions from shareable reports.
* Keep rendered wording secondary to codes and parameters.

### Risk: Compatible additions accidentally leak sensitive data

**Mitigations:**

* Require privacy review for every field.
* Keep report export schemas stricter than local API schemas.
* Apply ADR-005 field allowlists.
* Run forbidden-data canary tests.
* Do not consider “optional” synonymous with “safe.”

### Risk: Supporting previous API majors delays development

**Mitigations:**

* Keep compatibility logic at transport boundaries.
* Limit the target to the immediately previous stable major.
* Retire versions through explicit policy.
* Prefer additive v1 evolution until a real breaking need exists.
* Do not promise indefinite API-major support.

### Risk: Reports depend on externally hosted schemas

**Mitigations:**

* Use stable URNs.
* Bundle schemas with every release.
* Serve schemas through the local daemon.
* Validate offline.
* Treat any public schema website as a mirror, not an authority required at runtime.

## Validation criteria

ADR-006 will be considered successfully implemented when:

1. The local API is exposed under `/api/v1`.
2. `GET /api/v1/meta` reports product, API, event, and report-version support independently.
3. OpenAPI is the authoritative API contract.
4. JSON Schema is the authoritative report contract.
5. Schemas are bundled and usable offline.
6. Internal domain structs are not serialized directly by handlers or exporters.
7. API and report DTOs are separate where privacy requirements differ.
8. Every report declares its schema ID and format version.
9. Reports are validated before export.
10. API examples and representative responses validate in CI.
11. TypeScript client generation is reproducible.
12. Unknown finding and diagnosis codes do not break the bundled UI.
13. Unknown closed-enum values are rejected.
14. Compatible optional-field additions pass compatibility tests.
15. Removed or renamed fields are flagged as breaking.
16. Timestamp, duration, byte, null, and identifier rules are enforced.
17. SSE events use a common versioned envelope.
18. Clients can recover canonical state without relying exclusively on SSE history.
19. Error responses use typed codes and safe details.
20. Report readers enforce input limits before full parsing.
21. Current software can read every released stable report major.
22. Export schemas contain no generic free-form metadata fields.
23. New external fields require privacy classification.
24. The first Bitcoin diagnostic report can be rendered without access to the originating database.
25. The first report can be parsed by a later test build with changed internal domain structs.
26. Product-version changes do not automatically change API or report versions.
27. Evaluator and correlation-rule versions remain distinct from transport versions.
28. Deprecated fields remain supported until a new major removes them.
29. Contract-diff tooling runs in CI.
30. Golden tests verify API v1, report v1, and SSE v1 projections.

## Reconsideration triggers

This ADR should be revisited if:

1. A remote hosted API becomes a core product surface.
2. Multiple independent client teams require longer API support guarantees.
3. GraphQL or another protocol provides a demonstrated advantage over the resource-oriented API.
4. Per-endpoint versioning becomes necessary due to highly uneven evolution.
5. Third-party integrations require a formal extension namespace.
6. Report documents become too large for the current JSON representation.
7. A signed or cryptographically verifiable report format becomes necessary.
8. Binary schema formats become necessary for mobile or remote-agent efficiency.
9. Generated clients repeatedly fail to model required semantics accurately.
10. Indefinite report-reader support creates an unsustainable security burden.
11. Internationalization requires a materially different message contract.
12. Automated remediation adds state-changing API contracts.
13. A public plugin ecosystem requires independent capability and observation schema negotiation.
14. Compatibility requirements prevent necessary privacy improvements.
15. A future version needs to remove data that an older contract required.

A reconsideration trigger does not permit silently changing an existing contract.

A breaking change requires:

* a new API or report major where applicable
* migration or compatibility planning
* explicit documentation
* updated fixtures
* updated privacy review
* a new ADR when the change materially alters contract strategy

## Final decision statement

SATOSHI//REDLINE will expose explicit, versioned API and report schemas that remain independent of product releases, internal Go types, platform-provider models, and database structures.

The HTTP API will use a major version in its path. Reports will declare their own archival format version. Observation kinds, diagnostic codes, evaluator versions, and correlation-rule versions will evolve under separate semantic contracts.

External objects will be constructed through reviewed boundary projections and validated against committed OpenAPI or JSON Schema definitions.

Compatible additions may evolve within a major version. Changes to required structure, closed semantics, units, or meaning require a new major contract.

Older clients must tolerate unknown extensible diagnostic codes. Older reports must remain readable by newer Redline versions where safely practical.

The central rule established by this ADR is:

> A Redline release may change internally without changing its contracts, and a Redline contract may evolve only through explicit compatibility rules—not by accident.
