# ADR-008: Require Explicit Reasons and Coverage Semantics for Unknown Results

* **Date:** 2026-07-30
* **Decision owners:** SATOSHI//REDLINE maintainers
* **Depends on:**

  * ADR-001 — Use a Go Modular Monolith for the Diagnostic Backend
  * ADR-002 — Use Capability-Based, Composable Platform Adapters
  * ADR-003 — Separate Observations, Findings, and Diagnoses
  * ADR-004 — Run the Main Daemon Unprivileged and Isolate Deep-Scan Access in an Optional Privileged Helper
  * ADR-005 — Do Not Persist Raw Logs or Protocol Responses
  * ADR-006 — Version External API and Report Schemas Independently from Internal Models
  * ADR-007 — Compile First-Party Probes into the Redline Binary for v0.1
* **Scope:**

  * Semantics of `unknown`
  * Structured unknown reasons
  * Missing and conflicting evidence
  * Coverage calculation
  * Component and system summary aggregation
  * Cross-layer propagation of uncertainty
  * Continuous-monitoring blind spots
  * User-facing presentation of incomplete evidence
* **Excluded from scope:**

  * Exact visual design of status indicators
  * Alert-delivery channels
  * Final incident-retention policy
  * Automated remediation
  * Probabilistic confidence scoring
  * Product-specific paid support escalation

## Context

SATOSHI//REDLINE must diagnose systems in which the available evidence varies substantially by platform, configuration, privilege level, component version, and current system condition.

Examples include:

* Bitcoin RPC is configured but the cookie file is unreadable.
* Bitcoin RPC is reachable, but the response omits a field required by an older probe.
* Umbrel permits protocol checks but not host restart-history inspection.
* StartOS provides a service health flag but not the underlying process state.
* Two Bitcoin nodes are discovered, but Redline cannot determine which one supplies an Electrum backend.
* A scan is cancelled before all probes complete.
* A service responds once, but the response becomes stale before a dependent check runs.
* Docker reports a container as running while the application protocol does not respond.
* Two evidence sources provide contradictory values.
* A deep-scan capability is disabled by host policy.
* A protocol version is newer than the version the installed probe understands.
* A required log window is truncated before enough evidence can be collected.

In each case, Redline may be unable to establish whether a specific condition passed or failed.

This is not an exceptional edge case. It is an ordinary property of cross-layer diagnosis.

A naive health-check system often collapses this state in one of two unsafe ways:

```text
No failure was observed
        ↓
Assume pass
```

or:

```text
The check could not run
        ↓
Assume failure
```

Both are incorrect.

Failure to observe a fault is not evidence of health.

Failure to observe health is not evidence of a fault.

Redline’s product specification explicitly requires:

> Unknown is valid and preferred over false pass.

That principle needs an enforceable architectural definition.

Without one, different probes may use `unknown` inconsistently:

* one probe may use it for permission denial
* another may use it for unsupported versions
* another may return no finding at all
* another may treat a timeout as failure
* another may silently omit the check
* another may mark a component healthy because all completed checks passed

This would undermine Redline’s central promise of honest diagnosis.

The architecture therefore needs to define:

1. When `unknown` is required.
2. When `unknown` is prohibited.
3. Which structured reason must accompany it.
4. How missing evidence differs from contradictory evidence.
5. How uncertainty affects confidence.
6. How uncertainty propagates into diagnoses.
7. How incomplete coverage affects component and system summaries.
8. How monitoring should treat sustained loss of visibility.
9. How users can understand what Redline knows, what it does not know, and why.

## Decision

`unknown` will be a first-class finding status with strict semantic requirements.

A finding may have the status:

```text
pass
warning
failure
unknown
```

A finding with status `unknown` means:

> The evaluated condition is applicable, or may be applicable, but the available evidence is insufficient to establish pass, warning, or failure without making an unsupported assumption.

Every unknown finding must include at least one structured unknown reason.

An unknown finding may not exist without:

* a stable finding code
* a component reference
* an evaluator reference and version
* a structured reason code
* the missing, stale, ambiguous, or conflicting evidence involved
* the time the condition was evaluated
* a statement of whether more evidence could resolve it

`unknown` will remain distinct from:

* `not_applicable`
* `unsupported component`
* `probe failed internally`
* `scan not selected`
* `component not present`
* `finding not evaluated`
* `diagnosis inconclusive`

These states may contribute to an unknown finding, but they are not interchangeable with it.

System and component summaries will expose **health state and coverage state separately**.

A partial scan must never be rendered as fully healthy merely because no completed check failed.

The central decision is:

> Redline will never represent absence of evidence as evidence of health. Every unresolved applicable condition will remain visibly unknown, with a structured explanation of why.

## Decision drivers

The decision drivers, in priority order, are:

1. Prevent false green states.
2. Preserve the distinction between target failure and evidence failure.
3. Explain exactly why a conclusion could not be reached.
4. Make restricted-platform limitations honest and understandable.
5. Keep cross-layer diagnoses from overstating causality.
6. Allow users to improve coverage when possible.
7. Make unknown behavior consistent across all probes and platforms.
8. Support stable reporting and API contracts.
9. Detect sustained monitoring blind spots without calling them component failures.
10. Preserve known failures even when other parts of the scan remain unknown.

## Semantic distinctions

### Probe execution outcome

A probe execution describes whether evidence collection ran successfully.

Under ADR-003, probe execution outcomes include:

```text
completed
partial
unavailable
failed
cancelled
```

These outcomes describe the collector.

They do not directly describe component health.

Examples:

```text
Probe execution: unavailable
Reason: permission denied reading RPC cookie
```

```text
Probe execution: completed
Observation: TCP connection refused
```

The first may produce an unknown finding.

The second may produce a failure finding because connection refusal is evidence about the target.

### Finding status

A finding evaluates one diagnostic condition.

Examples:

```text
bitcoin.rpc.reachable = failure
```

when Redline reached the configured host and received a connection refusal.

```text
bitcoin.rpc.reachable = unknown
```

when Redline could not obtain the configured endpoint or required authentication reference.

### Applicability

Applicability remains separate from status.

Supported applicability states are:

```text
applicable
not_applicable
undetermined
```

Examples:

* A TLS certificate check is `not_applicable` to an explicitly configured plaintext endpoint.
* A pruning configuration check is `not_applicable` when the node is known not to be pruned.
* A systemd restart-loop check may have applicability `undetermined` when Redline cannot determine whether systemd manages the component.
* An applicable check with inaccessible restart history is `unknown`.

`not_applicable` is not a pass.

An evaluator must not use `unknown` merely because its condition does not apply.

### Unsupported component or version

Unsupported collection behavior is not automatically a component failure.

Example:

```text
Bitcoin implementation detected: future implementation
Probe support: unavailable
Finding: bitcoin.chain.synchronized = unknown
Reason: unsupported_implementation
```

The implementation itself is not necessarily unhealthy.

Redline simply cannot evaluate that condition reliably.

### Internal engine error

An evaluator defect, panic, schema mismatch, or internal programming error is not itself an unknown reason about the target.

The engine must record the internal failure separately.

Dependent findings may become unknown with a reason such as:

```text
evaluation_unavailable
```

but the report must distinguish:

```text
Redline could not evaluate this condition
```

from:

```text
The target system produced insufficient evidence
```

### Inconclusive diagnosis

`unknown` applies to findings.

A diagnosis that cannot establish causality uses a diagnosis classification such as:

```text
inconclusive
break_point
symptom_cluster
```

A diagnosis does not receive the finding status `unknown`.

Instead, it records:

* confidence
* unresolved questions
* blocking unknown findings
* plausible alternatives
* missing dependency evidence

They must not contain arbitrary provider or protocol text.

## Unknown reason structure

An unknown reason will be represented as structured data.

Conceptually:

```go
type UnknownReason struct {
    Code             UnknownReasonCode
    Stage            DiagnosticStage
    SummaryKey       MessageKey
    Parameters       map[string]TypedValue
    CapabilityID     *CapabilityID
    ProviderID       *string
    ProbeExecutionID *ProbeExecutionID
    EvidenceRefs     []EvidenceReference
    Retryability     Retryability
    Resolution       ResolutionClass
}
```

### Stage

The stage identifies where uncertainty arose:

```text
discovery
capability_resolution
collection
normalization
evaluation
correlation
```

### Retryability

Retryability indicates whether repeating the same operation may resolve the issue:

```text
retryable
not_retryable
conditionally_retryable
unknown
```

Examples:

* A transient timeout may be retryable.
* An unsupported protocol version is not retryable without a software update.
* Permission denial is conditionally retryable after configuration changes.
* Ambiguous component binding is conditionally retryable after user selection.

Retryability is not a promise that retrying will succeed.

### Resolution class

Resolution describes the kind of action that could improve certainty:

```text
retry_scan
enable_deep_scan
grant_host_access
configure_binding
correct_configuration
update_redline
update_component
enable_optional_check
manual_local_inspection
not_resolvable_on_platform
none_known
```

This is a structured coverage-resolution hint.

It is not an automated remediation command.

### Parameters

Parameters must be typed and bounded.

Permitted examples include:

```text
required capability ID
supported version range
observed version
maximum evidence age
actual evidence age
number of conflicting sources
required scan mode
```

Parameters must not contain:

* raw provider errors
* credentials
* external IP addresses
* onion addresses
* payout addresses
* raw logs
* raw protocol messages
* unrestricted configuration values

## Primary and secondary reasons

An unknown finding may have more than one reason.

Example:

```text
Electrum synchronization: unknown

Primary:
Bitcoin dependency binding is ambiguous.

Secondary:
One candidate Bitcoin node timed out.
```

The evaluator must select one primary reason deterministically.

Default priority should favor the reason closest to the fundamental evidence blockage.

A preliminary order is:

1. Binding or applicability ambiguity
2. Required capability unavailable
3. Security or normalization rejection
4. Unsupported implementation or version
5. Collection failure
6. Stale or conflicting evidence
7. Optional evidence limitation
8. Internal evaluation failure

This order is guidance, not a universal causal ranking.

Evaluator-specific logic may select a more appropriate primary reason, but the behavior must be deterministic and tested.

Secondary reasons remain available for expert inspection.

## Rules for selecting status

### Pass

A finding may be `pass` only when:

1. The condition is applicable.
2. All evidence defined as required by the evaluator is available.
3. The evidence falls within freshness and quality bounds.
4. The evaluator’s pass predicate is positively satisfied.
5. No contradictory evidence invalidates the conclusion.
6. The evaluator completed successfully.

No-error, no-event, or no-failure-found is insufficient unless the observation method itself establishes meaningful absence.

Example:

```text
No disk-write errors appeared in accessible logs.
```

does not prove:

```text
Filesystem health = pass
```

unless the evaluator explicitly defines that log source as sufficient evidence and coverage is complete.

### Warning

A finding may be `warning` when available evidence positively satisfies a warning condition.

Missing optional evidence may reduce confidence without changing the status.

A warning must not be used merely to avoid displaying unknown.

### Failure

A finding may be `failure` when available evidence positively satisfies a failure condition.

Missing unrelated or optional evidence does not erase a confirmed failure.

Example:

```text
Bitcoin RPC connection refused.
Restart history unavailable.
```

The RPC reachability finding remains a failure.

Restart-loop analysis may separately remain unknown.

### Unknown

A finding must be `unknown` when:

1. The condition is applicable or possibly applicable.
2. Required evidence is missing, stale, contradictory, unsafe to normalize, or below the evaluator’s quality threshold.
3. The evaluator cannot reliably select pass, warning, or failure.
4. No direct evidence independently establishes another status.

Unknown must not be used to soften a known failure.

### Partial evidence with a decisive result

Not every missing observation forces a finding to unknown.

If the evaluator has sufficient required evidence to determine status, missing optional evidence affects:

* confidence
* explanatory detail
* recommendation specificity
* coverage metadata

Example:

```text
TCP connection refused.
TLS handshake not attempted.
```

Endpoint reachability can still be a failure.

TLS status may be not evaluated or unknown as a separate finding.

### Conflicting evidence

Conflicting evidence produces unknown when the conflict prevents a reliable conclusion.

Example:

```text
StartOS service health: running
Protocol check: repeated timeout
```

This does not necessarily require the high-level service finding to be unknown.

The evaluator may produce:

```text
service process state = pass
application protocol reachability = failure
```

The evidence is only conflicting if two sources claim to measure the same condition under compatible semantics and timing.

Redline must not collapse different layers into a false conflict.

## Required and optional checks

Each scan profile will define which findings are:

```text
required
optional
informational
```

This classification is contextual.

For example:

* Bitcoin RPC reachability may be required for a Bitcoin node component.
* Restart-history analysis may be optional in Safe Scan and required in a specific Deep Scan profile.
* Tor egress may be optional unless the component is configured to depend on Tor.
* TLS validation is not applicable to a plaintext local endpoint.

The classification must be recorded in scan-plan metadata.

A check’s requirement level must not change after execution merely to improve the summary.

### Required

A required finding contributes directly to whether the component can be called fully assessed.

An unknown required finding creates a coverage gap.

### Optional

An unknown optional finding reduces optional coverage but does not necessarily block an otherwise supported healthy conclusion.

The UI must still disclose the limitation.

### Informational

An informational finding contributes context but not component health aggregation.

An unavailable informational check may be omitted from the primary summary while remaining visible in expert coverage details.

## Coverage model

Redline will not represent coverage solely as one percentage.

A single number could obscure the difference between:

* one missing critical check
* ten missing informational checks
* a platform where no required checks ran
* a complete safe scan without optional deep evidence

Coverage will be represented structurally.

A coverage summary should include:

```go
type CoverageSummary struct {
    ApplicableRequired       uint
    AssessedRequired         uint
    UnknownRequired          uint

    ApplicableOptional       uint
    AssessedOptional         uint
    UnknownOptional          uint

    InformationalCompleted   uint
    InformationalUnavailable uint

    NotApplicable            uint
    NotSelected              uint
}
```

### Assessed

A finding is assessed when its status is:

```text
pass
warning
failure
```

Unknown is not assessed.

### Required coverage ratio

A UI may derive:

```text
assessed_required / applicable_required
```

but must also display the counts and unknown reasons.

A 95% coverage number must not hide that the missing 5% contains the only critical storage-writeability check.

### Impact-weighted coverage

Redline may categorize coverage gaps by potential impact:

```text
critical-impact unknowns
high-impact unknowns
medium-impact unknowns
low-impact unknowns
```

The system will not initially compute a pseudo-precise weighted score.

Counts and categories are more honest than a composite number whose weighting has no empirical calibration.

### Platform-expected limitations

Coverage should distinguish:

```text
expected platform limitation
unexpected access loss
user-disabled check
unsupported component version
transient collection failure
```

An Umbrel app that cannot inspect host systemd state is different from a generic Linux installation where systemd access unexpectedly stopped working.

Both remain unknown where applicable, but their operational meaning differs.

## Health and coverage are separate axes

Component and system summaries will not collapse health and coverage into one status.

A summary will expose at least:

```go
type DiagnosticSummary struct {
    Health   HealthSummary
    Coverage CoverageState
}
```

### Health summary

Initial health summary values:

```text
healthy
warning
failure
no_conclusion
```

Definitions:

* **healthy** — required applicable findings were assessed and none produced warning or failure.
* **warning** — at least one warning exists and no failure overrides it.
* **failure** — at least one failure exists.
* **no_conclusion** — no warning or failure is established, but required evidence is too incomplete to call the component healthy.

### Coverage state

Initial coverage states:

```text
complete
partial
minimal
unavailable
```

Definitions:

* **complete** — all required applicable checks were assessed.
* **partial** — some required checks were assessed and some remain unknown.
* **minimal** — only a small or insufficient subset of required checks was assessed.
* **unavailable** — no required checks could be meaningfully assessed.

Exact thresholds between partial and minimal will be defined by scan-profile policy rather than hidden global percentages.

### Combined examples

```text
Health: healthy
Coverage: complete
```

Redline may render:

```text
Healthy
```

```text
Health: failure
Coverage: partial
```

Redline may render:

```text
Failure confirmed; some additional checks were unavailable
```

```text
Health: no_conclusion
Coverage: partial
```

Redline may render:

```text
No confirmed failure, but Redline could not complete enough checks to
determine health
```

```text
Health: warning
Coverage: complete
```

Redline may render:

```text
Warning
```

A component with partial required coverage must not receive an unqualified green healthy state.

## Aggregation rules

### Known failures are preserved

A confirmed failure must remain visible even when other findings are unknown.

Example:

```text
Bitcoin RPC reachability: failure
Filesystem capacity: unknown
Restart history: unknown
```

The component summary is:

```text
Health: failure
Coverage: partial
```

not:

```text
Health: unknown
```

Unknown findings must not erase known failures.

### Unknown can block healthy

If all assessed findings pass but one required finding is unknown:

```text
Health: no_conclusion
Coverage: partial
```

The summary must not be healthy.

### Optional unknowns

If all required findings pass and only optional checks are unknown:

```text
Health: healthy
Coverage: complete required coverage
Optional coverage: partial
```

The UI may show a qualified healthy state with an optional-coverage notice.

### Not applicable

Not-applicable findings do not reduce coverage.

### Cancelled scans

A cancelled scan reports its completed findings normally.

Unfinished required findings become unknown or not evaluated according to whether the evaluator was instantiated.

The scan itself must be labeled incomplete.

A cancelled scan cannot receive a complete coverage state.

## Cross-layer propagation

Unknown findings influence diagnoses, but uncertainty does not automatically propagate to every downstream component.

The correlation engine must reason about which missing evidence is material to the proposed explanation.

### Material unknown

An unknown is material when resolving it could change the diagnosis classification, root-cause component, break point, or affected dependency path.

Example:

```text
Sparrow cannot reach Electrum.
Electrum process state is unknown.
Electrum protocol endpoint is unreachable.
Firewall state is unknown.
```

Redline may identify:

```text
Confirmed break point: wallet-to-Electrum connectivity
```

It may not claim:

```text
Root cause: Electrum process stopped
```

because process and firewall evidence remain unknown.

### Non-material unknown

An unknown does not block a diagnosis when it cannot change the supported conclusion.

Example:

```text
Bitcoin data volume is confirmed full.
Bitcoin is repeatedly failing writes.
Bitcoin is restarting.
Fulcrum is behind.
Docker image metadata is unknown.
```

Unknown image metadata does not prevent Redline from identifying storage exhaustion as the likely root cause.

### Root-cause constraint

A correlation rule may emit `root_cause` only when all evidence declared material by that rule is assessed.

An unresolved material finding forces one of:

```text
break_point
contributing_factor
symptom_cluster
inconclusive
```

### Blocking unknown references

Every diagnosis that is weakened by uncertainty will include references to the blocking unknown findings.

Example:

```json
{
  "classification": "break_point",
  "confidence": "medium",
  "blocking_unknowns": [
    "finding_firewall_binding",
    "finding_electrum_process_state"
  ]
}
```

This allows the UI to explain why Redline stopped short of a stronger claim.

## Unknown transitions in continuous monitoring

Continuous monitoring introduces a distinction between:

* the component becoming unhealthy
* Redline losing visibility into the component

These events must not be conflated.

### Health incident

A health incident is based on warning or failure findings about the target.

Example:

```text
Bitcoin RPC connection refused
```

### Coverage incident

A coverage incident represents sustained loss of required diagnostic visibility.

Example:

```text
Redline has been unable to authenticate to Bitcoin RPC for 20 minutes.
The node’s current synchronization state is unknown.
```

A coverage incident does not claim that Bitcoin itself failed.

Initial coverage-incident classification:

```text
observability_gap
```

Coverage incidents may be useful when:

* a previously working capability becomes denied
* a required endpoint binding disappears
* a helper becomes unavailable
* repeated timeouts prevent a required check
* an update introduces an unsupported protocol version
* evidence remains stale beyond a configured monitoring window

### Debounce and hysteresis

A single transient unknown should not necessarily open a coverage incident.

Continuous monitoring will use:

* consecutive-failure thresholds
* elapsed-time thresholds
* recovery confirmation
* reason-specific debounce
* required-check impact

Example:

```text
One RPC timeout:
No coverage incident yet.

Three consecutive RPC timeouts over five minutes:
Open observability-gap incident.
```

The exact thresholds will be defined in monitoring policy.

### Recovery

A coverage incident resolves when the required check becomes assessed again.

If the recovered finding is a failure, the coverage incident resolves and a health incident may remain or open.

Example:

```text
Before:
Bitcoin synchronization unknown because RPC authentication was unavailable.

After credentials fixed:
Bitcoin RPC reachable, but node is 14 hours behind.

Result:
Coverage restored.
Health failure detected.
```

## User-facing presentation

Unknown must be visible without overwhelming non-expert users.

### Required message structure

Every user-visible unknown should answer:

1. What could Redline not determine?
2. Why could it not determine it?
3. What did Redline establish despite that limitation?
4. Can the uncertainty be resolved?
5. What action would improve coverage, if any?

Example:

```text
Bitcoin restart behavior: Unknown

Redline could not read systemd restart history in Safe Scan.

What Redline did confirm:
Bitcoin RPC is reachable and the node is synchronized.

To inspect restart history:
Run a Deep Scan with the privileged helper enabled.
```

### Platform restriction example

```text
Host filesystem health: Unknown

This Umbrel application does not have supported access to the host
filesystem.

Bitcoin RPC and Electrum synchronization checks completed normally.

This limitation cannot be resolved from inside the current Umbrel app.
```

### Ambiguous binding example

```text
Electrum-to-Bitcoin synchronization: Unknown

Redline discovered two Bitcoin nodes but could not determine which one
supplies Fulcrum.

Select the Fulcrum dependency in component settings to enable this check.
```

### Unsupported version example

```text
DATUM template freshness: Unknown

The installed DATUM version returned a status schema this Redline release
does not understand.

Update Redline or use a supported DATUM interface.
```

### No fake green language

When required coverage is incomplete, Redline must avoid language such as:

```text
Everything looks good
All systems operational
No issues found
Healthy
```

Acceptable language includes:

```text
No confirmed failures in completed checks
Required coverage is incomplete
Three checks passed; two could not be evaluated
```

### Grouping

Multiple unknown findings caused by the same limitation should be grouped.

Example:

```text
Five host-level checks were unavailable because Deep Scan is not enabled.
```

The underlying findings remain individually addressable for expert inspection.

This prevents the UI from showing dozens of repetitive unknown cards.

### Expert view

Expert views should expose:

* reason code
* diagnostic stage
* required capability
* provider
* probe execution
* retryability
* resolution class
* missing evidence
* blocking effect on diagnoses
* timestamps
* coverage role

Raw errors and forbidden data remain excluded.

## Reports and API contracts

Under ADR-006, unknown-reason codes form an extensible registry.

Older clients must tolerate unknown reason codes and render a generic fallback using:

* finding code
* summary key
* status
* stage
* retryability
* resolution class

A report must preserve enough information to understand why a finding was unknown without access to the originating daemon.

An exported unknown finding should include:

```json
{
  "code": "service.restart-loop",
  "status": "unknown",
  "applicability": "applicable",
  "unknown_reasons": [
    {
      "code": "access.platform_restriction",
      "stage": "capability_resolution",
      "retryability": "not_retryable",
      "resolution": "not_resolvable_on_platform"
    }
  ],
  "missing_evidence": [
    {
      "kind": "service.restart-history",
      "role": "required"
    }
  ]
}
```

Reports must not include raw provider error text.

## Persistence

Unknown findings are diagnostic records and may be persisted.

Persisted unknown data may include:

* reason codes
* diagnostic stage
* retryability
* resolution class
* capability and provider identifiers
* missing-evidence references
* evaluator version
* timestamps
* impact category
* coverage role

It must not include:

* raw protocol errors
* raw system errors
* raw log lines
* forbidden identifiers
* unrestricted provider messages
* secret-bearing configuration values

Historical unknown findings must remain immutable.

If a later scan resolves the uncertainty, it creates a new assessed finding rather than modifying the earlier unknown.

This allows Redline to reconstruct:

```text
08:00 — synchronization unknown because RPC credentials were unavailable
08:10 — RPC access restored
08:10 — synchronization failure detected
09:05 — node synchronized
```

## Unknown-reason ownership

The layer that has enough information to classify the limitation should produce the structured reason.

### Capability provider

A provider may classify:

```text
permission denied
unsupported operation
rate limited
target disappeared
```

### Probe

A probe may classify:

```text
protocol response invalid
required field missing
response too large
unsupported protocol message
```

### Evaluator

An evaluator may classify:

```text
evidence stale
evidence conflicting
required observation missing
threshold unavailable
```

### Correlation engine

The correlation engine may record:

```text
dependency unknown
material finding unknown
causal sequence unresolved
```

The final unknown reason attached to a finding is owned by the evaluator, which maps lower-level structured limitations into the finding’s semantic context.

Lower-level objects retain their own error categories for traceability.

## Error mapping

Providers and probes must not invent free-form unknown behavior independently.

Each evaluator will define explicit mappings from its expected input limitations.

Example:

```text
Capability permission denied
        ↓
Finding unknown reason:
access.permission_denied
```

```text
RPC response missing required chain-state field
        ↓
Finding unknown reason:
compatibility.unsupported_response_schema
```

```text
Bitcoin and Electrum observations exceed allowed skew
        ↓
Finding unknown reason:
evidence.temporally_inconsistent
```

Unexpected unmapped conditions produce:

```text
evaluation.internal_error
```

and an internal engine error record.

They do not default silently to pass, failure, or a generic unknown without traceability.

## Alternatives considered

### Alternative A: Omit checks that cannot run

This is rejected.

Silent omission makes the report appear more complete than it is and prevents users from understanding coverage limitations.

### Alternative B: Treat unavailable checks as pass

This is rejected because it creates fake healthy states.

### Alternative C: Treat unavailable checks as failure

This is rejected because inability to observe a component does not prove the component failed.

### Alternative D: Use only a free-form reason string

This is rejected.

Free-form strings are difficult to:

* aggregate
* localize
* version
* test
* compare over time
* render consistently
* keep free of sensitive values

Structured codes remain canonical. Rendered text is derived.

### Alternative E: Use one generic `insufficient_data` reason

This is rejected.

Users and correlation rules need to distinguish:

* permissions
* ambiguity
* unsupported versions
* timeouts
* stale evidence
* conflicting evidence
* policy restrictions
* cancellations

### Alternative F: Collapse health and coverage into one status

This is rejected.

A system can have:

* a confirmed failure with incomplete coverage
* no confirmed failure with insufficient coverage
* complete coverage with a warning
* healthy required checks with missing optional diagnostics

One status cannot represent both axes honestly.

### Alternative G: Make the whole component unknown when any check is unknown

This is rejected.

A confirmed failure must remain visible.

Unknown evidence should constrain unsupported conclusions, not erase known facts.

### Alternative H: Ignore unknowns in root-cause analysis

This is rejected.

A missing material upstream check can make a root-cause conclusion unsound.

### Alternative I: Require complete evidence before reporting any finding

This is rejected.

Independent findings may remain useful even when other checks are unavailable.

Redline should provide partial results with explicit coverage.

### Alternative J: Assign numerical probabilities to unknown causes

This is rejected for v0.1.

Redline does not have a calibrated probabilistic model.

Structured reasons, confidence levels, and alternatives are more honest.

## Consequences

### Positive consequences

* Redline cannot silently convert incomplete scans into healthy results.
* Users can see why a condition could not be evaluated.
* Restricted platforms remain useful without pretending to offer full coverage.
* Known failures remain visible alongside unknown checks.
* Root-cause claims are constrained by material evidence gaps.
* Monitoring can distinguish component failure from loss of visibility.
* Reports preserve uncertainty in a machine-readable form.
* Unknown results can be grouped and explained consistently.
* Users can identify which configuration or privilege change would improve coverage.
* Probe implementations share one semantic standard.
* Support analysis can distinguish platform limitations from transient faults.
* Historical changes from unknown to assessed states remain auditable.

### Negative consequences

* The status and summary model becomes more complex.
* Every evaluator must define missing-evidence behavior explicitly.
* The unknown-reason registry requires governance.
* The UI must present two axes instead of one simple color.
* Coverage aggregation requires scan-profile metadata.
* Reports contain more structured limitation information.
* Contributors must write additional tests for uncertainty paths.
* Some users may perceive frequent unknowns as product weakness.
* Monitoring must manage coverage incidents separately from health incidents.
* Ambiguous edge cases require careful evaluator-specific decisions.

### Neutral consequences

* Some scans will legitimately end without a system-wide health conclusion.
* Deep Scan may improve coverage without changing diagnostic semantics.
* Optional unknown checks do not necessarily block healthy required coverage.
* Unknown findings remain ordinary persisted domain records.
* Future clients may present coverage differently while preserving canonical semantics.

## Risks and mitigations

### Risk: Redline produces too many unknown findings

**Mitigations:**

* Group findings with the same root limitation.
* Distinguish required, optional, and informational checks.
* Avoid instantiating checks known to be not applicable.
* Improve platform capability providers over time.
* Prefer direct protocol evidence when host evidence is unavailable.
* Keep expert details expandable rather than always visible.

### Risk: Unknown becomes a convenient fallback for weak evaluators

**Mitigations:**

* Require explicit reason codes.
* Require declared missing evidence.
* Test all status boundaries.
* Review whether direct evidence supports pass or failure.
* Track evaluator rates of unknown outcomes.
* Treat unexplained generic unknowns as defects.

### Risk: Health summaries become confusing

**Mitigations:**

* Use plain-language combined summaries.
* Lead with confirmed failures.
* Display coverage as a qualification, not a competing alarm.
* Use consistent wording across CLI, web UI, and reports.
* Test presentation with non-expert users.

### Risk: Optional missing evidence blocks healthy status accidentally

**Mitigations:**

* Record requirement level in the scan plan.
* Make aggregation rules deterministic.
* Test optional and required coverage independently.
* Do not let evaluators change requirement level after execution.

### Risk: Required checks are classified as optional to improve UX

**Mitigations:**

* Define scan profiles in reviewed first-party configuration.
* Record profile versions.
* Require architectural or diagnostic review for requirement changes.
* Include critical dependency checks in validation fixtures.

### Risk: Material unknowns are ignored by correlation rules

**Mitigations:**

* Correlation rules declare material inputs.
* Root-cause tests include missing-evidence scenarios.
* Diagnoses record blocking unknown references.
* Architecture tests require material-input handling.

### Risk: Coverage percentages create false precision

**Mitigations:**

* Keep structured counts canonical.
* Show critical and high-impact gaps explicitly.
* Avoid one weighted health score.
* Label percentages as assessed-check coverage only.

### Risk: Coverage incidents create noisy alerts

**Mitigations:**

* Open them only for sustained loss of required visibility.
* Apply reason-specific debounce.
* Avoid incidents for expected unsupported optional checks.
* Resolve them separately from health incidents.
* Allow monitoring-profile configuration.

### Risk: Unknown reasons expose sensitive details

**Mitigations:**

* Use stable codes and typed safe parameters.
* Exclude raw provider text.
* Alias local resources.
* Apply ADR-005 persistence and export validation.
* Add canary-secret tests to reason rendering.

### Risk: Old clients do not understand a new reason code

**Mitigations:**

* Keep reason codes extensible.
* Include canonical status and stage.
* Require generic fallback rendering.
* Preserve safe rendered summaries in reports where useful.

## Testing strategy

### Evaluator status tests

Every evaluator must test:

* positive pass
* warning
* failure
* required evidence missing
* optional evidence missing
* stale evidence
* conflicting evidence
* cancelled collection
* unsupported version
* permission denial
* internal evaluator failure
* not-applicable behavior

### Invariant tests

Tests must verify:

1. Every unknown finding has at least one reason.
2. Every unknown finding identifies missing or invalid evidence.
3. No pass exists with missing required evidence.
4. No not-applicable finding is represented as unknown.
5. No direct failure is softened to unknown by unrelated missing evidence.
6. Unknown reasons contain no unbounded external strings.
7. Root-cause diagnoses contain no unresolved material unknowns.
8. Blocking unknowns are referenced by weakened diagnoses.

### Coverage tests

Coverage aggregation must test:

* all required findings pass
* required warning
* required failure
* one required unknown
* all required unknown
* optional unknown only
* not-applicable checks
* cancelled scan
* mixed failure and unknown
* zero applicable checks
* platform-expected restrictions
* unexpected capability loss

### Presentation tests

Golden tests should verify wording for:

* healthy with complete coverage
* healthy required checks with optional gaps
* confirmed failure with partial coverage
* no conclusion with partial coverage
* unavailable coverage
* grouped platform restrictions
* ambiguous bindings
* unsupported versions
* security-driven input rejection

### Monitoring tests

Continuous-monitoring tests must verify:

* one transient timeout does not immediately open a coverage incident
* sustained unknown required checks open an observability-gap incident
* coverage recovery resolves that incident
* recovery into failure opens or preserves a health incident
* optional unknown checks do not open required-coverage incidents
* expected permanent platform restrictions do not repeatedly alert

### Cross-layer tests

Correlation fixtures must include:

* confirmed root cause with no material unknowns
* break point with unresolved upstream cause
* multiple alternatives due to unknown evidence
* known downstream failure with unknown unrelated checks
* known upstream failure with optional unknown metadata
* conflicting observations from different semantic layers

### Privacy tests

Canary data embedded in lower-level provider errors must not appear in:

* unknown reason parameters
* application logs
* API responses
* SQLite
* reports
* coverage incidents

## Architecture enforcement

Automated checks should enforce that:

1. Unknown findings cannot be constructed without reasons.
2. Pass findings require a complete required-input declaration.
3. Applicability and status use separate types.
4. Component summaries expose health and coverage separately.
5. Correlation rules declare material inputs.
6. Unknown reason codes come from the registered taxonomy.
7. Unknown reason parameters use approved typed values.
8. Provider error strings do not cross into findings directly.
9. API and report schemas require reasons for unknown findings.
10. Optional and required coverage roles are recorded in the scan plan.
11. No UI projection converts `no_conclusion` into healthy.
12. Monitoring coverage incidents use a distinct classification from health incidents.

## Validation criteria

ADR-008 will be considered successfully implemented when:

1. Every unknown finding contains at least one registered reason code.
2. Every unknown finding identifies the missing, stale, conflicting, or unusable evidence.
3. Unknown reason parameters are typed, bounded, and privacy-safe.
4. Not-applicable checks are not represented as pass or unknown.
5. A missing required input can never produce pass.
6. A direct failure remains failure even when unrelated evidence is unknown.
7. Optional missing evidence does not automatically block required healthy coverage.
8. Scan profiles record required, optional, and informational checks.
9. Component summaries expose health and coverage separately.
10. Partial required coverage cannot produce an unqualified healthy state.
11. Confirmed failure with partial coverage remains visibly failed.
12. Unknown checks do not silently disappear from reports.
13. Repeated reasons can be grouped without deleting underlying findings.
14. Root-cause diagnoses cannot contain unresolved material unknowns.
15. Weakened diagnoses reference their blocking unknown findings.
16. Reports preserve structured unknown reasons.
17. Older clients can render unknown reason codes they do not recognize.
18. Raw provider error text does not enter unknown findings.
19. Sustained loss of required monitoring can create an observability-gap incident.
20. Coverage incidents remain distinct from component-health incidents.
21. A recovered capability resolves the coverage incident without assuming component health.
22. Cancelled scans cannot report complete coverage.
23. Stale and temporally inconsistent evidence produce explicit reasons.
24. Unsupported versions produce unknown rather than pass or component failure.
25. Platform restrictions are distinguished from unexpected access failures.
26. CLI, API, web UI, and report projections use consistent semantics.
27. The first Bitcoin and Electrum vertical slices demonstrate complete evidence lineage for unknown findings.
28. Architecture tests prevent construction of reasonless unknowns.
29. Golden tests verify no fake-green language.
30. Historical unknown findings remain immutable after later scans resolve the condition.

## Reconsideration triggers

This ADR should be revisited if:

1. The four finding statuses prove insufficient for important diagnostic conditions.
2. Users consistently misunderstand the distinction between unknown and failure.
3. Separate health and coverage axes create unacceptable UI complexity.
4. Continuous monitoring requires more detailed observability states.
5. A calibrated probabilistic diagnostic model is introduced.
6. Third-party rules require a formal missing-data algebra.
7. Distributed agents create new categories of partial or delayed evidence.
8. The required-versus-optional model cannot represent real scan profiles.
9. Unknown reason-code growth becomes unmanageable.
10. Impact-weighted coverage becomes necessary for automated alert prioritization.
11. Automated remediation requires stronger certainty classifications.
12. Platform vendors need standardized machine-actionable coverage contracts.
13. Reports need cryptographic attestations of which checks were actually executed.
14. A future compliance mode requires a stricter concept than diagnostic coverage.
15. User research demonstrates that a different canonical uncertainty model is materially clearer.

A reconsideration trigger does not permit silently treating unknown as pass or failure.

Any change to the core uncertainty semantics requires:

* a new ADR
* API and report compatibility review
* evaluator migration planning
* updated aggregation rules
* updated report fixtures
* explicit treatment of old unknown findings

## Final decision statement

SATOSHI//REDLINE will treat `unknown` as a first-class, evidence-based diagnostic result rather than a fallback or omission.

Every unknown finding will state exactly why Redline could not determine pass, warning, or failure. It will identify the blocked diagnostic stage, missing or conflicting evidence, retryability, and the class of action that could improve coverage.

Not applicable, unsupported, unselected, internally failed, and inconclusive are related but distinct states and will not be collapsed into one ambiguous bucket.

Known failures will remain visible even when other checks are unknown. Unknown required checks will prevent an unqualified healthy result.

Component and system summaries will represent health and diagnostic coverage separately.

Continuous monitoring will distinguish a component failure from Redline losing the ability to observe that component.

The central rule established by this ADR is:

> Redline may say that it does not know, but it must always know why it does not know.
